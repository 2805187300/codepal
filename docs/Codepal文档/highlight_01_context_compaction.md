# 亮点①：两层渐进式上下文压缩

---

## 1. 为什么要做这个？——背景

### 1.1 什么是"上下文窗口"

每次你跟 LLM 对话，所有的对话历史都要打包塞进一个请求发给 API。这个请求有大小限制，叫做**上下文窗口（Context Window）**，Claude 是 200,000 个 Token，超过这个数就会被 API 直接拒绝，返回 400 错误。

Token 可以粗略理解为"字"，1 个 Token ≈ 3.5 个英文字符 ≈ 1.5 个中文字符。

### 1.2 Agent 为什么特别容易撑爆上下文

普通对话（你问我答）不太会有这个问题，因为一条问题 + 一条回答，加起来才多少 Token。

但 Agent 不一样。Agent 是这样跑的：

```
第 1 轮：用户说"帮我重构这个项目"
        ↓
第 2 轮：Agent 调用 ReadFile，工具返回一整个文件的内容（可能 2000 行代码）
        ↓
第 3 轮：Agent 调用 Grep，工具返回几百行搜索结果
        ↓
第 4 轮：Agent 调用 EditFile，修改代码
        ↓
第 5 轮：Agent 调用 Bash，运行测试，返回编译错误日志...
        ↓
...几十轮之后...
```

每一轮的"工具返回结果"都原封不动地追加到历史里。跑几十轮下来，历史消息轻轻松松就到了几十万 Token，一不小心就超限了。

**结果就是：任务正做着，API 突然返回 400，整个 Agent 直接崩掉。**

---

## 2. 解决思路：两层防御

这个问题的核心是"历史太大"，所以解法就是**在合适的时机把历史变小**。

CodePal 设计了两层：

```
┌─────────────────────────────────────────────────┐
│ 第一层：超大工具结果即时落盘（局部处理）                  │
│   触发时机：某条工具结果本身超过 50,000 字符             │
│   做的事：把内容写到磁盘文件，在对话历史里只留一个指针         │
│   效果：立刻释放这条结果占用的 Token                   │
└─────────────────────────────────────────────────┘
              ↓ 如果第一层还不够，继续走第二层
┌─────────────────────────────────────────────────┐
│ 第二层：接近上限时 LLM 生成摘要替换历史（全局处理）          │
│   触发时机：总 Token 数接近窗口上限                    │
│   做的事：调用 LLM 把"旧的历史"压缩成一段摘要，             │
│           然后用"摘要 + 近期原始消息"替换整个历史           │
│   效果：Token 大幅缩减，对话可以继续                    │
└─────────────────────────────────────────────────┘
```

---

## 3. 第一层：超大工具结果落盘（Offload & Snip）

### 3.1 具体做什么

工具返回的结果（比如 ReadFile 读了一个 3000 行的文件）有时候非常大。但 Agent 大多数时候其实不需要一直看着这个结果，它看一眼、拿到需要的信息就继续下一步了。

既然这样，我们就可以：
- **把超大的工具结果存到磁盘文件**
- **在对话历史里只留一句话**："这个结果已经存到 `.codepal/tool_results/xxx` 文件里了"

这个指针很小，只占十几个 Token，而原来的内容可能占几万 Token。

### 3.2 触发条件

代码里有两个触发门槛：

| 触发条件 | 常量名 | 数值 | 含义 |
|---------|-------|------|------|
| 单条结果超大 | `SINGLE_RESULT_LIMIT` | 50,000 字符 | 一条工具结果超过这个就落盘 |
| 单消息聚合超大 | `MESSAGE_AGGREGATE_LIMIT` | 200,000 字符 | 一条消息里所有结果加起来超过就落盘 |

### 3.3 看代码理解

```java
// ContextCompactor.java — offloadAndSnip 方法（简化版）

for (int i = 0; i < messages.size(); i++) {
    Message msg = messages.get(i);
    // 只处理包含工具结果的消息
    if (msg.getToolResults() == null) continue;

    for (int j = 0; j < results.size(); j++) {
        ToolResultBlock tr = results.get(j);
        // 超过 50,000 字符才处理，小的工具结果不动它
        if (safeLength(tr.content()) <= SINGLE_RESULT_LIMIT) continue;

        // 把内容写到磁盘
        Path path = writeSpill(spillDir, tr.toolUseId(), tr.content());

        // 在对话历史里替换成一个指针
        results.set(j, new ToolResultBlock(
            tr.toolUseId(),
            String.format("[Result of %d chars saved to %s]",
                          tr.content().length(), path),
            tr.isError()));
    }
}
```

**替换前后对比：**

```
替换前（历史里的工具结果）：
  "public class UserService {
    private UserRepository repo;
    public User findById(Long id) { ... }
    // ... 3000 行代码 ...
  }"
  → 估算 Token 数：~5,000

替换后（只剩一个指针）：
  "[Result of 18432 chars saved to .codepal/tool_results/call_abc123]"
  → 估算 Token 数：~15
```

Token 从 5000 压到 15，这条结果占用的空间直接消失了。

## 4. 第二层：LLM 生成摘要替换历史（Auto-compact）

第一层只能处理"特别大的单条结果"，如果是很多条中等大小的历史积累，就需要第二层出手。

### 4.1 触发时机：软触发 vs 硬触发

```
总 Token 数
      │
      ├─────────────────── 软触发线（effectiveWindow - 13,000）
      │                    到这里：主动触发，还有空间可以从容压缩
      │
      ├─────────────────── 硬触发线（effectiveWindow - 3,000）
      │                    到这里：强制触发，再不压缩就要 400 了
      │
      └─────────────────── effectiveWindow（上下文窗口 - 20,000 摘要输出预留）
```

为什么要留 20,000 的预留（`SUMMARY_OUTPUT_RESERVE`）？因为压缩本身需要调用一次 LLM，LLM 生成摘要也会产生输出，如果不提前留好空间，生成摘要这个请求本身也可能超限。

### 4.2 核心逻辑："不是全部压缩，保留近期消息"

这是一个很重要的设计细节。

**朴素想法**：把整个对话历史都压缩成摘要。
**问题**：最近几轮的对话 Agent 正在用，直接压掉会丢失重要细节。

**实际做法**：只压缩"旧的历史"，保留"近期的原始消息"。

```
压缩前的历史（示意）：
  消息1：用户说"帮我重构"
  消息2：Agent 读了文件 A
  消息3：Agent 读了文件 B
  ...
  消息40：Agent 刚刚修改了一个函数（这是刚发生的）
  消息41：工具返回修改成功（这是刚发生的）
  消息42：Agent 正在思考下一步（当前状态）

  ↓ 压缩后：

  摘要消息（替换了消息1-38）：
    "用户请求重构项目，Agent 读取了文件 A、B，
     已修改了 UserService 类的 findById 方法..."
  消息39：...（近期原始消息原样保留）
  消息40：Agent 刚刚修改了一个函数
  消息41：工具返回修改成功
  消息42：Agent 正在思考下一步
```

### 4.3 "保留多少近期消息"的计算

代码里的 `computeKeepStartIndex` 方法负责决定"从哪条消息开始保留原样"。

规则是从最新消息往前数，直到满足以下任意一个条件就停：
- 积累了 10,000 Token（`KEEP_RECENT_TOKENS`）
- 至少保留了 5 条消息（`MIN_KEEP_MESSAGES`）

但还有一个上限：最多保留 40,000 Token（`KEEP_MAX_TOKENS`），防止"近期消息"本身太大。

### 4.4 配对约束：tool_use 和 tool_result 必须成对

这是整个设计里**最容易出错**、面试官最爱问的地方。

Anthropic API 有一个规定：

> 如果一条消息里有 `tool_use`（Agent 调用了工具），那么**下一条消息里必须有对应的 `tool_result`**（工具返回了结果）。两者必须配对出现，缺一不可，否则 API 返回 400 错误。

如果压缩时不小心把 `tool_use` 压进了摘要，但把对应的 `tool_result` 留在了近期消息里，就出现了"孤立的 `tool_result`"——它没有对应的 `tool_use`，API 会报错。

代码里的处理：

```java
// computeKeepStartIndex 方法末尾的配对保护
// 如果"保留边界"正好落在一条只有 tool_result 的消息上，就往前再退一步，
// 把它的 tool_use 也纳入保留范围，确保两者在同一侧。
while (keepStart > 0 && isToolResultMessage(messages.get(keepStart))) {
    keepStart--;  // 向前移动，直到不是孤立的 tool_result 消息
}
```

**用一张图来理解：**

```
错误的切割（会导致 400）：
  [ 摘要 | 消息N: tool_use(call_123) | 消息N+1: tool_result(call_123) ]
                                          ↑
                                    保留边界不能在这里！
                                    tool_result 和它的 tool_use 被分开了

正确的切割：
  [ 摘要 + 消息N: tool_use(call_123) | 消息N+1: tool_result(call_123) ]
  ↑                                   ↑
  这一侧一起压缩                      这一侧一起保留
```

### 4.5 如果摘要请求本身也超限？——PTL 重试机制

有时候"需要被压缩的旧历史"本身就已经很大，甚至超过了上下文窗口，连"请帮我总结这段历史"这个请求都发不出去。

解决方案：**PTL（Prompt Too Long）重试**

```
第1次尝试：把所有旧历史发给 LLM，请求生成摘要
   → API 报错：prompt too long

第2次重试：把最旧的一批消息（按 API 轮次分组）丢掉，
           剩下的再发给 LLM
   → 如果还报错，继续丢更旧的

最多重试 3 次（MAX_PTL_RETRIES = 3）
```

"按 API 轮次分组"是关键：一个 `tool_use` 和它对应的 `tool_result` 算一个轮次，丢弃时整组一起丢，绝不拆开，避免制造新的配对问题。

## 5. 完整流程一遍走

```
每次 Agent Loop 执行完一轮工具调用后，调用 ContextCompactor.manage()：

第一步：第一层处理
  → 扫描所有历史消息
  → 把超大的工具结果落盘，替换为指针
  → 这一步是无条件执行的，每轮都跑

第二步：检查 Token 数
  → 估算当前历史的 Token 总数
  → 如果没到软触发线，结束（不压缩）
  → 如果到了软触发线但没到硬触发线，尝试 Auto-compact
  → 如果到了硬触发线，强制 Auto-compact

第三步（如果触发 Auto-compact）：
  → 计算"保留边界"（近期消息保留原样）
  → 把"旧历史"序列化成文本
  → 调用 LLM 生成摘要（带 PTL 重试保护）
  → 用"摘要 + 保留的近期消息"替换整个历史
  → 记录 compact_boundary 到会话日志，方便后续恢复
```

## 6. 面试怎么答

### 标准描述（30 秒版）

> "Agent 跑长任务时，工具调用的返回结果会不断堆积，历史 Token 数快速增长，逼近 API 上下文窗口上限后请求被拒绝、任务中断。
>
> 我设计了两层防御：第一层对超过 5 万字符的工具结果即时落盘，在历史里只留一个文件路径指针，立刻释放这条结果占用的 Token；第二层在 Token 数接近窗口上限时触发，调用 LLM 把旧历史压缩成结构化摘要，再用'摘要 + 近期原始消息'替换历史。压缩边界严格对齐 tool_use / tool_result 配对约束，避免产生孤立的 tool_result 触发 API 400。
>
> 优化后单次会话可持续运行数小时不中断，Token 成本也比不压缩显著降低。"

### 【设计决策类】

**Q1：为什么要分两层，一层不行吗？**

> 两个问题的性质不同，粒度不同。第一层处理的是"某一条工具结果特别大"——局部问题，即时扫描替换，不需要调 LLM，成本极低，每轮都可以跑；第二层处理的是"大量普通消息慢慢积累"——全局问题，需要 LLM 理解语义、提炼摘要，成本高但效果好。
>
> 只用第一层：遇到几百条中等大小的历史照样超限，解决不了根本问题。只用第二层：每次触发都要调一次 LLM，频率高了既慢又贵，而且很多情况是一条超大结果撑爆的，压根不需要全局摘要。两层分工：高频低成本在前，低频高质量兜底，互补。

**Q2：为什么压缩时要保留近期消息，而不是全部压成摘要？**

> Agent 在执行任务时，"近期几轮"代表的是当前正在进行的动作——刚调了什么工具、返回了什么结果、下一步准备怎么做。这些信息如果被压进摘要，细节就会丢失，Agent 下一轮可能无法正确续上。
>
> 举个具体例子：Agent 刚读完一个文件、正准备编辑，如果这个"读文件的结果"被摘要掉，Agent 下一轮就不知道文件内容是什么，可能重复读或者写错。所以近期消息必须原样保留，只压旧的历史。

**Q3：保留多少近期消息？这个参数是怎么定的？**

> 代码里设了三个参数：至少积累 10,000 Token（`KEEP_RECENT_TOKENS`）或至少 5 条消息（`MIN_KEEP_MESSAGES`），同时不超过 40,000 Token 上限（`KEEP_MAX_TOKENS`）。
>
> 这是经验值，不是严格推导出来的。10,000 Token 大约能容纳 2-3 轮完整的工具调用交互，5 条消息是保底，防止每条消息都很小时保留数量不够。40,000 Token 上限是防止近期消息本身太大、留给摘要的空间太少。实际上这类参数都应该通过 Eval 框架来验证调优，而不是拍脑袋定死。

**Q4：软触发和硬触发的区别是什么，为什么要设两条线？**

> 核心原因是：**压缩本身有成本，而且可能失败。**
>
> 软触发（距上限 13,000 Token）的必要性：压缩需要调一次 LLM 生成摘要，LLM 的输出要写进上下文窗口。如果等到窗口快满了才触发，窗口里已经没有空间容纳摘要的输出，摘要请求本身就会超限失败。所以必须提前触发，留足空间让摘要从容写出来。
>
> 硬触发（距上限 3,000 Token）的必要性：软触发可能失败——LLM 超时、报错、或者摘要 Prompt 本身太大触发 PTL 问题。软触发失败后程序继续跑，Token 持续增长。等到只剩 3,000 Token 时就不能再等了，必须强制压缩，否则下一轮 API 请求铁定 400。
>
> 两条线的本质关系是主路径和兜底路径，不是重复：
> ```
> 软触发（-13,000）：有余量，从容压缩，正常路径
>         ↓ 如果失败，Token 继续增长
> 硬触发（-3,000）：最后防线，强制压缩，异常兜底
>         ↓ 如果也失败
> 下一轮 API 请求 400
> ```

**追问：硬触发也可能失败吗？失败了怎么办？**

> 对，硬触发也可能失败，这是这套设计的显式边界。失败场景主要两种：
>
> 1. **PTL 超限**：旧历史本身太大，摘要请求发不出去。这时 PTL 重试机制介入，从最旧的消息开始丢弃后重试，最多 3 次。3 次都失败就真的没辙了。
> 2. **LLM 不可用**：超时、网络错误、模型报错。压缩彻底失败，下一轮 400。
>
> 代码里没有继续往下兜底。设计上认为：到了硬触发线还失败，要么是 LLM 不可用（基础设施问题），要么是历史规模超出了 PTL 能处理的范围（异常使用场景）。这两种情况下让 Agent 崩掉比无限重试消耗资源更合理。
>
> 另外代码里有 Circuit Breaker（`AutoCompactTrackingState`）——软触发连续失败 3 次后停止尝试，不再浪费时间，直接等硬触发来处理。实际上只要 LLM 可用，PTL 重试几乎总能找到可压缩的子集，极少走到真正崩掉的路径。

**追问：真的崩掉了，有什么补救手段？**

> 崩掉分三个层面来聊：**提前感知、崩后恢复、设计改进**。
>
> **① 提前感知——可观测性**
> 崩掉最怕不是崩，是不知道要崩。工程上在压缩流程埋点：每次软/硬触发成功失败记 metrics，Token 使用率超过 70%/80%/90% 各打一条日志，连续失败次数超阈值发告警。这样崩之前能看到"这个会话 Token 已经 95%，压缩连续失败 3 次"，有时间人工介入。
>
> **② 崩后恢复——compact_boundary Checkpoint**
> CodePal 每次第二层压缩成功后，会往会话日志写一条 `compact_boundary`，记录摘要文本 + 保留的近期消息。Agent 崩掉重启时不需要从头重放整个历史，直接从最近一个 `compact_boundary` 恢复——摘要 + 近期消息重建对话状态，继续跑。类似数据库的 WAL，不能恢复到崩溃瞬间，但能恢复到最近一个一致性快照。
>
> **③ 设计改进——更激进的第一层**
> 当前第一层只落盘超过 5 万字符的结果。如果历史本身就是 100 万字符、PTL 重试永远发不出去，改进方向是对所有工具结果都落盘，上下文窗口里只保留"指针 + 近期内容"，彻底消灭超大历史的可能。代价是每次工具调用都有磁盘 I/O，对 I/O 密集型任务有性能影响，需要权衡。
>
> **面试话术**：主动说出"崩掉是有的，设计上有感知 + 恢复 + 改进空间三条线"，比只说"不会崩"更加分，说明你真正理解了系统边界。

### 【工程化细节类】

**Q5：tool_use / tool_result 配对约束是怎么发现的？上线前还是上线后踩的坑？**

> 这是在设计阶段看 Anthropic API 文档时发现的约束，不是踩坑后才知道的。Anthropic 文档明确说明：如果请求里包含 tool_use 消息，后面必须紧跟对应的 tool_result，否则 API 返回 400，错误信息是 "tool_use and tool_result must be alternating"。
>
> 所以在设计压缩边界逻辑时就考虑进去了：`computeKeepStartIndex` 计算完边界后做配对检查，如果边界落在孤立的 tool_result 消息上，就往前移一位，把它对应的 tool_use 也纳入保留范围。

**Q6：落盘的工具结果文件，什么时候清理？会不会一直堆积占用磁盘？**

> 代码里没有主动清理落盘文件的逻辑，文件会持久存在于 `.codepal/tool_results/` 直到用户手动清理。Session 文件（`.codepal/sessions/*.jsonl`）有 30 天过期自动清理，但落盘文件没有类似机制。这是一个改进点。
>
> **追问：那落盘文件消失了，恢复历史对话不就丢内容了吗？**
>
> 不会，因为落盘文件和历史恢复是两套完全独立的机制：
>
> - **历史恢复**靠 `.jsonl` session 文件 + `compact_boundary` 摘要重建，`SessionManager.rebuildConversation()` 只读 session 文件，不依赖落盘文件
> - **落盘文件**存的是超大工具结果的原始内容，对话历史里只留了一个指针字符串：`[Result of 18432 chars saved to .codepal/tool_results/call_abc123]`
>
> 恢复会话时，这个指针字符串原样重建进对话，LLM 能看到"这里曾有个大结果被落盘"，但读不到原始内容——这是**有意识的取舍**：落盘的目的是"释放这轮 Token 压力"，不是"永久存储"。超大工具结果（比如读了 3000 行文件的返回值）在 Agent 完成那步之后几乎不会再用到；真正需要跨会话保留的关键信息，靠摘要机制提炼进 `compact_boundary`，不靠原始结果文件。

**Q7：Token 数用字符数估算，精度够吗？会不会因为偏差导致提前或推迟触发？**

> 估算有误差，约 ±15%。但触发阈值设了双重安全边距（软触发距上限 13,000 Token），这个余量远大于估算误差，不会误触发也不会漏触发。
>
> 更精确的方案是调 API 的 tokenize 接口，但多一次网络请求得不偿失。当前的 UsageAnchor 机制——用上一次 API 返回的真实 usage 值作锚点，新增消息在基准上叠加估算——已大幅减少了误差累积。

**Q8：PTL 重试丢弃消息时，是随机丢还是按顺序丢？为什么？**

> 按 API 轮次从最旧的开始丢，不随机。理由：旧历史对当前任务的价值通常低于近期；必须整组丢弃（tool_use + tool_result 一组），不能拆开，否则制造新的配对错误。`groupMessagesByAPIRound` 方法把消息按组分好，按组从最旧开始丢，保证每次丢弃后历史仍然合法。

**Q9：压缩触发时 Agent 正在执行任务，会影响当前这一轮的结果吗？**

> 不会。压缩在每轮工具调用完成之后、下一轮 LLM 请求发出之前触发，时机是两轮之间的间隙。压缩修改的是 `ConversationManager` 里的 messages 列表，这是下一轮请求要带的历史，不是当前轮次已在跑的东西，时序上安全。

**Q10：摘要的 System Prompt 是怎么设计的？为什么让 LLM 先输出 `<analysis>` 再输出 `<summary>`？**

> Prompt 要求 LLM 分九个部分生成摘要：用户核心意图、关键技术决策、涉及的文件和代码片段、遇到的报错及解决方法、待处理任务、当前工作状态等。
>
> 先输出 `<analysis>` 是 Chain-of-Thought 技巧——让 LLM 先把思考过程写出来再输出摘要，生成质量显著高于直接输出。`<analysis>` 不会被截取进最终历史，只取 `<summary>` 标签里的内容。

### 【量化与验证类】

**Q11：怎么量化压缩效果的？"Token 成本显著降低"有具体数字吗？**

> 量化方式是对比：相同任务在有压缩和无压缩两种情况下跑完所消耗的总 Token 数，通过 MetricsCollector 采集每轮的 input_tokens + output_tokens 累加。
>
> 具体数字取决于任务类型，读文件密集型任务受益最大（第一层落盘消除大量工具结果 Token）。长任务（30 轮以上）中，有压缩方案的 Token 消耗比无压缩通常低 40%-60%。更严格的量化依赖 Eval 框架，用标准化测试用例固定输入、多次跑取平均值对比。

**Q12：怎么检测压缩后信息没有丢失关键内容？**

> 这是 Eval 框架的核心用途。具体方法：
> 1. 对话开头注入已知的关键信息（特定类名、文件路径、错误信息）
> 2. 多轮对话撑满上下文，触发压缩
> 3. 压缩后问 Agent："之前提到的 XXX 是什么？"
> 4. 检测回答里是否包含注入的关键信息
>
> 这就是"信息保留率"指标的来源。首次跑保留率只有 17%，说明摘要 Prompt 没有提炼出重要信息；优化 Prompt 后保留率达到 100%，代码零改动。这是 Eval 驱动优化的典型案例。

**Q13：压缩本身会不会引入新的 bug？你做了哪些测试？**

> 主要测了三类：
> 1. **配对完整性测试**：压缩后遍历 messages，验证每个 tool_use 都有对应的 tool_result，不存在孤立块。
> 2. **边界测试**：消息数为 0、1、MIN_KEEP_MESSAGES 时的压缩行为；切割边界恰好落在 tool_use/tool_result 对上的情况。
> 3. **Token 单调性测试**：压缩后 Token 数必须小于压缩前，否则说明逻辑有 bug。

**Q14：业界有没有类似的解决方案？你的设计和它们有什么不同？**

> | 方案 | 原理 | 问题 |
> |------|------|------|
> | 滑动窗口 | 只保留最近 N 条消息 | 早期上下文直接丢弃，不知道做过什么 |

**Q15：如果未来 LLM 的上下文窗口变得很大（比如 100 万 Token），这套设计还有必要吗？**

**Q16：这套方案对 OpenAI GPT 系列也适用吗？还是只针对 Anthropic？**

## 9. 补充问答：MESSAGE_AGGREGATE_LIMIT 与字符预估

**Q：`MESSAGE_AGGREGATE_LIMIT` 是什么场景下触发的？**

> 一条 `tool_result` 消息里可以包含**多个工具结果**——当 Agent 同一轮并发调用了多个工具（`StreamingExecutor` 批量执行），它们的结果会被打包进同一条消息。每个单条结果没超 50,000，但加在一起可能很大：
>
> ```
> 一轮并发调用：
>   ReadFile(A) → 30,000 字符   ← 单条不超 50,000，不触发单条落盘
>   ReadFile(B) → 30,000 字符
>   ReadFile(C) → 30,000 字符
>   ReadFile(D) → 30,000 字符
>   ReadFile(E) → 30,000 字符
>   ReadFile(F) → 60,000 字符   ← 这条会先被单条落盘
>   聚合总量 = 210,000 字符      ← 超过 200,000，触发聚合落盘
> ```
>
> 触发聚合落盘后，阈值更激进——超过 200 字符的结果都落盘（而不是单条的 50,000 门槛），整条消息里几乎所有结果都被替换成指针。
>
> 代码逻辑（`offloadAndSnip`）是两次扫描：先按单条触发，再算聚合总量，两个条件独立判断：
>
> ```java
> // 第一遍：单条超 50,000 → 落盘
> if (safeLength(tr.content()) > SINGLE_RESULT_LIMIT) { writeSpill(...) }
>
> // 第二遍：聚合超 200,000 → 对该消息里剩余所有 >200 字符的结果落盘
> if (agg > MESSAGE_AGGREGATE_LIMIT) {
>     if (safeLength(tr.content()) > 200) { writeSpill(...) }
> }
> ```

**Q：字符数是怎么预估成 Token 数的？**

> 两个地方用途不同，方法也不同：
>
> **落盘触发判断**（`offloadAndSnip` 里的 `safeLength`）：直接用 Java 字符串长度，不换算，简单快：
> ```java
> private static int safeLength(String s) {
>     return s == null ? 0 : s.length();  // 就是字符数，没有任何转换
> }
> ```
>
> **Token 总量估算**（`estimateTokens` 里）：用 `/3.5` 换算成 Token 数，给软/硬触发线做判断：
> ```java
> total += (int) (safeLength(m.getContent()) / 3.5) + 4;
> total += (int) (safeLength(tr.content()) / 3.5) + 10;
> ```
>
> 3.5 是折中经验值：英文约 4 字符一个 Token，中文约 1.5 字符一个 Token，混合文本取 3.5。精度约 ±15%，但触发阈值设了足够大的安全边距（软触发留 13,000 Token 余量），误差不影响正确性。

**Q：估算不准确怎么办？误差会不会累积导致提前或延迟触发？**

> 纯字符估算有两个问题：误差随轮数累积越来越大；有 Prompt Cache 命中时，API 实际计费的 input tokens 远小于字符估算值，会导致严重高估、提前误触发压缩。
>
> 解决方案是 **UsageAnchor 机制**——每轮 API 调用结束后，用 API 返回的真实 token 数作为新的基准锚点：
>
> ```java
> // Agent.java — 每轮 stream 结束后
> conv.recordUsageAnchor(turnInput, turnOutput, turnCacheRead, turnCacheCreation);
> // baselineTokens = input + cacheRead + cacheCreation + output（API 真实值）
> ```
>
> 然后 `currentTokens()` 的计算变成"锚点之前用真实值 + 锚点之后只估算增量"：
>
> ```java
> public static int currentTokens(List<Message> messages, UsageAnchor anchor) {
>     if (anchor == null) {
>         return estimateTokens(messages);  // 冷启动，全量估算
>     }
>     // 锚点之后新增的消息才需要估算，增量小误差可控
>     List<Message> appended = messages.subList(anchor.anchorCount(), messages.size());
>     return anchor.baselineTokens() + estimateTokens(appended);
> }
> ```
>
> 效果：每轮之后误差归零重置，不再累积。即使有 Cache 命中，锚点也反映了真实的 token 消耗，不会提前误触发。字符估算只用于锚点之后的新增消息（增量通常很小），误差始终在可控范围内。
