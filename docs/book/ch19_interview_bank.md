## 19.0 面试官的三层提问逻辑（先理解套路）

大厂 AI Agent 岗的面试，几乎都遵循这个由浅入深的漏斗：

```
第一层：概念题（筛掉背不出定义的人）
  "什么是 Agent / Function Calling / RAG / MCP？"
        │  能答上来 → 进入第二层
        ▼
第二层：实现题（筛掉只会调库、不懂原理的人）
  "你的 Agent Loop 具体怎么转？工具并发怎么保证安全？"
        │  能讲清 → 进入第三层
        ▼
第三层：工程/权衡题（筛选真正做过生产的人 —— 这层拉开差距）
  "上线出故障怎么排查？成本怎么控？为什么不用 X 方案？"
```

**关键认知**：概念题和实现题网上背背就能过，真正决定 offer 等级的是**第三层**——工程化能力和技术判断力。CodePal 的价值就在于给你提供了第三层的"真实弹药"：你不是背概念，是真的踩过坑、做过取舍。

**高频对比题——Function Calling vs RAG**（字节真题，必背）：
> Function Calling 是"让模型主动决定去拿什么"（模型输出 tool_use，Agent 执行工具，结果回传）；RAG 是"我们提前替模型检索好，塞进 prompt"。Function Calling 更灵活（模型可多轮、可组合工具），RAG 更简单可控（一次检索一次生成）。Code Agent 用 Function Calling 驱动的实时检索（grep/read），因为代码是结构化的、随时在变，向量索引会过期。

> 上下文管理的本质是"token 预算分配"。我们做了两层压缩：Layer 1 把大的工具结果即时落盘（只在历史里留一个引用），Layer 2 在接近窗口上限时用 LLM 生成结构化摘要。最关键的两个工程点：一是压缩边界要对齐 Function Calling 的 tool_use/tool_result 配对，不能切一半（否则 API 400）；二是压缩摘要的质量靠评测保证——我们做了信息保留率测试，把摘要 prompt 从"总结对话"改成结构化的 9 章要求，保留率从 17% 提到 100%。

**必背的差异化答法——Code Agent 为什么不用 RAG**（这题能体现你有独立判断，而不是无脑上 RAG）：
> 三个原因：①代码是结构化的，grep/AST 精确命中比向量相似度更准，"找 `foo()` 的定义"用向量检索反而不如 `grep`；②代码一直在改，向量索引会过期，维护成本高；③理解代码需要"顺藤摸瓜"式的链式读取（看到 import 再去读那个文件），RAG 的"一次检索"做不到这种多跳。所以 Code Agent 用工具驱动的实时检索（ReadFile + Grep + Glob）——本质也是"检索+生成"，只是检索用工具调用而非向量搜索。

> ⚠️ 注意：**别把"不用 RAG"说成"RAG 不好"**。要说清是"这个场景不适合"，换成企业知识库问答、客服，RAG 仍是首选。面试官考的是你能不能分场景取舍。

**答题主线**：
> MCP 是"给 Agent 接工具的标准协议"，类比 USB——不用为每个工具写专门的适配代码，遵循 MCP 的 Server 都能即插即用。它和 Function Calling 是两个层次：Function Calling 是 LLM 层的协议（模型怎么表达"我要调工具"），MCP 是应用层的协议（工具怎么被发现、描述、调用）。MCP 除了 Tools，还提供 Resources（数据）、Prompts（模板）。安全上，因为 MCP Server 可能是第三方的，存在"工具投毒"（描述里藏恶意指令）风险，所以我们的权限系统做最后兜底——无论工具来自哪，危险操作都要过五层权限。

**能拿分的答法**：
> 评测 Agent 比评测 LLM 难，因为是端到端的多步任务，中间任何一步错都会失败。我们的 EvalCase 定义 prompt + 四种验证（文件存在检查、关键词检查、Bash 命令验证、组合）；EvalRunner 跑独立 Agent 实例，消费事件队列，验证后汇总。关于 benchmark 污染：原版 SWE-bench 很多题在训练数据里，frontier 模型能"背答案"，所以我们用 SWE-bench-Live（每月新题），2026 年的题不在任何训练集里，结果更可信。防作弊上，验证不能只查关键词（模型可能 `echo` 骗过），要查真实产物（文件是否真的被正确修改、测试是否真的通过）。

## 19.11 可观测性与成本

| 问题 | 考察点 | 备注 |
|------|--------|------|
| Trace 和 Span 怎么设计？Agent 可观测性怎么做？ | 分布式追踪 | 🎯 第8章 TraceStore |
| 可观测性的三大支柱是什么？ | Metrics/Trace/Log | 🎯 第8章 |
| Agent 系统的日志、监控、告警怎么设计？ | 生产运维 | |
| 怎么监控生产环境的 LLM？ | 成功率、延迟、成本 | 🎯 第8章 MetricsCollector |
| LLM API 成本怎么优化？ | 缓存、路由、压缩 | 字节真题 🎯 |
| 模型路由（Model Routing）怎么做？ | 简单任务用小模型 | |

**答题主线**：
> 可观测性三支柱：Metrics（聚合指标，如工具调用成功率、P99 延迟、每轮 token）、Trace（单次请求的完整链路，我们用 TurnTrace 记录每轮的每个 ToolSpan）、Log（原始日志）。我们的 MetricsCollector 用 AtomicLong + ConcurrentHashMap 做并发安全统计（多个工具并发执行时同时写）。这些数据不是摆设——它直接支撑了两个优化决策：一是靠"每轮 token 消耗"曲线确定压缩阈值，二是靠"工具执行延迟分布"调工具超时参数。成本优化三板斧：Prompt Cache（稳定前缀命中 10% 计费）、上下文压缩（减少每轮 input token）、模型路由（简单任务用便宜模型）。

## 19.12 工程化与生产问题（第三层，拉开差距的地方）

| 问题 | 考察点 | 备注 |
|------|--------|------|
| API 限流/失败怎么处理？ | 重试、指数退避、幂等 | 🎯 第4章 rate limit 自愈 |
| Agent 延迟怎么优化？（流式/缓存/批处理） | 首字延迟、并发 | 🎯 第2章流式 + 第3章并发 |
| 高并发下 Agent 系统怎么扩展？ | 无状态化、水平扩展 | |
| Agent 的灾难恢复和高可用怎么设计？ | 状态持久化、故障转移 | |
| 怎么做灰度发布和 A/B 测试？ | 渐进发布 | |
| Prompt Drift 怎么管理（避免退化）？ | 版本 + 评测 | 🎯 第8章评测 |
| 什么是 12-Factor Agents？ | 生产级 Agent 准则 | |
| 为什么有时要"手写" Agent 而不用框架？ | 可控性 vs 开发速度 | 🎯 CodePal 就是手写的 |
| 你的 Agent 上线出故障，怎么系统排查？ | 排障方法论 | 🎯 第8章 Trace 定位 |

**排障方法论标准答法**（系统设计题常见收尾）：
> 分三步定位：①先看 Metrics——是所有请求都挂还是部分？成功率、延迟哪个异常？②锁定异常请求，看它的 Trace——是 LLM 调用失败、还是某个工具超时、还是压缩后上下文丢了关键信息？③根据 Trace 定位到具体环节：如果是 API 429（限流）→ 检查退避重试是否生效；如果是工具超时 → 看是不是某个 Bash 命令卡死（我们有 600s 超时保护）；如果是模型行为异常 → 大概率是 prompt 问题，用评测复现。关键是**有 Trace 才能定位**，没有可观测性就只能靠猜。

**"为什么手写 Agent 而不用 LangChain"**（CodePal 的立身之本，必有观点）：
> 框架适合快速验证想法，但生产级 Agent 我倾向于手写核心 Loop。原因：①Agent Loop 的每个决策点（何时压缩、怎么分批、错误怎么恢复）都需要精细控制，框架的抽象往往挡在中间，出问题难调试；②框架封装的"魔法"在遇到边界情况（tool_use/tool_result 配对、上下文压缩边界）时反而是负担；③Harness Engineering 的核心是"每次犯错就工程化一个永久修复"，这要求你能改到最底层。CodePal 就是完全手写的，14 步 Loop、两层压缩、五层权限，每一层我都能讲清为什么这么设计——这是用框架给不了的深度。

## 19.13 系统设计题

大厂 AI 岗越来越爱出系统设计题，常见的有：

1. **设计一个支持多轮对话 + 工具调用的 Agent 系统**（最基础，直接讲 CodePal 架构）
2. **设计一个能读代码并给改进建议的 Agent**（对标 CodePal 本身！）
3. **设计一个带引用追踪的文档 Q&A 系统**（RAG + 引用约束）
4. **设计一个多 Agent 协作产出研究报告的系统**（多 Agent + 任务分解）
5. **设计一个分层 Agent 架构（Orchestrator/Worker）**（对标 Lead-Teammate）
6. **智能客服 Agent 生产系统**（工单分析 + 自动回复 + 升级）

**系统设计题的答题框架**（套路化，任何题都能用）：
```
1. 澄清需求（1分钟）：规模？延迟要求？成本预算？要多准确？
2. 画整体架构：入口 → Agent Loop → 工具层 → LLM 层 → 存储层
3. 讲核心 Loop：调 LLM → 判断工具 → 执行 → 回填 → 终止条件
4. 讲三个难点（挑你熟的深入）：
   - 上下文管理（压缩策略）
   - 工具调度（并发安全）
   - 安全（权限/沙箱）
5. 讲生产加固：限流重试、可观测性、评测、成本控制
6. 讲取舍：为什么这么选，什么场景要改设计
```

**关键**：把系统设计题往你的 CodePal 强项上引。面试官问"设计 code agent"，你直接说"我正好做过一个"，然后按上面框架讲，深度立刻碾压。

## 19.14 场景/开放题（考技术判断力）

| 问题 | 怎么答 |
|------|--------|
| 微调 vs RAG vs Prompt，怎么选型？ | 按"知识多久变一次 + 要不要改行为"分：静态知识+改行为→微调；动态知识→RAG；只是格式/风格→prompt |
| Cursor / Claude Code / Windsurf 对比？ | 从"上下文获取方式"（索引 vs 实时检索）、"自主程度"、"权限模型"三个维度谈 |
| Harness 和 Context Engineering 哪个更重要？ | 不是谁更重要，是分工：Harness 决定可靠性上限，Context 决定效果上限，缺一不可（第17章） |
| 基模越来越强，你做的这些工程还有用吗？ | 有用。窗口再大也有 lost in the middle；模型再聪明也需要工具、权限、可观测性。工程是"把不确定的模型变成可信赖的产品"的那一层 |
| 最近让你眼前一亮的 AI 进展/论文？ | 提前准备 1-2 个（如 Anthropic 的 context engineering、MCP 生态、某个 Agent benchmark），体现你在持续跟进 |

## 19.15 五条高频真实追问链（面试官的深挖套路）

面试官很少问完一题就换，而是顺着你的答案一层层追。提前演练这五条链，被追问时不慌。

### 追问链 A：从"什么是 Agent"追到系统设计（10 层）

```
1. 什么是 Agent？和普通 LLM 调用有什么区别？
2. → Agent 的核心组件是什么？
3. → Agent Loop 具体怎么转？
4. → 循环什么时候停？（终止条件）
5. → 如果模型反复调同一个工具、死循环了怎么办？
6. → 工具调用失败了怎么自愈？
7. → 上下文快超窗口了怎么处理？
8. → 如果是多 Agent，主子怎么通信、怎么分任务？
9. → 生产上并发几百路，成本和延迟怎么控？
10. → 现在从零设计这个系统，画架构。
```
👉 CodePal 能覆盖全链：1-2 第1章，3-7 第4章，8 第15章，9 第2/8章，10 第18章系统设计框架。

### 追问链 B：RAG 深挖

```
RAG 是什么？→ 为什么不用微调？→ 文档怎么分块？→ 分块语义丢失怎么办？
→ Embedding 模型怎么选？→ 向量召回不准怎么办（混合检索+rerank）
→ 检索到了还幻觉怎么办？→ 怎么量化 RAG 效果？→ 知识库天天变怎么更新？
→ 那 code agent 为什么不用 RAG 用 grep？
```
👉 最后一环是你的差异化答案（19.5）。前面几环要能答上概念（你不做 RAG 不代表不懂 RAG）。

### 追问链 C：Function Calling / MCP

```
Function Calling 原理？→ 模型怎么学会调工具的？→ 多个工具并行调用有什么坑（并发安全/读写顺序）？
→ 调用失败/超时怎么处理？→ 工具太多（几百个）token 撑爆怎么办（ToolSearch/延迟加载）？
→ MCP 和 Function Calling 区别？→ MCP 有哪些安全风险（工具投毒/间接注入）？
→ 怎么做权限隔离和沙箱？
```
👉 全链都是 CodePal 强项：并发安全（第3章）、ToolSearch（第7章）、MCP（第7章）、权限沙箱（第6章）。

### 追问链 D：上下文/记忆

```
上下文窗口满了怎么办？→ 怎么压缩（丢什么、留什么）？→ 压缩后信息丢失怎么评估（信息保留率）？
→ 短期 vs 长期记忆怎么存？→ 长期记忆用什么介质？→ 过时记忆怎么淘汰更新？
→ lost in the middle 怎么缓解？
```
👉 全链 CodePal 覆盖：两层压缩（第8章）、信息保留率（第8章）、记忆系统（第9章）、recency bias（第5章）。

### 追问链 E：生产稳定性

```
你的 Agent 上线后出故障，怎么排查？→ 有没有 trace/metrics？→ 怎么定位是模型问题还是工具问题？
→ API 限流/超时怎么处理（重试/幂等/退避）？→ 成本怎么控（模型路由/缓存/prompt cache）？
→ 怎么灰度发布和防止 prompt 退化？
```
👉 排障靠 Trace（第8章），限流自愈（第4章），成本三板斧（19.11），prompt 退化靠评测（第8章）。
