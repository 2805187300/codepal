# CodePal 项目面试题汇编

---

## Q1：Agent Loop 整体流程是怎样的？

每一轮进来先检查上下文长度，超阈值就触发压缩，保证不会因为历史太长让下一次 API 调用爆掉。然后把 system prompt、工具列表、对话历史、环境信息、项目指令、长期记忆打包发给 LLM，开始流式接收，边收边把事件推给 UI 渲染。

流结束后判断模型是不是要调工具：
- 不调就把回复落进历史，Loop 结束
- 要调就把模型回复连同工具调用一起落历史，按并发安全性分批，每个工具过权限检查、执行、结果落历史，然后进入下一轮

中间穿插着各种 hook，轮次开始、发送前、调用前后、轮次结束都有，方便外部扩展。Multi-Agent 场景下还会在轮次开头检查消息队列，把队友发来的消息拼进历史。

## Q2：工具并行执行你怎么设计的？怎么判断哪些工具可以并行？

**考点：并发安全性设计**

每个工具自己声明能不能并发。判断标准：

- **只读类**（不修改任何外部状态）：可并发，比如 ReadFile、Glob、Grep
- **写类**（会修改文件、执行命令、影响外部状态）：不可并发，比如 WriteFile、EditFile、Bash
- **spawn 子 Agent 类**：不可并发，因为 spawn 本身有副作用，要创建 worktree、注册任务、加入 team 消息通道等共享状态，几个 spawn 同时跑会竞争；但 spawn 完之后子 Agent 自己在后台并行跑，主 Agent 不阻塞，所以并发能力是通过 background 模式实现的，不是工具级并发

分批算法是**相邻同性质合并**：遍历模型返回的工具调用列表，连续的并发安全工具合并到同一个并发批次，碰到非并发安全工具就开一个新的串行批次。这样既保留了模型给出的执行顺序，又最大化了并发。

**追问：两个 ReadFile 读同一个文件，并发会有问题吗？**

单次 ReadFile 是只读 IO，并发没问题。如果模型在一轮里既 ReadFile 又 WriteFile 同一个文件，分批后 ReadFile 在并发批次跑、WriteFile 在串行批次跑，顺序由模型给出的顺序保证，读后写不会冲突。

**追问：并发工具之间会不会看见对方的中间状态？**

不会。并发批次内部全是只读类工具，按定义不修改外部状态。读和写之间靠分批保证顺序：不管模型返回多复杂的读写序列，分批算法都是按顺序遇到写就切一刀，保证写前的读先跑完、写后的读能看到写的结果。

**追问：并发批次里如果有一个工具特别慢，会不会拖垮整批？**

批次内并发等所有任务完成，最慢的工具决定批次耗时。优化空间在两处：一是给每个工具配独立超时（ReadFile 10 秒、Bash 5 分钟），超时直接返回错误结果；二是让慢工具支持流式产出中间状态，UI 上能看到进度。

## Q3：Plan Mode 是什么？为什么要专门搞这个模式？

**考点：是否理解复杂任务需要规划先行，以及如何在工程上实现先规划再执行的流程**

Plan Mode 就是先出方案再动手。输入 `/plan` 进入这个模式后，Agent 一般会分几步走：先派子 Agent 去读代码理解现状，然后设计实现方案，最后把完整计划写到一个 plan 文件里交给用户审批，整个过程中权限被锁定为只读，不允许修改任何文件。用户确认方案后再退出 Plan Mode 进入执行。

紧跟着的是上下文预算管理。Agent 一个任务可能跑几十轮，每轮的工具调用和结果都往对话历史里堆，不主动管理很快撑到上下文窗口上限。我做了两层防御：大结果即时落盘只留引用、接近上限时调 LLM 生成摘要替换历史。用户还可以手动 `/compact` 主动触发。每层都有边界情况，比如落盘截断点怎么选、摘要质量怎么保证、压缩边界要对齐 Function Calling 协议约束。

## Q4：你的 Skill 系统是怎么设计的？Skill、MCP、Function Calling 三者是什么关系？

**考点：扩展机制的层次理解**

Skill 是行为层面的扩展。每个 Skill 是一个 markdown 文件，frontmatter 声明名字、描述、允许用的工具列表、执行模式，正文是一段 prompt 模板，支持占位符接收参数。

三个来源按优先级：项目级放 `.codepal/skills` 目录，用户级放 home 目录，内置的打包在代码里。同名 Skill 项目级优先覆盖。

两种执行模式：
- **inline 模式**：把 Skill 的 prompt 注入当前会话，Agent 带着额外指令继续跑
- **fork 模式**：开一个独立子 Agent，有自己的对话历史和过滤过的工具集，跑完把结果返回主 Agent

支持热加载，每次调用时重新读源文件，改完不用重启。

**三者关系：**
- Function Calling 是底层协议，模型输出工具调用请求，Agent 执行后把结果回传，所有工具调用都走这条路
- MCP 扩展的是工具集，解决 Agent 能做什么，MCP Server 提供远程工具，包装成普通工具注册进字典
- Skill 扩展的是行为模式，解决 Agent 该怎么做，本质是 prompt 配置加工具过滤，不提供新工具能力，而是约束和引导 Agent 在特定任务上的思路和可用工具范围

类比：Function Calling 是嘴和手的连接方式，MCP 是往工具箱里加工具，Skill 是给 Agent 一份作业指导书。

**追问：Skill 跟直接写 system prompt 有什么区别？**

system prompt 是全局固定的，对所有任务生效。Skill 是按需激活的，用户触发某个 Skill 时才加载进来，任务结束可以卸掉。区别在于粒度和生命周期：system prompt 定义 Agent 的基础人格和通用规则，Skill 定义特定任务的指令和工具约束，两者叠加。把所有 Skill 内容塞进 system prompt，一是太长浪费 token，二是不同任务的指令互相干扰，三是用户没法按需组合。

## Q5：你的评测体系是怎么设计的？

**考点：量化评估 Agent 能力，数据驱动优化**

评测最关键的一点是控制变量。让 CodePal 和 Claude Code 接同一个模型跑同一批任务，差异就完全来自框架本身。简单的单文件 bug 两边通过率都在七八成，差距不大。中等难度的有一个涉及十几个文件的 bug，CodePal 花了大概一小时自己一步步追调用链最终定位到了根因，跟官方 PR 修法一致。整体下来 CodePal 大概四成多，Claude Code 大概六成，差距主要在复杂任务上。

除了修 bug 的能力，我还专门测了上下文管理。设计了一个**上下文信息保留测试**：在对话开头告诉 Agent 几个关键信息，然后连续发多轮任务撑满上下文触发压缩，最后看它还记不记得。CodePal 第一次跑只记住了六分之一，Claude Code 全记住了。排查发现是压缩摘要的 prompt 没写好，改了一版 prompt 就从六分之一提到了全部记住，代码一行没动。评测不光是给个分数，更重要的是通过评测暴露问题然后指导优化。

**追问：为什么用 SWE-bench-Live 而不是原版 SWE-bench？**

原版 SWE-bench 的数据污染问题已经很严重了，OpenAI 内审发现超过 60% 的任务有缺陷，frontier 模型能根据任务 ID 直接复现答案，OpenAI 已经停止报告 SWE-bench Verified 的分数了。SWE-bench-Live 是微软后来推出的，每月收录最新的 GitHub issue，2026 年的题不在任何模型的训练数据里，评测结果更可信。

## Q6：你这个项目有用到 RAG 吗？

**考点：理解 RAG 和工具驱动检索的差异，能否解释技术选型背后的取舍**

没有用 RAG。不是不知道 RAG，而是 Code Agent 场景下工具驱动的检索比向量检索更合适。

理由：
1. **代码是结构化的**。import 关系、函数调用链、类型定义，这些靠 grep 一搜就精确命中。向量相似度是语义匹配，搜调用方可能给你一堆名字像但毫无关系的函数，精度不够
2. **代码一直在改**。RAG 的向量索引建完就是静态的，代码一改索引就过期了，要不停重建。Agent 直接读文件系统，永远拿到的是最新状态
3. **理解代码需要顺藤摸瓜**。Agent 读一个文件，发现它引用了另一个模块，跟过去再读，一步步追下去。RAG 是一次性检索 top-k 片段，做不到这种链式跟踪

CodePal 的做法是让 Agent 自己用工具实时检索：ReadFile 读文件、Grep 搜关键词、Glob 找文件、Bash 跑命令，本质上也是「检索加生成」，只是检索环节从向量搜索换成了工具调用，更精确也更灵活。

**追问：有没有场景是 RAG 比工具检索更合适的？**

有。如果要检索的不是代码而是大量非结构化文档，比如几千篇技术博客或者产品文档，grep 搜不动语义，这时候 RAG 的语义检索就有优势了。技术选型不是哪个更先进就用哪个，是看场景适不适合。

## Q7：你用的是什么 AI 编程工具？用的哪个模型？

**考点：AI 工具链的选型判断力**

目前 Coding Agent 里最强的两个是 Claude Code 和 Codex，算是这个领域的标杆，我两个都用。做 CodePal 的时候主力是 Claude Code，模型用 Opus 4，大量的跨文件重构、架构调整都是在里面完成的。它跑在终端里，1M token 的上下文窗口，复杂任务可以跑几十轮工具调用不断档。同样一个重构任务，Cursor Agent 花了 188K tokens 还没搞定，Claude Code 33K tokens 就完成了，成本差了将近六倍。

## Q8：具体描述一下你对 Harness 工程的理解，它与 Context 工程/Prompt 工程的区别

**考点：对三代 AI 工程方法论演进的深度理解**

这三个概念是包含关系，不是并列的：

- **Prompt Engineering**：管「怎么跟模型说话」，把指令写清楚、写结构化，但只作用于单轮对话
- **Context Engineering**：往外扩一圈，管「给模型什么信息」，通过 RAG、检索、token 排序把正确的知识塞进上下文窗口，但有个盲区：信息给够了，模型可能拿着信息干危险的事，Context 层没有任何机制拦它
- **Harness Engineering**：再往外扩一圈，管「整个系统怎么运转」，在模型外围建确定性的约束、反馈和验证，让 Agent 跨多个 context window 都能稳定工作

所以是 Prompt 在 Context 里面，Context 在 Harness 里面。

类比：Prompt 是油门指令，Context 是燃油，Harness 是整辆车。光踩油门加燃油，没有方向盘和刹车，车是要出事的。

做 CodePal 的时候体感很明显：花时间调 prompt 的措辞，效果改善有限。真正让 Agent 可靠性产生质变的，是加权限拦截、加错误信息回传、加工具输入校验这些 Harness 层的东西。Mitchell Hashimoto 说过一句话：「每次 Agent 犯错就工程化一个永久修复」，这抓住了本质。换模型提升天花板，搭 Harness 提升落地能力。
