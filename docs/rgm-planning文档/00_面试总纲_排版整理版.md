# 面试总纲：把 4 条技术点串成一个完整故事

**RGM 促销规划系统 | 多租户 SaaS**

**项目概述：** 面向快消品牌的促销规划平台，支持促销活动及销量、收入与 Spend 模拟。基于 Java 17、Spring Boot、SAP CAP、HANA、Kafka 和 Redis，参与 Spend 模拟、异步任务分解及多租户后台任务的性能与稳定性优化。

**核心工作：**

1. **查询与计算优化：** 针对数百 SKU 场景下的 N+1 查询和 O(N×M) 线性匹配问题，参与批量 IN 查询和 HashMap 索引优化，将匹配复杂度降至 O(N+M)，典型规模下可避免最高约 1.12 亿次 UUID 比较。

2. **异步异常治理：** 针对促销数据拆分为 SKU、日期和 UOM 子任务并行计算时，部分失败无法被父任务感知的问题，参与改造 CompletableFuture 异常处理，引入显式 ERROR 结果并补充异常场景测试，使失败可统计、可定位。

3. **线程池背压：** 针对促销分析任务突发提交、下游处理能力有限导致的内存积压问题，参与实现 5 worker + 100 容量队列的有界线程池，通过阻塞式拒绝策略形成背压，并补充饱和、中断及关停测试，限制 JVM 内任务积压。

4. **分布式租约：** 针对多 Pod 重复执行租户任务及长任务超过锁租期的问题，基于 Redisson 分布式锁实现多实例互斥，自实现 Watchdog 线程每 3 分钟续期（2秒抢锁、9分钟租期），结合 5 worker 并发处理，实现长任务续租。

## 二、业务链路串联（4 条亮点不是孤立的，是一条流水线）

```
【实时链路：KAM 点"模拟"触发】
─────────────────────────────────────────────────────────
KAM 在页面上调整大促参数，点"模拟"
  → Kafka 消息触发后端计算
        ↓
┌─────────────────────────────────────────────────────┐
│ 亮点①  查询与计算优化                                │
│                                                     │
│ 问题：                                               │
│   300 个 SKU，每个单独查 KPI 明细                    │
│   → N+1 查询，300 次网络往返，~600ms 白白浪费         │
│   → 批量查回来后 O(N×M) 双重循环匹配，1.12亿次比较    │
│   → 过滤条件未下推，传输 87% 无用数据                 │
│                                                     │
│ 优化：                                               │
│   一次 IN 批量查询取代 300 次单条查询                 │
│   预建 HashMap 索引，O(N×M) → O(N+M)                │
│   UOM_TYPE 过滤下推到 HANA 列存引擎，数据量减少 87%   │
└─────────────────────────────────────────────────────┘
        ↓  查到的 KPI 明细（300 SKU × 多 UOM）
┌─────────────────────────────────────────────────────┐
│ 亮点②  异步异常治理                                  │
│                                                     │
│ 问题：                                               │
│   300 SKU × 多 UOM × 多日期 = 数百个子任务并行计算   │
│   某子任务失败 → exceptionally { return null }       │
│   → 静默吞掉，父任务 filter(nonNull) 跳过            │
│   → Spend 汇总少了几个 SKU，数据错了但没有报错（脏数据）│
│                                                     │
│ 优化：                                               │
│   引入显式 ERROR 结果对象（携带 status + errorMsg）   │
│   失败返回 ERROR 状态而非 null                        │
│   父任务统计 ERROR 数，失败可感知、可定位、可统计      │
└─────────────────────────────────────────────────────┘
        ↓  子任务提交到线程池
┌─────────────────────────────────────────────────────┐
│ 亮点③  线程池背压                                    │
│                                                     │
│ 问题：                                               │
│   用无界队列（LinkedBlockingQueue），高并发下任务无限  │
│   积压在 JVM 堆内存 → OOM 崩溃                       │
│   CallerRunsPolicy 占用 Kafka Listener 线程          │
│   → 停止消费 → Kafka 触发 rebalance                  │
│                                                     │
│ 优化：                                               │
│   换有界队列 ArrayBlockingQueue(100)                 │
│   自定义阻塞式拒绝策略：queue.put() 队满阻塞生产者    │
│   不占 Listener 线程，不丢任务，内存积压有上界        │
└─────────────────────────────────────────────────────┘
        ↓  返回 KAM 模拟结果（Spend / Volume / Revenue）
─────────────────────────────────────────────────────────
【后台链路：cron 每 6 分钟触发（独立于实时链路）】
─────────────────────────────────────────────────────────
        ↓
┌─────────────────────────────────────────────────────┐
│ 亮点④  分布式锁 + Watchdog                           │
│                                                     │
│ 问题一：3 个 Pod 同时触发定时任务                     │
│   → 重复执行，数据竞争                               │
│                                                     │
│ 问题二：几十个租户处理完需要几十分钟                  │
│   锁租期 9 分钟，任务跑一半锁就过期                   │
│   → 其他 Pod 抢入，又重复了                           │
│                                                     │
│ 优化：                                               │
│   Redisson tryLock（等2s / 租期9min）                │
│   → 只有抢到锁的 Pod 执行，其他直接跳过              │
│   ScheduledExecutorService 每 3 分钟续期（重置TTL）  │
│   → 任务在跑：锁一直有效                             │
│   → Pod 宕机：Watchdog 也死，9分钟内锁自动过期        │
│   5 worker 并发处理所有租户，缩短总执行时间           │
└─────────────────────────────────────────────────────┘
        ↓  把基线数据（base_vol / price_elasticity 等）
           同步到 Redis 缓存，供亮点①的实时链路使用
```

**两条链路的定位：**

```
实时链路（亮点①②③）：
  KAM 点模拟 → 几秒内返回结果
  优化目标：响应快、结果准、内存稳
后台链路（亮点④）：
  cron 每 6 分钟 → 刷新所有租户基线数据到 Redis
  优化目标：多实例不重复执行、长任务锁不提前失效
```

**两条链路的数据交叉点：**

```
后台链路（亮点④）预热到 Redis 的：
  base_vol、price_elasticity 等历史统计值（变化慢，适合缓存）
实时链路（亮点①）实时查询的：
  这场大促 300 个 SKU 的 KPI 明细（每次促销组合不同，无法全量缓存）
计算时两份数据合并：
  KPI 明细（实时查）+ 基线数据（从 Redis 取）→ 计算 Spend
```

**能把这条链路讲出来 = 面试官相信你真的在这个项目里待过、理解全局。**

## 五、高频追问速查（被问到不慌）

| 追问 | 快速答 |
|------|--------|
| CompletableFuture 和 Future 区别 | Future 只能阻塞 get；CompletableFuture 支持链式回调、组合(allOf)、异常处理(exceptionally) |
| exceptionally vs handle | exceptionally 只处理异常；handle 成功失败都触发，能同时拿结果和异常 |
| 为什么不用 CallerRunsPolicy | 会占用 Kafka Listener 线程导致消费停滞/rebalance |
| put vs offer | put 满了阻塞等待；offer 满了立刻返回 false |
| Redisson 自带看门狗为啥还手写 | 自带看门狗只在不指定租期时生效，这里显式指定租期(540s)就不启动了 |
| 为什么用 AtomicBoolean | 跨线程可见性（主线程写、续期线程读），普通 boolean 有可见性问题 |
| N+1 为什么慢 | 慢在网络往返次数，不是 DB 计算 |
| 谓词下推为什么快 | 源头减少数据传输量 + 列式库过滤快 + 让引擎做擅长的事 |
| HashMap 会退化 O(n) 吗 | 极端哈希冲突会，但 UUID 分布均匀实际 O(1)，Java8+ 桶超8转红黑树 O(log n) |
| 续期是怎么续的 | 就是重置 Redis key 的 TTL，底层一条 EXPIRE key 540 命令 |
| 为什么续期间隔是租期的1/3 | 业界惯例（Redisson自带也是÷3），能容忍连续失败2次，第3次还能补救 |
