# 亮点④：分布式租约——Redisson 分布式锁 + Watchdog 续期

---

## 1. 业务背景

### 1.1 这是什么场景？——后台定时任务

前三条亮点围绕的都是"KAM 点模拟"这个实时请求。第四条场景完全不同——这是一个**定时后台任务**。

RGM 是多租户 SaaS，每个快消品牌是一个**租户**：

```
租户列表：
  tenant-001：可口可乐
  tenant-002：百事可乐
  tenant-003：雀巢
  tenant-004：联合利华
  ... 共几十个租户
```

系统需要定时给每个租户同步数据——比如把各租户的促销基线数据从 HANA 同步到应用缓存（Redis），确保 KAM 做模拟时拿到的是最新数据。

> **和亮点①的区别——同步的是不同层面的数据：**

>

> 亮点④定时任务同步的是**基线数据**（base_vol、base_spend、price_elasticity 等历史统计值），这类数据变化很慢（几周才更新一次），适合提前缓存到 Redis。

>

> 亮点①优化的是**模拟计算时动态查询的 KPI 明细**——KAM 每次模拟的促销配置不同，涉及的 300 个 SKU × 多个 UOM 的参数必须实时查，没办法提前全部缓存，所以才有 N+1 问题需要优化。

>

> 两者不冲突：定时任务负责把"相对静态的基础数据"预热到缓存；模拟计算负责实时查"和当前促销配置强相关的动态参数"。

**用一次完整的 KAM 模拟流程举例：**

```
【第一步】定时任务（亮点④）提前做的事——每 6 分钟跑一次
  把基线数据从 HANA 同步到 Redis：
    SKU-001（可乐330ml）缓存到 Redis：
      base_vol         = 1200 箱/周  ← 不促销自然卖多少
      price_elasticity = -2.5         ← 价格弹性系数
      base_spend       = 36000 元/周
  这些是历史统计值，今天和明天几乎一样
  提前算好放在 Redis，KAM 模拟时直接取，不用查 HANA
【第二步】KAM 设定大促，点"模拟"——亮点①登场
  这次大促配置（实时的，每次不一样）：
    SKU-001：8折，CASE 维度
    SKU-002：9折，UNIT 维度
    SKU-003：买赠，DISPLAY 维度
    ... 共 300 个 SKU，各自不同
  系统必须实时查这 300 个 SKU 的 KPI 明细 ← 亮点①优化点
  → 一次 IN 批量查询拿到所需的 375 条明细
  → 从 Redis 取 base_vol（亮点④提前缓存的）
  → 两份数据合并计算 Spend
为什么 base_vol 可以缓存，KPI 明细不行？
  base_vol（可以缓存）：
    SKU-001 这周自然销量是 1200 箱
    不管 KAM 搞什么促销，这个历史均值都一样
    所有模拟共用这一份，提前缓存划算
  KPI 明细（不能提前全部缓存）：
    KAM A 的促销：300 个 SKU，CASE 维度
    KAM B 的促销：150 个 SKU，UNIT 维度，完全不同的组合
    系统有几千个 SKU × 多个 UOM = 几万条组合
    每次模拟只用其中几百条，全部预缓存大量浪费
    → 不如实时查，用批量 IN 查询一次拿到需要的那些
```

```
定时任务（每 X 分钟触发一次）：
  for each tenant in [可口可乐, 百事可乐, 雀巢, ...]:
      同步该租户的基线数据
      刷新该租户的 Redis 缓存
      ...
单个租户同步可能要几分钟
几十个租户全部跑完：可能要几十分钟（长任务）
```

### 1.2 部署架构：多 Pod

系统部署在 Kubernetes 上，为了高可用会同时跑**多个 Pod**（多个实例）：

```
Kubernetes 集群
  ├── Pod-1（rgm-planning 实例）
  ├── Pod-2（rgm-planning 实例）
  └── Pod-3（rgm-planning 实例）
        ↓ 三个 Pod 都连着同一个
  [HANA 数据库]  [Redis]  [Kafka]
```

每个 Pod 是完全相同的一份代码，里面都有定时任务调度器（Spring `@Scheduled`）。

### 1.3 问题一：多 Pod 重复执行

定时任务时间到了，**三个 Pod 同时触发**：

```
t=10:00 定时任务触发
  Pod-1：开始遍历所有租户，逐一同步数据
  Pod-2：开始遍历所有租户，逐一同步数据  ← 重复！
  Pod-3：开始遍历所有租户，逐一同步数据  ← 重复！
后果：
  资源浪费：3 倍计算量，3 倍 HANA 查询压力
  数据竞争：三个 Pod 同时写同一个租户的 Redis 缓存
             可能互相覆盖，数据不一致
```

**需要确保同一时刻只有一个 Pod 在执行这个任务。**

### 1.4 问题二：长任务超过锁租期

解决重复执行的方案是用**分布式锁**——抢到锁的 Pod 才执行。但锁不能永久持有，必须设过期时间（租期），防止 Pod 宕机后锁永远不释放、其他 Pod 永远无法接管。

```
Pod-1 抢到锁，设租期 9 分钟
  ↓ 开始执行，处理 tenant-001, tenant-002, tenant-003...
  ↓ 9 分钟到了，任务还没跑完（还有几十个租户）
锁自动过期！
  ↓
Pod-2 看到锁释放了，抢到锁，开始从头执行
  ↓
Pod-1 还在跑，Pod-2 也开始跑 → 又重复了，问题没解决
```

**需要在任务还在跑的时候，持续给锁续期，防止锁提前过期。**

## 2. 解决方案一：Redisson 分布式锁

### 2.1 什么是分布式锁？

单机锁（`synchronized`、`ReentrantLock`）只在同一个 JVM 内有效，不同 Pod 之间不共享。

分布式锁借助一个**所有 Pod 都能访问的外部存储**（这里是 Redis）来协调：

```
抢锁：向 Redis 写入一个 key，写成功 = 抢到锁
释放锁：删除这个 key
其他 Pod：尝试写同一个 key，发现已存在 = 锁被占了，放弃执行
锁过期：key 到了 TTL 自动删除，防止 Pod 宕机后死锁
```

### 2.2 Redis 和 Redisson 的关系

**Redis** 是内存数据库，数据存在内存里，读写极快，支持 key 的过期时间（TTL）。

**Redisson** 是 Java 里操作 Redis 的客户端库，类比关系：

```
Redis    = MySQL 数据库本身
Redisson = MyBatis（Java 里操作 MySQL 的库）
Redisson 底层还是发 Redis 命令
只是把分布式锁的各种细节封装好了
```

**为什么不直接用 Redis 命令自己实现？** 坑很多：

```
坑一：原子性
  // 错误写法：检查 + 写入是两步，不是原子的
  if (redis.get("lock") == null) {    // 检查
      redis.set("lock", "pod-1");     // 写入  ← 这两步之间另一个 Pod 可能插进来
  }
  // 正确：必须用 SET key value NX EX 540（原子命令）
坑二：释放时要验证是不是自己的锁
  // 不能直接 DEL，可能删掉别人的锁
  // 需要 Lua 脚本保证"检查value + 删除"的原子性
坑三：可重入性
  // 同一线程多次加锁需要额外处理
```

**Redisson 把这些全封装好了：**

```java
// 自己写：原子命令 + Lua 脚本 + value 验证... 一堆复杂代码
// Redisson：一行搞定，底层帮你处理所有细节
RLock lock = redissonClient.getLock("tenant-sync-job-lock");
lock.tryLock(2, 540, TimeUnit.SECONDS);
```

```java
RLock lock = redissonClient.getLock("tenant-sync-job-lock");
boolean acquired = lock.tryLock(
    2,          // waitTime：最多等 2 秒抢锁，抢不到就放弃
    540,        // leaseTime：抢到后锁的租期 540 秒（9 分钟）
    TimeUnit.SECONDS
);
if (acquired) {
    try {
        // 只有抢到锁的 Pod 才会进来
        runTenantSyncJob();
    } finally {
        lock.unlock();  // 任务完成，释放锁
    }
} else {
    // 没抢到锁，说明其他 Pod 在执行，跳过
    log.info("另一个实例正在执行，跳过本次");
}
```

### 2.3 加锁以什么为依据？

锁的本质是 Redis 里的一个 **key**，key 的名字就是加锁的依据：

```java
RLock lock = redissonClient.getLock("tenant-sync-job-lock");
//                                   ↑ 这个字符串 = Redis 里的 key 名
```

**所有 Pod 运行同一份代码，用同一个 key 名去抢锁：**

```
Pod-1：SET "tenant-sync-job-lock" "pod-1-uuid" NX EX 540 → 成功（key 不存在）→ 抢到
Pod-2：SET "tenant-sync-job-lock" "pod-2-uuid" NX EX 540 → 失败（key 已存在）→ 没抢到
Pod-3：SET "tenant-sync-job-lock" "pod-3-uuid" NX EX 540 → 失败（key 已存在）→ 没抢到
Redis 里同一时刻只能有一个这个 key → 天然互斥
```

**锁的粒度取决于 key 的名字：**

```java
// 整任务一把锁（我们用的）：所有租户串在同一把锁下，确保整体只跑一次
RLock lock = redissonClient.getLock("tenant-sync-job-lock");
// 也可以按租户加锁（更细粒度）：不同租户可以并行
RLock lock = redissonClient.getLock("tenant-sync-lock:" + tenantId);
// Redis 里：
//   "tenant-sync-lock\:tenant-001" → Pod-1 持有
//   "tenant-sync-lock\:tenant-002" → Pod-2 持有（不同租户互不干扰）
```

我们用整任务一把锁，因为要保证整个同步流程只跑一次，不需要细化到租户级别。

### 2.4 没抢到锁的 Pod 去干什么？

**直接跳过，什么都不做，等下一次定时触发。**

```java
boolean acquired = lock.tryLock(2, 540, TimeUnit.SECONDS);
if (acquired) {
    try {
        runTenantSyncJob();   // 抢到了，执行任务
    } finally {
        lock.unlock();
    }
} else {
    // 没抢到，记个日志，方法直接返回
    log.info("另一个实例正在执行，跳过本次调度");
    // 线程结束，Pod-2/3 继续做它们自己的其他工作
}
```

**完整时间线：**

```
t=10:00  定时任务触发
  Pod-1：tryLock() 抢到锁 → 开始执行任务
  Pod-2：tryLock() 等最多 2 秒 → 没抢到 → log 一行 → 方法返回
  Pod-3：tryLock() 等最多 2 秒 → 没抢到 → log 一行 → 方法返回
t=10:02  Pod-2、Pod-3 已结束，什么都没干
         Pod-1 还在跑，Watchdog 每 3 分钟续期
t=10:45  Pod-1 任务完成，释放锁
t=11:00  下一次定时触发，三个 Pod 再次竞争，重新抢锁
```

**没抢到锁的 Pod，定时任务线程空闲了，是不是浪费？**

这是刻意的取舍，不是浪费。原因有两个：

```
原因一：Pod 不只有定时任务线程
  Pod-2（没抢到锁）：
    ├── 定时任务线程：本次跳过，空闲
    ├── Kafka Listener：继续消费 KAM 模拟请求 ✓
    ├── HTTP 线程池：继续处理 API 请求 ✓
    └── 其他后台线程：正常运行 ✓
  Pod-2 只是"不参与这次定时同步"，其他能力完全正常
原因二：这个任务不适合多 Pod 分摊
  如果让 Pod-1/2/3 各处理一部分租户：
    谁来分片？怎么保证不重叠不遗漏？
    某个 Pod 宕机了，它负责的租户谁来补？
    分片协调逻辑本身就是复杂度和风险
  而且任务内部已经有 5 个 worker 并发处理租户了
  单 Pod 内部并发足够，不需要跨 Pod 分摊
```

**什么时候才需要多 Pod 协作？** 租户数量极大、单 Pod 内 worker 处理不过来时，才引入分布式任务调度（XXL-Job、Elastic-Job），把任务切片分发给多个 Pod。我们几十个租户还没到这个量级。

**一句话：用一个 Pod 全包，是在用简单换正确——不重复、不遗漏、不需要分片协调。**

**但如果持锁的 Pod 宕机了，其他 Pod 还会执行吗？**

不会。其他 Pod 在定时触发时已经跳过了，线程早就结束了：

```
t=10:00  定时触发
  Pod-1：抢到锁，开始执行
  Pod-2：没抢到，跳过，线程结束
  Pod-3：没抢到，跳过，线程结束
t=10:10  Pod-1 宕机
t=10:19  锁到期释放，但 Pod-2/3 不会主动接管
t=10:19~t=11:00  这次同步任务没跑完，无人执行
t=11:00  下一次定时触发，Pod-2 或 Pod-3 抢到锁，从头完整跑一次
         把上次没完成的数据也覆盖掉
```

**这次任务缺失——靠下一次定时触发自然补上。**

这能成立有一个前提：**同步任务是幂等的**——重复执行结果一样，从头跑不会出问题，只是数据晚了一个周期更新。

为什么不做"Pod-1 宕机，Pod-2 立刻接管"？因为那需要宕机事件检测 + 任务进度持久化 + 续跑逻辑，基本上是一套完整的分布式任务调度系统。我们的场景宕机概率低、数据延迟一个周期业务可接受，不值得引入这个复杂度。

### 3.1 为什么需要 Watchdog？——直接设长租期不行吗？

**核心矛盾：任务跑的时间远超锁的租期。**

```
锁租期：9 分钟
任务实际耗时：几十分钟（几十个租户 × 每个几分钟）
```

如果没有 Watchdog，9 分钟后锁自动过期，任务还没跑完：

```
t=0:00   Pod-1 抢到锁，租期 9 分钟，开始执行
t=9:00   租期到！锁自动过期（任务才跑了一半）
t=9:01   Pod-2 发现锁释放了，抢到锁，从头开始执行
         Pod-1 还在跑，Pod-2 也开始跑 → 又重复了
```

**那把租期设长一点不就行了，比如设 2 小时？**

```
租期 2 小时，Pod-1 第 10 分钟突然宕机
    ↓
锁还有 110 分钟才过期
    ↓
Pod-2/3 要等 110 分钟才能接管任务
    ↓
这 110 分钟数据没同步，KAM 拿到的全是旧数据
```

**两个需求天然矛盾：**

```
需求①：任务跑几十分钟，锁要一直有效
需求②：Pod 宕机后，锁要尽快自动释放（9分钟内），让其他 Pod 接管
固定租期只能满足一个：
  租期短 → 满足需求② → 但任务跑一半锁就过期，违反需求①
  租期长 → 满足需求① → 但宕机后等很久，违反需求②
Watchdog 同时满足两个：
  正常情况：任务在跑 → Watchdog 续期 → 锁一直有效       （满足需求①）
  宕机情况：JVM 挂了 → Watchdog 也死了 → 9 分钟后锁过期  （满足需求②）
```

**Watchdog 的本质：动态感知"任务还在不在跑"——在跑就续期，宕机了就让锁自然过期。这是固定租期做不到的。**

**既然是定时任务，锁过期了其他 Pod 也不会来抢，是不是没必要续期？**

这个逻辑在"任务执行时间 < 定时间隔"时是对的。但看一下实际配置：

```json
// .ci/charts/crontab/cronjobs/upgrade-dynamic-contents.json
"cron_expression": "*/6 * * * *"   // 每 6 分钟触发一次
```

```
定时间隔：6 分钟
任务执行时间：几十分钟（几十个租户 × 每个几分钟）
锁租期：9 分钟
任务还没跑完，6 分钟后下一个周期就触发了
下一周期的 Pod 会来抢锁，锁如果过期就重复执行
```

具体场景：

```
t=0:00   定时触发，Pod-1 抢到锁开始执行，Pod-2/3 跳过
t=6:00   第二次定时触发，Pod-2 新线程来抢锁
         → 有续期：锁还在 → 跳过 ✓
         → 没续期：锁在 t=9:00 才过期，这次还好，Pod-2 抢不到
t=9:00   没有续期的情况：锁过期
t=12:00  第三次定时触发，Pod-3 来抢锁 → 锁没了 → 抢到 → 重复执行 ✗
有续期：
  Watchdog 每 3 分钟续期，锁一直有效
  直到任务完成主动释放，其他 Pod 才能抢到
```

**关键约束：定时间隔（6分钟）< 锁租期（9分钟）< 续期后一直有效**

租期必须大于定时间隔，否则第一次触发的锁还没到续期时间就过期，第二次触发就重复进来了。

Redisson 有一个内置的看门狗机制，能自动续期——**但有一个前提：不能指定 `leaseTime`**。

```java
// 自带看门狗生效：不指定 leaseTime
lock.tryLock(2, TimeUnit.SECONDS);
// Redisson 自动设 30 秒租期，并每 10 秒自动续期
// 自带看门狗不生效：指定了 leaseTime
lock.tryLock(2, 540, TimeUnit.SECONDS);
// 固定 540 秒，到期自动释放，不续期
```

我们必须指定 `leaseTime = 540 秒`，原因是：**如果 Pod 宕机，必须保证锁在合理时间内自动释放**。Redisson 自带看门狗在 Pod 宕机时无法感知宕机（JVM 都没了），会导致锁永远不释放。

所以不用自带看门狗，**自己实现一个**。

### 3.2 续期的本质：重置 Redis key 的 TTL

锁在 Redis 里就是一个 key，TTL（Time To Live，过期时间）决定它什么时候自动消失。**续期就是在这个 key 还没过期之前，把它的 TTL 重新设成 540 秒**：

```
t=0s    抢到锁，Redis 里：
        key="UPGRADE_DYNAMIC_CONTENTS_JOB"  TTL=540s
t=180s  Watchdog 续期，Redis 里：
        key="UPGRADE_DYNAMIC_CONTENTS_JOB"  TTL=540s  ← 重置了，不是从 360s 继续倒计时
t=360s  Watchdog 续期，Redis 里：
        key="UPGRADE_DYNAMIC_CONTENTS_JOB"  TTL=540s  ← 再次重置
t=540s  如果没有续期，key 本来会在这里自动消失
        但因为续期了，TTL 一直维持在 540s 左右，永不过期
t=2700s 任务完成，主动 DEL 这个 key → 锁释放
```

底层就是一条 Redis 命令：

```
EXPIRE "UPGRADE_DYNAMIC_CONTENTS_JOB" 540
# 把这个 key 的过期时间重置为 540 秒后
```

### 3.3 真实代码实现：ScheduledExecutorService

文档前面的伪代码用的是 `Thread + sleep`，实际代码用的是更专业的 **`ScheduledExecutorService`**：

```java
// JobHandler.java 真实代码

private final ScheduledExecutorService lockExtender =

    }
    try {
        // 启动 Watchdog 定时续期
        jobRunning.set(true);
        extensionTask = startLockExtension(jobRunning);  // ← 关键
        // 执行实际任务（5个worker并行处理所有租户）
        runAllTenants();
    } finally {
        // 停止续期
        jobRunning.set(false);
        if (extensionTask != null) {
            extensionTask.cancel(false);  // 取消定时任务
        }
        // 主动释放锁
        lockService.unlock(JOB_LOCK_KEY);
    }
}
// Watchdog 实现
private ScheduledFuture\<?> startLockExtension(AtomicBoolean jobRunning) {
    return lockExtender.scheduleAtFixedRate(() -> {
        if (jobRunning.get()) {
            boolean extended = lockService.extendLock(
                JOB_LOCK_KEY,
                540,          // 续期到 540 秒后
                TimeUnit.SECONDS,
                5             // 续期操作本身最多等 5 秒
            );
            if (extended) {
                log.info("lock extended for another 540 seconds");
            } else {
                log.error("CRITICAL: Failed to extend job lock!");
            }
        }
    }, 180, 180, TimeUnit.SECONDS);
    //  ↑首次延迟180s  ↑之后每隔180s执行一次
}
```

**`Thread + sleep` vs `ScheduledExecutorService` 的区别：**

```
Thread + sleep（伪代码里的写法）：
  手动管理线程生命周期
  sleep 期间无法精确控制时间
  中断处理复杂
  生产代码不推荐
ScheduledExecutorService（真实写法）：
  专业的定时调度框架
  scheduleAtFixedRate 保证执行间隔精准
  返回 ScheduledFuture，可以随时 cancel()
  线程池统一管理，@PreDestroy 时统一 shutdown()
```

### 3.4 为什么用 AtomicBoolean？

`jobRunning` 被两个线程访问：

- 主线程：写（任务完成时 `set(false)`）

- Watchdog 线程：读（定时任务里 `get()` 检查）

普通 `boolean` 在多线程下有**可见性问题**——主线程改了值，Watchdog 线程可能因为 CPU 缓存拿到的是旧值，还以为任务在跑，继续续期。

`AtomicBoolean` 基于 `volatile`，保证跨线程可见性：主线程写了，Watchdog 线程立刻能读到最新值。

### 3.5 续期时间线（结合真实参数）

```
t=0s     Pod-1 抢到锁，TTL=540s
         ScheduledExecutorService 启动，首次续期在 180s 后
t=180s   续期触发，TTL 重置为 540s（原本还剩 360s，现在重置到 540s）
t=360s   续期触发，TTL 重置为 540s
t=540s   续期触发，TTL 重置为 540s（如果没续期，锁本来这时候自动消失）
t=720s   续期触发，TTL 重置为 540s
...
t=2700s  任务完成
         jobRunning.set(false)
         extensionTask.cancel(false)  ← 取消定时续期
         lockService.unlock()         ← 主动 DEL Redis key
         其他 Pod 下次定时触发时可以抢锁
```

`EXTENSION_LOCK_TIMEOUT_SECONDS = 5` 的设计原因（代码注释说明）：

```
公式：waitTimeout(2s) + 操作时间(2s) + 安全余量(1s) = 5s
防止的场景：
  新 Pod 正在 tryLock 等待（最多等 2s）
  Watchdog 续期操作同时发生
  两者之间有竞争，5s 超时确保续期操作不无限等待
```

## 6. 业务延伸：周期同步的数据是旧的，可以接受吗？

### 这个任务在同步什么？

代码里方法名是 `upgradeDynamicContents`——更新**动态内容**，也就是 Spend 模拟依赖的**基线数据**：历史销量、历史花费、价格弹性系数等。这些数据从外部系统（S/4HANA、KPI 服务）同步过来，存在本地供 KAM 模拟用。

### 为什么周期同步可以接受？

因为这些数据本身就是**历史统计值**，不是实时数据：

```
基线销量     = 过去 52 周历史均值，今天和明天的值几乎没有变化
价格弹性系数  = 统计模型算出来的系数，可能几周才更新一次
```

KAM 做大促预算决策，用的是历史趋势参考，不是实时库存。

```
KAM 今天做模拟：用上个周期同步的基线
KAM 明天做模拟：用今天同步的基线
两份数据的差异：极小（历史均值变化很慢）
对 Spend 模拟结果的影响：可以忽略不计
```

类比：天气预报不需要每秒更新，因为天气本身变化就是小时级的。

### 如果要实时同步，代价是什么？

```
实时同步 = 上游每次数据变化都立刻触发更新
  需要监听所有上游数据变更事件
  并发写入 + 租户隔离 + 数据一致性，复杂度成倍增加
  对 HANA 和 Redis 的压力极大
收益：基线精度提升极小（历史均值本来变化就慢）
成本：系统复杂度大幅上升
结论：不值得，周期同步是合理的工程取舍
```

### 每 6 分钟触发一次，任务到底要跑多久？

代码里没有固定的预估时间，因为执行时间取决于**租户数量和每个租户的账户计划数量**，是动态的。

但任务有**智能跳过机制**，大多数情况下跑得很快：

```java
// PlanningService.java
apUuids.removeIf(apUuid ->
    currentCommit.equals(planningRedisHandler.getValue(apUuid, tenantId)));
// 如果这个账户计划的数据已经是最新版本（git commit 一致），直接跳过
// 不需要重新计算
```

实际执行模式：

```
第一次执行（或新版本部署后）：
  所有租户的数据都需要处理 → 可能跑几十分钟
后续常规执行：
  检查每个账户计划的 commit，发现和当前版本一致
  直接跳过，不做重复计算 → 很快结束
只有两种情况才真正"跑很久"：
  1. 新版本部署后第一次执行（commit 变了，全量更新）
  2. 基础数据真的发生了变更
```

**所以"每 6 分钟触发、Watchdog 每 3 分钟续期"这两个频率是独立的：**

```
cron 每 6 分钟：触发新一轮检查，大多数时候很快跳过
Watchdog 每 3 分钟：只在任务真正在跑的时候才需要，平时根本用不到
```

续期机制是为**少数真正跑很久的情况**准备的兜底，不是每次都用得上。

## 7. 三个参数的设计依据

从代码里可以看到三个核心参数：

```java
LOCK_WAIT_TIMEOUT_SECONDS       = 2    // 抢锁等待时间
INITIAL_LOCK_LEASE_TIME_SECONDS = 540  // 锁的初始租期（9 分钟）
LOCK_EXTENSION_INTERVAL_SECONDS = 180  // Watchdog 续期间隔（3 分钟）
```

### 2 秒抢锁——为什么不长不短？

```
太短（0 秒）：Pod-2/3 立刻放弃，但 Pod-1 刚抢到还没稳定，偶尔误判
太长（30 秒）：Pod-2/3 的线程白白挂着等，浪费资源
2 秒：足够三个 Pod 竞争出胜负，不让失败的 Pod 等太久
```

还有一个原因（代码注释写了）：防止 Watchdog 续期操作和新的抢锁操作之间的竞争——2 秒给续期操作留了足够缓冲。

### 9 分钟租期——为什么是 3 倍续期间隔？

```
太短（1 分钟）：Watchdog 每 3 分钟续期，1 分钟租期根本撑不到续期
太长（2 小时）：Pod 宕机后要等 2 小时，数据长时间不更新
9 分钟 = 3 × 续期间隔（3 分钟）：
  即使 Watchdog 一次续期失败（网络抖动），还有 6 分钟缓冲
  下一次续期能补救，不会锁提前过期
  Pod 宕机后最多等 9 分钟，业务可接受
```

### 3 分钟续期——为什么是租期的 1/3？

**核心思路：续期间隔决定了"连续失败几次锁才过期"。**

```
续期间隔 × N = 租期
N 就是"能容忍连续失败几次"
```

**间隔太短（1 分钟）的问题：**

```
租期 9 分钟，续期间隔 1 分钟：
  任务跑 45 分钟 = 45 次续期请求
  每次都向 Redis 发操作，大部分都是"成功但没必要"
  频繁操作反而增加 Redis 负载，在 Redis 本身压力大时更容易引发抖动
注意：间隔短并不是"更危险"，容错次数反而更多（9次才过期）
真正的代价是：对 Redis 造成不必要的压力
```

**间隔太长（8 分钟）的问题：**

```
租期 9 分钟，续期间隔 8 分钟：
t=0    抢到锁，TTL=540s（9分钟）
t=480s 续期触发，TTL 重置为 540s ✓（还有 60s 才过期，刚好续上）
但如果 t=480s 这次续期失败：
  t=480s  续期失败！TTL 还剩 60s
  t=540s  锁过期！下一次续期要到 t=960s，根本来不及救
只有 60s 的容错窗口
一次失败就完了，风险极高
```

**3 分钟（= 9 ÷ 3）的容错分析：**

```
t=0s    抢到锁，TTL=540s
t=180s  续期，TTL=540s（还有 360s 才过期）
假设 t=180s 续期失败：
  TTL 继续倒计时，t=360s 还有 180s 才过期
  t=360s 再次续期，成功！TTL=540s ✓
  → 一次失败，完全补救
假设 t=180s 和 t=360s 连续两次失败：
  t=540s 还剩 0s，锁过期
  但此时 t=540s 又触发一次续期
  → 两次连续失败，刚好在边界，风险存在但极低
实际上：网络抖动通常是秒级的，连续失败 2 次（6 分钟持续抖动）极为罕见
3 分钟间隔在"Redis 压力可控"和"容错能力足够"之间取得平衡
```

**业界经验比例：续期间隔 ≈ 租期 ÷ 3**

```
这个比例不是这个项目发明的，是业界惯例：
  Redisson 自带 Watchdog：租期 30s，续期间隔 10s（= 30 ÷ 3）
  这个项目：租期 540s，续期间隔 180s（= 540 ÷ 3）
÷3 的含义：即使 Watchdog 连续失败 2 次，还有最后一次机会补救
```

**三个参数的关系：**

```
续期间隔（3 分钟）× 3 = 租期（9 分钟）
抢锁等待（2 秒）< 续期操作时间，防止竞争冲突
```

### Q6：如果锁一直续期、任务卡死了怎么办？

**面试官意图**：考察你对异常场景的防御性思考。

**回答：**

这是真实存在的风险，代码里有四层保护：

**第一层：操作本身有超时**

> HANA 查询、Redis 写入都设有超时时间，单个操作卡住会抛异常，CompletableFuture 捕获后任务最终会结束，锁会被释放。不会出现单个操作永远卡住的情况。

**第二层：Kubernetes liveness probe**

```
Pod 卡死无响应
    ↓
K8s liveness probe 检测到不健康
    ↓
K8s 强制 kill Pod → JVM 终止 → Watchdog 线程也死了
    ↓
不再续期 → 9 分钟后锁自动过期 → 其他 Pod 可以接管
```

**第三层：`@PreDestroy` 清理**

```java
@PreDestroy
public void cleanup() {
    lockExtender.shutdown();  // 强制停掉续期线程
    tenantExecutor.shutdown();
}
```

Pod 正常关闭时（K8s 滚动更新、缩容），Spring 调 `@PreDestroy`，续期线程被停掉，锁自然过期。

**第四层：续期失败报警**

```java
if (!extended) {
    log.error("CRITICAL: Failed to extend job lock!");
    // 接入监控后触发报警，人工介入
}
```

**结论：任务操作有超时、K8s 会强杀卡死的 Pod、JVM 死了续期也停——"锁永远续期卡死"在实际中很难发生，有多层兜底。**
