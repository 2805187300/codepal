## 0. 项目介绍

### 0.1 30 秒版本

**面试官：介绍一下城遇优选，以及你主要做了什么。**

**候选人：**

城遇优选是一个基于 Spring Boot、Redis、Redisson、Kafka 和 MySQL 的本地生活与商户运营平台，包含商户查询、优惠券发放与抢购、达人探店、好友关注、签到和附近商户搜索等功能。

我重点负责四块：第一，使用 JWT 双 Token、Redis 和自定义拦截器实现多实例下的登录鉴权与令牌主动失效；第二，为优惠券秒杀设计资格令牌、令牌桶和滑动窗口，分层拦截无效及突发请求；第三，使用 Redis + Lua 原子完成库存预扣和一人一单校验，再通过 Kafka 异步创建订单，并用幂等和对账补偿保证最终一致性；第四，使用 Redis LFU 识别热点店铺，以 Caffeine + Redis 二级缓存承接热点查询，并用布隆过滤器治理缓存穿透。

### 0.2 2 分钟版本

**候选人：**

这个项目的核心矛盾是：平时以读请求为主，但秒杀时会瞬间出现大量写请求。如果所有请求都直接访问 MySQL，库存行、数据库连接池和订单写入会成为瓶颈。因此我把链路拆成四层：

1. **身份层**：Access Token 承担短期接口鉴权，Refresh Token 的有效状态放在 Redis，支持多实例共享和主动撤销。
2. **流量层**：滑动窗口限制单用户高频请求，令牌桶控制系统入口速率，秒杀资格令牌进一步减少进入扣库存链路的请求。
3. **交易层**：Lua 在 Redis 内原子执行库存判断、重复购买判断和预扣；成功请求写入 Kafka，由消费者按数据库承载能力异步落单。
4. **查询层**：热点店铺进入 Caffeine + Redis 二级缓存；布隆过滤器先拦截明显不存在的店铺 ID，降低恶意穿透造成的数据库压力。

这四层分别解决“谁能访问、多少流量能进来、订单怎样可靠落库、热点查询怎样稳定”四个问题。

### 0.3 架构链路

```text
普通查询：客户端 -> JWT 拦截器 -> Caffeine -> Bloom Filter -> Redis -> MySQL

秒杀请求：客户端 -> JWT 拦截器
                  -> 单用户滑动窗口
                  -> 全局令牌桶
                  -> 秒杀资格校验
                  -> Redis Lua（库存 + 一人一单）
                  -> Kafka
                  -> 幂等消费者
                  -> MySQL 订单
                  -> 对账与补偿
```

## 1. 登录鉴权：JWT 双 Token + Redis

### 1.1 为什么使用双 Token，而不是一个长期 JWT？

**面试官：一个 JWT 就能鉴权，为什么还要 Access Token 和 Refresh Token？**

**候选人：**

单个长期 JWT 一旦泄露，在过期前很难撤销；如果把有效期设得很短，用户又要频繁登录。双 Token 是在安全性和用户体验之间折中：

- Access Token 有效期短，用于访问业务接口。泄露后的风险窗口较小。
- Refresh Token 有效期长，只用于换取新的 Access Token，并在 Redis 保存服务端状态。
- 刷新时不仅校验 Token 签名和过期时间，还校验 Redis 中的 Refresh Token 是否仍有效。

这样 Access Token 保持轻量，Refresh Token 又具备服务端可控的撤销能力。

### 1.2 Redis 在多实例登录中承担什么角色？

**面试官：JWT 不是无状态的吗，为什么还需要 Redis？**

**候选人：**

JWT 的签名校验可以无状态，但“刷新、登出、改密后失效”都是有状态需求。Redis 主要保存三类状态：

```text
auth:refresh:{userId}:{sessionId} -> refresh token 摘要或 jti
auth:blacklist:{accessJti}        -> 1
auth:version:{userId}             -> tokenVersion（若实现全设备失效）
```

多实例部署时，请求无论落到哪台服务，都读取同一份 Refresh Token 和撤销状态，不依赖某台机器的本地内存。Redis key 的 TTL 与对应 Token 剩余有效期一致，避免无效状态长期占用内存。

### 1.3 自定义拦截器的处理顺序是什么？

**面试官：拦截器具体做了哪些事情？**

**候选人：**

我会按固定顺序处理：

1. 判断是否为登录、刷新令牌等白名单接口。
2. 从请求头提取 Access Token，校验签名、过期时间和必要声明。
3. 使用 `jti` 检查 Redis 黑名单；如果实现了 `tokenVersion`，再校验用户版本号。
4. 从可信 Token 中取出 `userId` 和角色，写入请求上下文。
5. 请求结束后清理线程上下文，避免线程池复用导致身份串线。

业务接口不信任前端传入的 `userId`，当前用户身份只能来自校验后的 Token。

### 1.4 登出和改密怎样让令牌主动失效？

**面试官：JWT 签发后不能撤销，你如何处理登出？**

**候选人：**

登出当前设备时，我会删除该会话的 Refresh Token，并把当前 Access Token 的 `jti` 加入黑名单。黑名单 TTL 只需要覆盖 Access Token 的剩余有效期。

```text
DEL auth:refresh:{userId}:{sessionId}
SETEX auth:blacklist:{accessJti} {accessTokenRemainingTtl} 1
```

改密比当前设备登出范围更大。如果要求所有设备立即失效，只拉黑当前 `jti` 不够，还需要用户级 `tokenVersion`：改密后将版本号加一，旧 Token 中的版本号与 Redis 不一致，就会被全部拒绝，同时删除该用户的 Refresh Token。

**真实性边界：**如果实际代码没有实现 `tokenVersion` 或会话索引，就只能准确表述为“当前令牌主动失效”，不能宣称“所有设备立即下线”。

### 1.5 每个请求都查 Redis，JWT 还有意义吗？

**面试官：既然黑名单要查 Redis，这不又变成有状态 Session 了吗？**

**候选人：**

JWT 仍然避免了查询用户表和反序列化完整会话，Redis 只做一次简单 key 查询。但它确实不是完全无状态，这是为了换取主动撤销能力。工程上可以通过较短的 Access Token 有效期、只缓存撤销状态、连接池和超时配置降低开销。

安全链路不能在 Redis 异常时默认放行。对于下单、改密等敏感写接口，应失败关闭；部分低风险公开查询可以走降级策略。

### 1.6 Refresh Token 被盗怎么办？

**候选人：**

服务端只保存 Refresh Token 的摘要或唯一标识，不明文保存完整 Token；刷新成功后可以执行 Refresh Token Rotation，签发新 Token 并删除旧状态。旧 Refresh Token 再次出现时，说明可能发生重放，应撤销对应会话。前端侧还应使用安全存储和 HTTPS，避免令牌被脚本或中间人窃取。

## 2. 秒杀限流：资格令牌 + 令牌桶 + 滑动窗口

### 2.1 三种机制是不是重复设计？

**面试官：资格令牌、令牌桶、滑动窗口都是限流，为什么要同时使用？**

**候选人：**

三者控制的对象不同：

| 机制 | 控制对象 | 主要目标 |
| --- | --- | --- |
| 滑动窗口 | 单用户、单接口的请求次数 | 防止脚本和重复点击 |
| 令牌桶 | 系统单位时间内接收的总流量 | 削峰并允许有限突发 |
| 秒杀资格令牌 | 能进入库存校验链路的人数 | 尽早淘汰没有购买资格的请求 |

我会先做成本低、拒绝率高的判断，再做成本更高的库存操作。它们共同形成流量漏斗，而不是重复限流。

### 2.2 滑动窗口如何实现？为什么不用 `INCR`？

**候选人：**

固定窗口的 `INCR + EXPIRE` 在窗口边界可能放过双倍流量。例如限制每秒 10 次，用户可以在前一个窗口末尾发 10 次、下一个窗口开头再发 10 次。

滑动窗口可以使用 Redis ZSet：score 是请求时间戳，member 是唯一请求 ID。Lua 脚本原子执行删除窗口外记录、统计当前数量、判断是否放行和写入本次请求：

```lua
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1] - ARGV[2])
local count = redis.call('ZCARD', KEYS[1])
if count >= tonumber(ARGV[3]) then
    return 0
end
redis.call('ZADD', KEYS[1], ARGV[1], ARGV[4])
redis.call('PEXPIRE', KEYS[1], ARGV[2] + 1000)
return 1
```

它比固定窗口精确，但每个请求要维护 ZSet，内存和计算成本更高，因此适合用户级防刷，不适合直接承接全站海量流量。

### 2.3 令牌桶为什么适合秒杀入口？

**候选人：**

令牌桶按固定速率补充令牌，请求拿到令牌才进入后续链路。桶中可以积累少量令牌，所以既限制长期平均速率，也允许短时突发。限流速率不能拍脑袋设置，应根据压测得到的 Redis Lua、Kafka 生产和数据库消费能力，取核心链路可稳定承载值，并预留余量。

未拿到令牌的请求应快速失败或提示稍后重试，不能转而进入应用线程池排队，否则压力只是从入口转移到了服务内部。

### 2.4 秒杀资格令牌如何设计？

**候选人：**

活动开始前，根据可售库存初始化有限的资格数量。用户请求先原子获取资格，拿不到就不进入库存 Lua。资格数可以等于库存，也可以略大于库存以容忍拿到资格但未完成后续请求的情况。

资格令牌不是库存事实，只是前置流量过滤。因此即使资格略微超发，最终仍必须由 Redis Lua 的 `stock > 0` 判断防止超卖。资格令牌也不能替代一人一单校验。

### 2.5 限流顺序怎样安排？

**候选人：**

```text
身份校验
-> 活动状态 / 售罄快速判断
-> 单用户滑动窗口
-> 全局令牌桶
-> 秒杀资格令牌
-> 库存 Lua
```

活动状态和售罄判断成本低，应该尽量靠前。单用户防刷先淘汰明显异常用户，全局令牌桶保护系统总容量，再让通过的请求竞争有限资格。具体顺序还要结合网关和业务服务的部署位置，不能为了“层数多”增加无意义的 Redis 往返。

### 2.6 同一个用户并发请求会不会拿到多个资格？

**候选人：**

资格阶段可以用用户维度的幂等标记减少重复获取，但最终防线仍是库存 Lua 中的一人一单校验，以及 MySQL 上 `(user_id, voucher_id)` 的唯一约束。任何单层防重都不能代替数据库最终约束。

## 3. 异步下单：Redis + Lua + Kafka + 最终一致性

### 3.1 为什么 Lua 能防止超卖和重复购买？

**面试官：Redis 预扣库存怎样保证原子性？**

**候选人：**

我把“检查用户是否购买过、检查库存、扣减库存、记录购买用户”放在同一个 Lua 脚本中。Redis 在执行脚本期间不会插入其他命令，因此这组操作不会出现多个请求同时读到同一份库存再重复扣减的问题。

```lua
-- KEYS[1] = seckill:{voucherId}:stock
-- KEYS[2] = seckill:{voucherId}:users
-- ARGV[1] = userId

if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -2
end

local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock <= 0 then
    return -1
end

redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1
```

如果使用 Redis Cluster，多个 key 必须通过 `{voucherId}` hash tag 落在同一个 slot，否则脚本会报 `CROSSSLOT`。

### 3.2 Redis 单线程是否等于 Lua 可以无限复杂？

**候选人：**

不是。Lua 的原子性来自执行期间阻塞其他命令，因此脚本越长，对 Redis 的影响越大。脚本里只做必要的内存判断和写入，不做循环扫描、大对象处理或外部调用。业务日志、订单创建和复杂计算都放到脚本之外。

### 3.3 为什么不直接在 MySQL 扣库存？

**候选人：**

MySQL 当然可以用条件更新保证不超卖：

```sql
UPDATE voucher_stock
SET stock = stock - 1
WHERE voucher_id = ? AND stock > 0;
```

但秒杀的绝大多数请求最终不会成功，如果全部进入数据库，会竞争同一库存行并占用连接池。Redis Lua 先在内存中筛出成功请求，Kafka 再把瞬时写峰值转换为数据库可以稳定消费的流量。MySQL 的条件更新和唯一索引仍应作为最后防线，而不是因为前面有 Redis 就省略。

### 3.4 Redis 预扣成功后，为什么通过 Kafka 异步落单？

**候选人：**

创建订单通常涉及订单表、库存流水和唯一约束，数据库事务耗时明显高于 Redis 操作。同步落库会让请求线程等待，并把瞬时峰值直接传递给 MySQL。Kafka 把链路拆成两段：

```text
同步：鉴权 -> 限流 -> Lua 预扣 -> 返回“处理中”
异步：Kafka Consumer -> 幂等校验 -> MySQL 事务创建订单
```

用户拿到的是“请求已受理”，不是“订单一定成功”。前端需要根据请求 ID 或订单 ID 查询最终状态。

### 3.5 Lua 成功，但 Kafka 发送失败怎么办？

**面试官：Redis 已经扣库存，消息却没发出去，不就少单了吗？**

**候选人：**

这是链路中最关键的一致性窗口，不能只回答“Kafka 会重试”。安全做法是让每次预扣有可追踪的业务 ID，并留下待处理记录；发送 Kafka 时开启确认和有限重试；对账任务比较“Redis 预扣成功记录”和“MySQL 订单”，发现只有预扣没有订单时，重发消息或执行库存补偿。

```text
orderId / requestId
    -> Redis 预扣成功记录（PENDING）
    -> Kafka 消息
    -> MySQL 订单
    -> 状态完成或补偿
```

如果实际实现只做了定时对账，就如实说“通过对账缩短不一致窗口”，不要宣称已经实现本地消息表或事务消息。简历写的是“结合对账补偿机制”，面试时应把自己真正实现的记录来源、扫描条件、重试次数和补偿动作说清楚。

### 3.6 Kafka 重复投递会不会重复创建订单？

**候选人：**

Kafka 常见语义是至少一次投递，因此消费者必须幂等。我会做三层保护：

1. 消息携带全局唯一 `messageId` 或 `orderId`。
2. 订单表对 `order_id` 建唯一约束。
3. 对 `(user_id, voucher_id)` 建唯一约束，保证业务上的一人一单。

消费者在一个数据库事务中插入订单、写库存流水或消费记录。重复消息触发唯一键冲突时，先确认已存在记录与当前消息业务内容一致，再按幂等成功处理，而不是无限重试。

### 3.7 消息什么时候提交 offset？

**候选人：**

只有数据库事务成功后才能确认消费。如果先提交 offset 再写数据库，服务在两者之间宕机会永久丢单；如果数据库成功但 offset 未提交，消息会重投，因此要依赖消费者幂等。可恢复异常使用有限次数重试和退避，不可恢复的参数或数据异常进入死信或人工处理，避免毒消息阻塞分区。

### 3.8 对账补偿具体对什么？

**候选人：**

至少比较三类事实：Redis 预扣成功记录、Kafka 消费状态、MySQL 订单及库存流水。

| 差异 | 可能原因 | 处理方式 |
| --- | --- | --- |
| Redis 已预扣，MySQL 无订单 | 发送或消费失败 | 重发；超过时限则回补库存并清理购买标记 |
| MySQL 已有订单，消息再次到达 | 重复投递 | 依据唯一键幂等返回成功 |
| 订单长期处理中 | 消费者或数据库异常 | 查询消息状态，重试或进入异常队列 |
| 订单取消但库存未释放 | 补偿失败 | 依据订单状态和库存流水执行幂等回补 |

补偿动作本身也必须幂等，例如使用 `operationId` 防止同一库存被回补两次。MySQL 订单状态和库存流水更适合作为长期事实来源，不能直接人工修改 Redis 后就认为问题解决。

### 3.9 Redis 宕机时能不能降级为直接写 MySQL？

**候选人：**

秒杀链路不能这样降级。Redis 异常时直接把高峰请求切到 MySQL，会绕过前置削峰并把数据库打穿。更安全的策略是临时关闭秒杀入口、快速失败或提示稍后重试，等待 Redis 恢复后再依据数据库和流水重建活动库存。

## 4. 热点缓存：Redis LFU + Caffeine + Bloom Filter

### 4.1 为什么需要 Caffeine + Redis 二级缓存？

**面试官：Redis 已经很快了，为什么还要本地缓存？**

**候选人：**

热点店铺可能让请求集中到少数 Redis key，Redis 虽快，但仍有网络开销，也可能形成单节点热点。Caffeine 在应用进程内读取，不经过网络，可以吸收最热的一小部分请求；Redis 作为共享二级缓存，保证不同实例都能获得缓存数据，并承担本地缓存未命中的查询。

代价是本地缓存存在多副本和短暂不一致，所以只适合店铺详情这类读多写少、允许短时间最终一致的数据，不适合库存、支付状态等强一致字段。

### 4.2 Redis LFU 如何识别热点？

**候选人：**

Redis 配置 LFU 淘汰策略后，会为 key 维护带衰减的访问频次。热点识别任务可以对候选店铺 key 采样，通过 `OBJECT FREQ` 获取近似频次，超过阈值后将对应店铺提升到 Caffeine。

要注意三点：

1. LFU 计数是近似且会衰减，不等于精确 QPS。
2. 不能在生产上高频 `KEYS *` 或全量扫描所有 key；应限定候选集合、分批采样，或结合应用访问指标。
3. 热点也要能降级，频次下降后依靠 Caffeine 的容量淘汰和 TTL 退出。

因此简历中的“基于 Redis LFU 访问频次识别热点”应表述为热点发现信号，而不是精确统计系统。

### 4.3 二级缓存的读取链路是什么？

**候选人：**

```text
1. 查询 Caffeine，命中则返回
2. 判断店铺 ID 是否可能存在
3. 查询 Redis，命中则返回；热点数据回填 Caffeine
4. 查询 MySQL
5. 存在则写 Redis，并按热点策略决定是否写 Caffeine
6. 不存在则写短 TTL 空值，防止同一无效 ID 反复回源
```

布隆过滤器用于快速拒绝“一定不存在”的 ID；它判断“可能存在”时仍要继续查询 Redis 或数据库。

### 4.4 布隆过滤器为什么能防穿透？有什么局限？

**候选人：**

布隆过滤器用多个哈希函数把合法店铺 ID 映射到位数组。查询结果为“不存在”时可以直接拒绝，因此大量随机无效 ID 不会继续访问 Redis 和 MySQL。

它可能把不存在的数据误判为可能存在，但不会把已经正确加入过滤器的数据判断为不存在。误判只会多一次后续查询，所以还要配合空值缓存。新增店铺时要同步加入过滤器；如果初始化未完成或增量更新丢失，就可能出现业务上的假阴性，因此系统启动和重建期间不能盲目信任一个不完整的过滤器。

### 4.5 如何防缓存击穿和雪崩？

**候选人：**

- **穿透**：布隆过滤器 + 短 TTL 空值缓存，处理查询不存在数据。
- **击穿**：热点 key 过期时使用互斥重建或逻辑过期，让一个线程回源，其余线程返回旧值或稍后重试。
- **雪崩**：TTL 增加随机抖动，避免大量 key 同时过期；对回源请求限流，并准备降级数据。

互斥重建要设置锁超时并使用唯一值安全释放锁，避免重建线程异常后形成死锁。逻辑过期会返回短时间旧数据，只适用于允许最终一致的店铺展示信息。

### 4.6 店铺信息更新后，二级缓存如何保持一致？

**候选人：**

数据库是事实来源，采用 Cache Aside：先更新数据库，事务成功后删除 Redis 缓存，并通知各应用实例删除 Caffeine 本地缓存。删除而不是直接更新缓存，可以减少并发写造成的新旧值覆盖。

消息通知仍可能失败，因此还需要较短 TTL 或重试作为兜底。这个方案保证的是最终一致，不是强一致。如果面试官提出“刚更新后另一个请求把旧值写回缓存”的并发窗口，可以通过延迟双删、按版本号写入或订阅数据库变更进一步缩短窗口，但不要把这些未实现方案说成已落地功能。

### 4.7 Caffeine 如何控制内存？

**候选人：**

必须设置最大容量或权重、过期策略并观察命中率和淘汰量，不能只设置 TTL。缓存对象要避免携带无关的大字段；如果热点集合过大，本地缓存会挤压 JVM 堆并增加 GC 压力。热点提升阈值、最大容量和 TTL 都应通过流量与堆内存数据调整。

## 5. 综合追问

### 5.1 Redis 在项目里承担了哪些职责？是否过度依赖？

**候选人：**

Redis 在项目里承担 Refresh Token 状态和黑名单、限流计数、秒杀资格、库存预扣、热点数据缓存等职责。它们虽然都使用 Redis，但一致性要求不同：

- 鉴权状态和秒杀库存失败时倾向于拒绝请求，不能绕过。
- 查询缓存失败时可以受控回源或返回降级数据。
- 长期事实仍由 MySQL 的订单、库存流水和业务数据保存。

工程上应按用途区分 key 前缀、TTL、监控和容量，必要时拆分 Redis 实例，避免缓存淘汰影响鉴权或秒杀状态。

### 5.2 你如何证明系统“稳定”？

**候选人：**

稳定性不能只看平均响应时间。我会分层验证：

| 链路 | 重点指标或断言 |
| --- | --- |
| 登录鉴权 | 鉴权延迟、黑名单命中、改密后旧令牌是否被拒绝 |
| 滑动窗口与令牌桶 | 放行速率、拒绝率、边界突发是否受控 |
| Redis Lua | 成功数不超过初始化库存、同一用户只有一次成功 |
| Kafka | 发送失败率、重试、Consumer Lag、重复消息幂等 |
| MySQL | 订单唯一约束、库存流水、连接池等待、事务耗时 |
| 二级缓存 | L1/L2 命中率、回源量、淘汰量、JVM 堆占用 |

测试用户必须使用不同的 `userId`，否则测到的只是“一人一单拒绝性能”。结果还要对账 Redis 成功记录、订单数和库存流水，不能只看接口返回成功率。

### 5.3 具体 QPS、P99 和优化比例是多少？

**候选人：**

这份简历没有写量化性能数据。如果项目没有在固定机器配置、数据规模和脚本下做过正式压测，我会如实回答：目前完成了功能并发测试和一致性校验，但没有可复现的生产级 QPS/P99 数据，所以不报一个虚构数字。随后说明如果补测，会记录机器配置、并发用户、持续时间、数据分布、P95/P99、错误率、Redis CPU、Kafka Lag 和数据库连接池等指标。

这比脱离测试环境说“提升多少倍”更可信。

### 5.4 这个项目最难的地方是什么？

**候选人：**

最难的不是写 Lua 或接入 Kafka，而是划分一致性边界。Redis 预扣成功不等于 MySQL 已有订单，Kafka 也可能重复投递，所以必须给每个请求稳定的业务 ID，让消费者幂等，并通过对账发现“已预扣但无订单”的中间状态。我的核心思路是接受短暂不一致，但所有中间状态必须可追踪、可重试、可补偿。

### 5.5 如果重新设计，你会优先改进什么？

**候选人：**

我会优先补齐可观测性和故障演练：统一 `requestId/orderId/messageId` 贯穿 Redis、Kafka 和 MySQL；为限流拒绝率、Lua 耗时、Kafka Lag、补偿积压和缓存命中率建立指标；再演练 Redis 超时、Kafka 重投、消费者宕机和缓存同时过期。这样不仅能说明方案理论上正确，也能证明异常路径确实可恢复。

## 6. 高频速答

### 6.1 JWT 和 Session 的区别？

JWT 将声明放在签名令牌中，适合跨实例鉴权，但主动撤销需要额外状态；Session 将会话状态放在服务端，撤销直接，但每次通常需要读取会话。这个项目选择短期 Access Token + Redis Refresh 状态和撤销状态，是在轻量鉴权与可控失效之间折中。

### 6.2 为什么黑名单 TTL 不能设成永久？

Access Token 到期后本身就失效，黑名单继续存在没有意义。TTL 设置为 Token 剩余有效期，可以限制 Redis 内存增长。

### 6.3 令牌桶和漏桶的区别？

令牌桶允许桶容量范围内的突发流量，更适合秒杀入口；漏桶强调以固定速率处理请求，输出更平滑，但突发请求通常排队或丢弃。

### 6.4 为什么 Lua 之外还要数据库唯一索引？

Redis 可能发生数据丢失、重复初始化或补偿异常，Kafka 也可能重复投递。数据库唯一索引是最终数据层的防重底线。

### 6.5 Kafka 分区数与消费者数是什么关系？

同一 Consumer Group 内，一个分区同一时刻只能由一个消费者实例消费。消费者数超过分区数不会继续提升并行度；扩容消费者时要结合分区数、消息 key 和数据库承载能力。

### 6.6 秒杀消息如何选择 Kafka key？

如果同一优惠券的事件要求严格有序，可以用 `voucherId` 作为 key，但会让热点券集中到一个分区；如果订单之间相互独立，可以用 `orderId` 分散负载，并依赖幂等和状态机保证单订单正确。是否需要券维度全局顺序要先由业务规则决定。

### 6.7 布隆过滤器能删除元素吗？

普通布隆过滤器不能安全删除，因为多个元素可能共享同一位。需要删除能力时可使用计数布隆过滤器，或定期从有效数据重建过滤器。

### 6.8 本地缓存会不会造成多实例不一致？

会，所以本地缓存只放允许短时最终一致的数据；更新后广播失效通知，并使用 TTL 兜底。库存、令牌状态等强一致数据不能放入普通本地缓存。

### 6.9 Kafka 堆积怎么办？

先降低秒杀入口放行速率，避免继续扩大积压；再看分区数、消费者并发、单条处理耗时和数据库连接池。扩容消费者不能超过有效分区并行度，也不能超过数据库稳定写入能力。

### 6.10 Redis Cluster 下执行多 key Lua 有什么要求？

所有 key 必须位于同一 slot。可使用相同 hash tag，例如 `seckill:{voucherId}:stock` 和 `seckill:{voucherId}:users`。

## 8. 一分钟收尾

城遇优选中，我主要围绕高并发场景做了四层治理：鉴权层使用 JWT 双 Token 和 Redis，使多实例共享刷新状态，并支持令牌主动失效；入口层使用滑动窗口、令牌桶和秒杀资格令牌，把无效与突发流量挡在库存链路之前；交易层使用 Redis Lua 原子完成库存预扣和一人一单，再通过 Kafka 异步落单，并用消费者幂等、数据库唯一约束和对账补偿保证最终一致；查询层使用 Redis LFU 发现热点，以 Caffeine + Redis 二级缓存承接热点访问，并使用布隆过滤器和空值缓存治理穿透。

这套设计的核心不是简单堆 Redis、Kafka 等组件，而是让不同组件各自承担清晰职责：Redis 负责高并发下的快速状态判断，Kafka 负责削峰，MySQL 保存最终业务事实，对账补偿负责发现和修复短暂不一致。

## 9. 四轮连环拷打

这一部分按真实面试节奏组织。第一问考项目表达，第二问考实现细节，第三问攻击异常边界，第四问判断内容是否真正做过。

### 9.1 登录鉴权连环追问

**第一问：为什么不用 Spring Session，非要使用 JWT？**

JWT 更适合把基础身份声明在多个服务间传递，不需要每次读取完整 Session；但项目并没有追求完全无状态，而是把 Refresh Token 和撤销状态放在 Redis，以支持续签、登出和改密失效。选择依据不是“JWT 一定比 Session 好”，而是当前项目需要短期鉴权和服务端主动控制并存。

**第二问：Access Token 每次都查黑名单，Redis 查询失败怎么办？**

不能统一回答“放行”或“拒绝”，要按接口风险区分。订单、改密等敏感写接口采用 fail closed，Redis 撤销状态无法确认时拒绝访问；公开店铺查询可以不依赖登录，或者返回降级数据。还要设置短超时，避免 Redis 故障拖满业务线程。

**第三问：用户修改密码后，如何找到他所有未过期 Access Token？**

不应该扫描所有 Token。用户级 `tokenVersion` 可以把问题从“找出全部 Token”转换成“一次递增版本号”：新请求携带的旧版本与 Redis 不一致即失效。如果实际代码没有版本号，只能失效当前 Token 或已建立索引的会话，不能声称实现了全部令牌失效。

**第四问：如果 Redis 中的黑名单 key 被淘汰，已登出的 Token 是否重新有效？**

会有这个风险。因此鉴权撤销数据不能与可随意淘汰的普通缓存混用，至少要保证容量、TTL 和淘汰策略匹配，生产上更适合拆分逻辑实例或独立实例。Access Token 保持短有效期也是降低最坏风险窗口的手段。

**第五问：为什么不把用户权限全部写进 JWT？**

角色可以作为粗粒度声明，但频繁变化或高风险权限不宜完全依赖长期 Token，否则权限修改后旧 Token 仍保留原权限。可以使用短 Token、权限版本号，或对敏感操作查询最新授权状态。JWT 中也不能放密码、手机号等敏感信息，因为 JWT 通常只是签名，并非加密。

### 9.2 秒杀限流连环追问

**第一问：令牌桶已经限流，为什么还要资格令牌？**

令牌桶只知道系统每秒能接收多少请求，不知道某张券有多少库存。资格令牌与具体活动绑定，可以把大量注定失败的请求挡在库存脚本之前。令牌桶保护系统容量，资格令牌过滤业务竞争者。

**第二问：资格令牌获取后，客户端断网了，这个资格是否永久浪费？**

资格不能设计成永久占用。可以给资格设置短 TTL，或把资格与后续预扣做成紧邻操作并记录状态，由超时任务回收未使用资格。不过回收本身必须幂等。若资格只是允许略微超发的入口计数，也可以不做逐个回收，由库存 Lua 决定最终成功数；具体回答必须与实际实现一致。

**第三问：滑动窗口每次都执行 ZSet 操作，会不会让 Redis 更慢？**

会增加 Redis 操作和内存成本，所以它只用于用户级精确防刷，key 设置短 TTL，并限制单窗口最大成员数。全局大流量使用令牌桶，不会把所有请求都堆进一个超大 ZSet。若精度要求不高，也可以使用固定窗口或本地预限流换取成本下降。

**第四问：攻击者不断更换 userId，用户级限流是不是失效？**

是，所以防刷不能只有 userId 维度。网关还可以结合 IP、设备标识、账号风险状态和验证码，但这些属于扩展治理。当前项目亮点只明确写了接口滑动窗口，面试时可以说“用户维度解决重复请求，恶意账号集群需要更多风控维度”，不要宣称已实现完整风控系统。

**第五问：资格令牌等于库存，为什么仍可能卖不完？**

因为获得资格不等于成功完成预扣和下单，网络中断、用户重复购买、请求超时都会消耗入口机会。可以适度超发资格或回收超时资格，但无论如何都不能突破 Lua 的真实库存判断。

### 9.3 异步下单连环追问

**第一问：Redis 扣库存成功，Kafka 发送失败，具体靠什么记录发现？**

必须存在可枚举的预扣成功记录，例如带 `orderId` 的待处理集合、Stream 或业务记录。对账任务不能凭空知道哪些请求成功。如果代码没有留下这种记录，“定时对账”就是不可执行的口号，应先补齐可追踪状态。

**第二问：先写待处理记录再发 Kafka，这两步也不是原子的，怎么办？**

如果待处理记录与库存扣减由同一个 Lua 脚本写入 Redis，两者可以保持原子；随后发送 Kafka 失败时，待处理状态仍可被扫描重发。如果待处理记录在 MySQL，则涉及跨 Redis 和数据库的一致性，不能用本地事务直接解决，需要可靠事件、补偿或更成熟的事务消息方案。

**第三问：消费者创建订单成功，但回写处理状态失败怎么办？**

消息可能再次被扫描或投递，因此订单落库必须幂等。再次处理时先按 `orderId` 或业务唯一键查询，确认订单已经成功后，再补写完成状态，而不是创建第二个订单。状态机更新也应使用条件更新，防止已完成状态被旧任务覆盖。

**第四问：唯一键冲突都可以当作消费成功吗？**

不可以。要区分“相同业务的重复消息”和“不同请求错误地使用同一个 ID”。发生冲突后，应读取已有记录并校验用户、优惠券和订单号是否一致；一致才按幂等成功处理，不一致说明数据或 ID 生成逻辑有问题，应报警而不是吞掉异常。

**第五问：Kafka 能不能保证 Exactly Once，所以不需要幂等？**

不能这样理解。Kafka 的 Exactly Once 主要覆盖 Kafka 内部的生产和消费事务，不会自动把外部 MySQL 事务纳入同一个原子边界。只要消费者要写 MySQL，就仍要依赖业务唯一键和幂等处理。

**第六问：订单消息为什么不直接无脑增加消费者数量？**

消费者并行度受 Topic 分区数限制，最终还受 MySQL 连接池和稳定写入 TPS 限制。消费者过多会增加再均衡和数据库竞争。正确做法是观察 Lag、单条处理耗时和数据库负载，再协调分区、消费者并发和入口限流速率。

### 9.4 热点缓存连环追问

**第一问：`OBJECT FREQ` 得到的数值代表多少次访问？**

它不是精确访问次数，而是对数增长、随时间衰减的近似计数，只适合比较冷热趋势。因此热点阈值需要实验调节，不能把该值直接解释成 QPS。

**第二问：应用有十个实例，如何保证每个实例的 Caffeine 都知道哪些 key 是热点？**

可以由各实例根据自身访问提升热点，也可以由热点检测任务发布热点或失效消息。前者简单但每个实例热点集合可能不同，后者更统一但增加消息可靠性问题。无论哪种方式，本地缓存都只是优化层，未命中仍可访问 Redis。

**第三问：先更新数据库再删除缓存，删除失败怎么办？**

记录并重试失效消息，配合缓存 TTL 兜底。如果一致性要求更高，可以使用数据库变更日志驱动缓存失效。当前方案仍然是最终一致，不能承诺更新请求返回后所有实例立刻看到新值。

**第四问：为什么不先删除缓存再更新数据库？**

如果先删缓存，随后有查询读到数据库旧值并写回缓存，再更新数据库，就可能让旧值一直保留到 TTL 到期。先更新数据库再删除缓存通常窗口更小，但仍不是严格原子。

**第五问：布隆过滤器说不存在，但数据库里其实有，可能吗？**

算法在元素已正确加入时没有假阴性，但工程实现可能有：过滤器初始化不完整、新增数据尚未同步、重建期间切换错误。因此过滤器的就绪状态和增量更新同样重要，不能只谈算法性质。

## 10. 故障场景题

### 10.1 Redis 主从切换后库存回退

**面试官：主节点刚扣完库存，还没同步到从节点就宕机；从节点提升后库存变多，怎么办？**

**候选人：**

Redis 异步复制确实存在已确认写丢失的窗口，Lua 原子性不能解决跨节点持久化问题。因此 MySQL 唯一约束和库存条件更新仍是最终防线；对账要能发现 Redis 预扣记录与订单事实的差异。对强一致要求极高的库存，还要评估 Redis 方案是否合适，或使用更强的一致性配置，但性能和可用性会有代价。

不要回答“Redis 有主从，所以数据绝不会丢”。

### 10.2 Kafka 某个分区持续积压

排查顺序：

1. 看是否只有一个分区积压，判断消息 key 是否造成热点倾斜。
2. 看消费者是否频繁异常重试或发生再均衡。
3. 看单条数据库事务耗时、慢 SQL 和连接池等待。
4. 先降低对应活动入口速率，再修复消费者瓶颈。
5. 如果业务允许，调整 key 分布或增加分区；增加分区后不能再依赖原有全局顺序。

### 10.3 Caffeine 热点 key 同时过期

本地缓存过期后，大量请求会同时访问 Redis；如果 Redis 也过期，就进一步回源 MySQL。应让 L1 和 L2 使用不同 TTL，增加随机抖动，并在 Redis 回源处做单飞或互斥重建。缓存预热只针对可预测热点，不能把全量数据都塞入本地缓存。

### 10.4 对账任务重复执行

每次补偿使用稳定 `operationId`，补偿表或库存流水对其建立唯一约束；更新订单状态时带前置状态条件。例如只有 `PENDING` 才能转为 `COMPENSATED`。即使调度器重复触发或多个实例同时执行，也只能有一个操作真正生效。

### 10.5 系统时间发生偏移

滑动窗口、Token 过期和活动时间都依赖时钟。多实例机器需要时钟同步；安全校验允许非常小的时钟偏差，但不能放宽过多。分布式业务 ID 和顺序判断不要只依赖可能回拨的本地毫秒时间戳。

## 11. 面试手写题

### 11.1 写出一人一单的数据库约束

```sql
ALTER TABLE voucher_order
ADD CONSTRAINT uk_user_voucher UNIQUE (user_id, voucher_id);
```

解释：Redis Set 是高并发前置校验，唯一索引是最终数据层兜底。两层作用不同。

### 11.2 写出数据库防超卖更新

```sql
UPDATE voucher_stock
SET stock = stock - 1,
    version = version + 1
WHERE voucher_id = :voucherId
  AND stock > 0;
```

执行后检查影响行数：等于 1 表示扣减成功，等于 0 表示库存不足或记录不存在。

### 11.3 写出安全释放分布式锁的 Lua

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

解释：锁值使用每个持有者唯一的标识，避免线程 A 超时后误删线程 B 新获得的锁。热点缓存重建可以使用该模式；业务订单幂等不能只依赖锁。

### 11.4 写出 Token 黑名单 key

```java
String key = "auth:blacklist:" + accessTokenJti;
Duration ttl = Duration.between(Instant.now(), accessTokenExpiresAt);
if (!ttl.isNegative() && !ttl.isZero()) {
    redisTemplate.opsForValue().set(key, "1", ttl);
}
```

解释：黑名单生命周期不超过 Access Token 剩余生命周期；真正代码还要处理 Redis 失败并避免把完整 Token 写入日志。

### 11.5 设计消费者幂等伪代码

```text
begin transaction
  if order(orderId) exists:
      verify userId and voucherId
      commit and return success

  insert order(orderId, userId, voucherId, PENDING)
  update voucher_stock set stock = stock - 1
    where voucherId = ? and stock > 0
  insert inventory_ledger(operationId, orderId, -1)
commit
ack message
```

需要说明：实际表设计可能不同；数据库库存是否再次扣减取决于 Redis 预扣与 MySQL 库存模型，但唯一约束、事务和幂等原则不变。

## 12. 容易说错的红线答案

### 12.1 “Redis 是单线程，所以绝对不会超卖”

错误。Lua 只能保证当前 Redis 实例内脚本原子执行；Redis 数据丢失、错误补偿、重复初始化和数据库落库仍可能产生差异。最终还要数据库约束和对账。

### 12.2 “用了 Kafka，所以消息不会丢”

错误。要继续说明生产端确认与重试、预扣成功记录、消费者 offset、幂等和对账补偿。组件名称不是可靠性证明。

### 12.3 “布隆过滤器百分之百准确”

错误。它存在假阳性；工程上的初始化和同步错误还可能造成业务假阴性。

### 12.4 “Caffeine 比 Redis 快，所以所有数据都放本地”

错误。本地缓存多副本、一致性弱且占用 JVM 堆，只适合少量热点、读多写少的数据。

### 12.5 “JWT 是加密的，前端看不到内容”

错误。常见 JWT 是 Base64URL 编码加签，Payload 可以被读取，只是不能在不知道密钥的情况下被无痕篡改。

### 12.6 “消费者越多，Kafka 消费越快”

错误。有效并行度受分区数和下游数据库容量限制，消费者过多还会增加再均衡成本。

### 12.7 “缓存一致性用延迟双删就彻底解决了”

错误。延迟时间难以精确选择，删除也可能失败，它只是缩短部分并发窗口。TTL、消息重试、版本控制或 CDC 都是不同强度的补充方案。

### 12.8 “没做正式压测，但项目能扛十万并发”

错误。并发用户数、请求速率和系统吞吐量不是同一个指标。没有固定环境和复现脚本时，只能陈述已经验证的功能与一致性断言。
