# 亮点②：异步异常治理——CompletableFuture 异常传播修复

---

## 1. 业务背景

### 1.1 这个功能在做什么

接着亮点①的场景：KAM 创建好大促、配好折扣和陈列，点"模拟"，系统要对 300 个 SKU 分别计算 Spend。

亮点①解决了"怎么查数据"的问题，这里要解决"怎么算得快"的问题——300 个 SKU 如果串行一个接一个算，太慢，所以系统把计算任务**拆成子任务并行跑**。

### 1.2 任务是怎么拆的？

一个 SKU 的 Spend 计算，按三个维度拆分成子任务：

```
一场大促的 Spend 计算
    ↓ 拆分维度：SKU × UOM × 日期
子任务①：SKU-001 × CASE  × 第1周
子任务②：SKU-001 × CASE  × 第2周
子任务③：SKU-001 × UNIT  × 第1周
子任务④：SKU-002 × CASE  × 第1周
子任务⑤：SKU-002 × CASE  × 第2周
...（总计几百个子任务）
```

**为什么这样拆？** 因为每个维度组合的计算是完全独立的——SKU-001 第1周 CASE 的 Spend 和 SKU-002 第2周 UNIT 的 Spend 之间没有依赖，可以同时算，最后把所有子任务的结果加起来就是总 Spend。

### 1.3 并行用什么实现？——CompletableFuture

Java 里并行任务用 `CompletableFuture`。先理解它是什么：

**Future（旧）**：提交任务后拿到一个"票据"，需要结果时调 `get()` 阻塞等待。不支持链式操作、组合多个任务。

**CompletableFuture（新）**：在 Future 基础上支持：

- 链式回调（`.thenApply`、`.thenCompose`）

- 组合多个任务（`.allOf` 等所有完成、`.anyOf` 等任意一个完成）

- 异常处理（`.exceptionally`、`.handle`）

```java
// 提交子任务：每个子任务异步跑在线程池里
List\<CompletableFuture\<Result>> futures = subTasks.stream()
    .map(task -> CompletableFuture.supplyAsync(
        () -> calculateSpend(task),   // 计算逻辑
        executor                       // 线程池（亮点③的内容）
    ))
    .collect(toList());
// 等所有子任务都完成
CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
// 收集所有结果
List\<Result> results = futures.stream()
    .map(CompletableFuture::join)
    .collect(toList());
// 汇总 Spend
double totalSpend = results.stream().mapToDouble(Result::getSpend).sum();
```

这是正常流程。问题出在**某个子任务计算失败**的时候。

### 1.4 和亮点①如何串联：从数据准备到并行计算

亮点①和亮点②属于同一条促销模拟链路的前后两个阶段，但职责不同：

```text
KAM 在前端配置促销并点击“模拟”
                ↓
亮点①：准备计算数据
  按需批量查询当前活动的 KPI
  用 SKU + UOM + 日期建立索引并精确匹配
  检查缺失、重复和维度冲突
                ↓
生成一个个输入完整的 CalculationTask
                ↓
亮点②：执行计算任务
  用 CompletableFuture 并行计算
  每个任务返回 SUCCESS 或 ERROR
                ↓
全部成功后才汇总 Spend / Volume / Revenue
```

业务逻辑上两者明确串联；具体代码是否位于同一个方法，需要以真实源码为准。面试中可说“位于同一条模拟计算链路的前后阶段”，不要在未核验源码时断言一定在同一个方法中。

#### 优化前：边查边算，查询和计算混在一起

最直观的原始实现是每处理一个 SKU，先查它的 KPI，再立即计算：

```java
for (PromotionItem item : promotionItems) {
    KpiData kpi = kpiRepository.findBySkuId(item.getSkuId());
    Result result = calculate(item, kpi);
    results.add(result);
}
```

如果为了加速而直接把这段逻辑放入 CompletableFuture：

```java
List<CompletableFuture<Result>> futures = promotionItems.stream()
    .map(item -> CompletableFuture.supplyAsync(() -> {
        KpiData kpi = kpiRepository.findBySkuId(item.getSkuId());
        return calculate(item, kpi);
    }, executor))
    .toList();
```

它只是把 N+1 从“串行发送很多 SQL”变成“多个线程并发发送很多 SQL”，并没有减少查询总数：

```text
20 个 SKU：仍然约 20 次 KPI 查询
300 个 SKU：仍然约 300 次 KPI 查询
```

这种设计还有三个副作用：

1. worker 大量时间花在等待数据库，而不是真正计算；
2. 多个 worker 同时占用连接，容易放大连接池和 HANA 压力；
3. 查询超时、KPI 缺失和公式异常混在同一个异步任务里，失败来源不容易区分。

如果此时再使用原来的异常处理：

```java
.exceptionally(ex -> {
    log.error("calculation failed", ex);
    return null;
})
```

无论是查询失败还是计算失败，都会变成 null，随后被父任务过滤，最终可能把残缺金额当成成功结果返回。

#### 优化后：亮点①的输出就是亮点②的输入

亮点①把查询集中到计算前：

```java
List<String> skuIds = promotionItems.stream()
    .map(PromotionItem::getSkuId)
    .distinct()
    .toList();

List<KpiData> allKpis = kpiRepository.findBySkuIdIn(skuIds);
```

然后按更准确的业务键建立索引：

```java
record KpiKey(String skuId, String uomType, LocalDate dateCode) {}

Map<KpiKey, List<KpiData>> kpiIndex = allKpis.stream()
    .collect(Collectors.groupingBy(kpi -> new KpiKey(
        kpi.getSkuId(), kpi.getUomType(), kpi.getDateCode())));
```

前端配置会先展开为细粒度计算项。例如一个 SKU 同时有 CASE 折扣和 DISPLAY 补贴：

```text
前端配置：SKU-03，W18，CASE 八五折 + 2 个 DISPLAY

展开后：
  SKU-03 / CASE    / W18
  SKU-03 / DISPLAY / W18
```

每个计算项从索引中取得唯一 KPI，并在进入并行计算前检查数据完整性：

```java
List<KpiData> matches = kpiIndex.getOrDefault(key, List.of());

if (matches.isEmpty()) {
    throw new MissingKpiException("缺少 KPI: " + key);
}
if (matches.size() > 1) {
    throw new DuplicateKpiException("KPI 重复: " + key);
}

CalculationTask task = new CalculationTask(
    item.getSkuId(),
    item.getUomType(),
    item.getDateCode(),
    item.getPromotionConfig(),
    matches.get(0)
);
```

因此，优化前后的任务输入发生了本质变化：

```text
优化前的异步任务输入：
  只有前端促销配置
  → 子任务内部还要查询 KPI

优化后的异步任务输入：
  前端促销配置 + 已精确匹配的 KPI
  → 子任务主要负责业务计算
```

#### 两层完整性保护

亮点①应尽量在计算前发现确定性输入问题：

```text
KPI 不存在       → MISSING_KPI
同一业务键有多条 → DUPLICATE_KPI
关键字段为空     → INVALID_KPI
UOM/日期不匹配   → DIMENSION_MISMATCH
前端规则互斥冲突 → INVALID_CONFIG
```

但亮点①不能替代亮点②。即使输入完整，运行时仍可能出现：

```text
公式边界错误、数值除零、临时超时、线程中断、外部服务故障、程序 Bug
```

因此两层职责是：

```text
亮点①：保证进入计算前的数据尽可能完整、正确
亮点②：保证进入计算后的任何失败都不会消失
```

#### 20 个 SKU 场景下的优化意义

假设 20 个 SKU 展开成 29 个 `SKU + UOM + 日期` 计算项，其中发生：

```text
SKU-07 / CASE / W18 → KPI 缺失
SKU-08 / CASE / W18 → KPI 重复
SKU-18 / CASE / W18 → 输入通过，但计算时出现除零异常
```

优化后的处理顺序是：

```text
批量查询并建立索引
    ↓
亮点①提前发现 SKU-07 缺失、SKU-08 重复
    ↓
数据修正后生成 29 个完整任务
    ↓
亮点②并行执行
    ↓
SKU-18 运行时失败，返回显式 ERROR，而不是 null
    ↓
父任务发现 ERROR，拒绝汇总残缺 Spend
```

这说明两项优化共同实现的是：

```text
亮点①：减少不必要的数据库工作，并保证任务输入正确
亮点②：并行执行剩余的必要工作，并保证任务输出完整
```

#### 端到端代码骨架

```java
SimulationResponse simulate(SimulationRequest request) {
    // 1. 校验前端配置
    validateRequest(request);

    // 2. 亮点①：批量查询、建立索引、生成完整任务
    List<CalculationItem> items = expand(request);
    List<KpiData> kpis = batchQueryKpis(items);
    Map<KpiKey, List<KpiData>> index = buildKpiIndex(kpis);
    List<CalculationTask> tasks = buildAndValidateTasks(items, index);

    // 3. 亮点②：并行计算，失败转换为显式 ERROR
    List<CompletableFuture<CalculationResult>> futures = tasks.stream()
        .map(task -> CompletableFuture
            .supplyAsync(() -> calculate(task), executor)
            .exceptionally(ex -> CalculationResult.error(
                task.getSkuId(),
                task.getUomType(),
                task.getDateCode(),
                classifyError(ex),
                safeMessage(ex))))
        .toList();

    CompletableFuture.allOf(
        futures.toArray(new CompletableFuture[0])
    ).join();

    List<CalculationResult> results = futures.stream()
        .map(CompletableFuture::join)
        .toList();

    // 4. 有任何失败就不返回残缺金额
    List<CalculationResult> errors = results.stream()
        .filter(CalculationResult::isError)
        .toList();

    if (!errors.isEmpty()) {
        throw new SimulationException(errors);
    }

    // 5. 全部成功后才汇总
    return aggregate(results);
}
```

记忆时可以压缩为：

```text
优化前：边查边算 → 查询多 → 异常变 null → 残缺结果仍成功

优化后：批量查 → 建索引 → 校验并生成完整任务
                  → 并行计算 → 显式 ERROR → 全部成功才汇总
```

## 2. 问题：子任务失败被"静默吞掉"

### 2.1 什么叫静默吞掉？

原始代码对子任务的异常处理是这样的：

```java
CompletableFuture\<Result> future = CompletableFuture
    .supplyAsync(() -> calculateSpend(task))
    .exceptionally(ex -> {
        log.error("子任务计算失败", ex);
        return null;   // ← 失败了返回 null
    });
```

`exceptionally` 是 CompletableFuture 的异常处理方法：当 `supplyAsync` 里抛出异常时，`exceptionally` 的回调被触发，这里打了日志，然后 `return null`。

**关键问题**：`return null` 之后，这个 future 变成了一个"正常完成、结果为 null"的 future。外面的 `.allOf().join()` 不会报错，父任务感知不到任何异常。

### 2.2 父任务怎么处理 null 的？

```java
List\<Result> results = futures.stream()
    .map(CompletableFuture::join)     // 拿结果，失败的子任务结果是 null
    .filter(Objects::nonNull)          // ← null 被过滤掉，失败信息彻底消失
    .collect(toList());
double totalSpend = results.stream()
    .mapToDouble(Result::getSpend)
    .sum();
// 问题：SKU-002 的子任务失败了，被过滤掉
// totalSpend 少算了 SKU-002 的贡献，是错的
// 但父任务不知道，照样返回"成功"给 KAM
```

### 2.3 后果：脏数据

```
场景：300 个 SKU 的子任务里，SKU-002 因为数据库超时失败了
原来的结果：
  KAM 看到的总 Spend = Σ(SKU-001 到 SKU-300，但跳过了 SKU-002)
  系统显示：✅ 模拟成功
  实际情况：数据残缺，少算了一个 SKU 的花费
KAM 基于这个错误数字做了预算决策，实际促销花费比预测多出来一块
但 KAM 完全不知道，因为系统显示的是"成功"
```

### 2.4 为什么叫"静默"？

```
子任务抛出异常
    ↓
exceptionally 捕获
    ↓
log.error（打进日志，但没人实时盯着日志）
    ↓
return null（异常被"消化"掉，不再传播）
    ↓
父任务：一切正常，继续执行 ✓（其实结果是错的）
    ↓
KAM：界面显示成功，没有任何报错提示
```

整个失败过程对业务代码、对 KAM 完全不可见，就像从来没发生过一样——这就是"静默"。

## 3. 解决方案：引入显式 ERROR 结果

### 3.1 核心思路

不用 `null` 表示失败，而是用一个**带状态的结果对象**：

- 成功 → `Result(status=SUCCESS, spend=1000)`

- 失败 → `Result(status=ERROR, skuId="SKU-002", errorMsg="DB timeout")`

失败的子任务不再"消失"，而是以 ERROR 结果的形式保留下来，父任务可以检查、统计、定位。

### 3.2 定义结果类型

```java
public class Result {
    public enum Status { SUCCESS, ERROR }
    private final Status status;
    private final String skuId;      // 哪个 SKU
    private final String uomType;    // 哪个 UOM
    private final double spend;      // 计算结果
    private final String errorMsg;   // 失败原因（SUCCESS 时为 null）
    // 正常结果
    public static Result success(String skuId, String uomType, double spend) {
        return new Result(Status.SUCCESS, skuId, uomType, spend, null);
    }
    // 失败结果：保留 skuId、uomType，方便定位是哪个子任务失败了
    public static Result error(String skuId, String uomType, String msg) {
        return new Result(Status.ERROR, skuId, uomType, 0, msg);
    }
    public boolean isError() {
        return status == Status.ERROR;
    }
}
```

### 3.3 改造后的异常处理

```java
CompletableFuture\<Result> future = CompletableFuture
    .supplyAsync(() -> calculateSpend(task))
    .exceptionally(ex -> {
        log.error("子任务失败 skuId={} uom={}", task.getSkuId(), task.getUomType(), ex);
        // 不再 return null，而是返回 ERROR 结果，保留失败信息
        return Result.error(task.getSkuId(), task.getUomType(), ex.getMessage());
    });
```

### 3.4 父任务收集并检查

```java
List\<Result> results = futures.stream()
    .map(CompletableFuture::join)
    .collect(toList());   // 不 filter，保留所有结果（包括 ERROR）
// 检查有没有失败的子任务
List\<Result> errors = results.stream()
    .filter(Result::isError)
    .collect(toList());
if (!errors.isEmpty()) {
    // 有失败！记录哪些 SKU/UOM 失败了，整体标记失败
    String failedInfo = errors.stream()
        .map(r -> r.getSkuId() + "/" + r.getUomType() + ": " + r.getErrorMsg())
        .collect(joining(", "));
    log.error("Spend 计算有子任务失败，共 {} 个: {}", errors.size(), failedInfo);
    throw new CalculationException("子任务失败 " + errors.size() + " 个: " + failedInfo);
    // 整体失败，不返回脏数据给 KAM
}
// 全部成功，正常汇总
double totalSpend = results.stream()
    .mapToDouble(Result::getSpend)
    .sum();
```

### 3.5 改造前后对比

```
改造前：
  子任务失败 → return null → filter 过滤 → 失败信息彻底丢失
                                         → 父任务照样成功返回脏数据
                                         → KAM 不知情
改造后：
  子任务失败 → return ERROR结果 → 父任务检测到 ERROR
                                → 整体失败，不返回脏数据
                                → 日志有 skuId/uomType/errorMsg，可定位
                                → KAM 看到明确报错
```

## 4. CompletableFuture 核心知识点

### 4.1 exceptionally vs handle

面试常问，要能区分：

```java
// exceptionally：只在有异常时触发，正常完成时不执行
CompletableFuture\<Result> f = future.exceptionally(ex -> {
    // ex：异常对象，只有出错才进来
    return Result.error("fallback");
});
// 正常完成 → exceptionally 不执行，直接透传结果
// 异常     → exceptionally 执行，返回值替换掉异常，变成"正常完成"
// handle：无论成功还是失败都触发，能同时拿到结果和异常
CompletableFuture\<Result> f = future.handle((result, ex) -> {
    if (ex != null) {
        // 有异常，result 为 null
        return Result.error(ex.getMessage());
    }
    // 正常，ex 为 null
    return result;
});
```

**什么时候用 handle？** 需要在同一个地方统一处理成功和失败，比如记录耗时日志（不管成功失败都要记）。

### 4.2 为什么不让异常直接向上抛？

如果去掉 `exceptionally`，让异常自然传播：

```java
// 去掉 exceptionally，异常不处理
CompletableFuture\<Result> future = CompletableFuture
    .supplyAsync(() -> calculateSpend(task));
// 等所有任务完成
CompletableFuture.allOf(futures.toArray(...)).join();
// 问题：allOf().join() 遇到任意一个子任务失败，会立刻抛异常
// 等所有子任务都跑完之后统一收集上报。这样拿到的是完整的失败列表，而不是只有一个异常。
// 我们需要知道是哪些 SKU 失败了，所以不能这样做
```

**用 ERROR 结果对象的好处**：

1. 所有子任务都能跑完，不会因为第一个失败就停掉

2. 收集所有失败信息（哪些 SKU、哪些 UOM、什么原因）

3. 统一上报，方便排查

## 6. 面试话术

**描述问题：**

> "促销数据按 SKU、日期、UOM 拆成子任务并行计算时，原来的异常处理用 `exceptionally return null`，父任务 filter 掉 null 之后感知不到失败，会把残缺的计算结果当成正确结果返回给 KAM，产生脏数据。"

**描述方案：**

> "把 null 改成显式的 ERROR 状态结果对象，父任务收集完所有结果后先检查有没有 ERROR，有的话整体标记失败并记录是哪些 SKU/UOM 失败了，不再返回脏数据。这样失败可统计、可定位。"

## 7. 高频追问

| 追问 | 回答要点 |
|------|----------|
| CompletableFuture 和 Future 区别？ | Future 只能阻塞 `get`；CF 支持链式回调、组合、异常处理 |
| `exceptionally` vs `handle`？ | `exceptionally` 只处理异常；`handle` 成功失败都触发，能同时拿结果和异常 |
| 为什么不直接让异常上抛？ | `allOf.join()` 只抛第一个失败，其他丢失；ERROR 结果能收集所有失败信息 |
| 这样改会不会影响性能？ | 不会，ERROR 对象很轻量；反而减少了脏数据导致的重算成本 |
| 子任务失败率高怎么办？ | 看业务容忍度：核心计算要严格失败；分析看板可降级——标注"部分数据缺失"继续展示 |

### Q1：你说"静默吞掉"，日志不是打了吗？为什么还叫静默？

**面试官意图**：考察你对"感知"的理解层次。

**回答：**

> "日志是打了，但日志是给开发者排查用的，不是给业务流程用的。父任务的代码逻辑层面完全不知道有失败——它拿到的是 null，filter 掉之后继续汇总，最终返回了一个'看起来成功'的结果。KAM 看到的界面是正常的，没有任何报错提示。只有去翻日志才能发现，但没人会在每次模拟后都去翻日志。所以从业务角度是'静默'的——系统没有把失败的信息传递给任何需要知道的人。"

### Q2：为什么不直接让异常向上抛，而要用 ERROR 结果对象？

**面试官意图**：考察你对 CompletableFuture 异常传播机制的理解。

**回答：**

> "如果不用 `exceptionally`，让异常自然传播，`allOf(...).join()` 在有任何子任务失败时会立刻抛出异常，但只抛第一个失败的，其他子任务的失败信息全部丢失。

>

> 我们需要知道是哪些 SKU、哪些 UOM 失败了，方便定位和重试，所以用 ERROR 结果对象把每个子任务的失败信息都保留下来，等所有子任务都跑完之后统一收集上报。这样拿到的是完整的失败列表，而不是只有一个异常。"

### Q3：这个问题是你发现的吗？怎么发现的？

**面试官意图**：验证真实参与度。

**回答：**

> "是在 code review 时发现的。我看到 `exceptionally` 里 `return null`，然后往上找父任务怎么处理这个 future，看到了 `filter(Objects::nonNull)`，意识到 null 被过滤掉之后失败信息就彻底丢了。

>

> 然后我想了一下业务场景——如果 SKU-002 的计算失败了，过滤掉之后 totalSpend 就少算了 SKU-002 的贡献，但系统还是返回成功，KAM 拿到的是错的数字。这就是脏数据问题。我在 review 里提出了这个隐患，分析了原因，并提出了引入 ERROR 结果对象的改进方向。"

### Q3.5：开发过程中遇到什么问题？怎么定位的？怎么验证改动成功？

**面试官意图**：这是最能区分"真做过"和"背答案"的问题，细节越具体越可信。

#### 怎么定位到这个 bug 的？

不是程序崩了才发现，是 code review 里**顺着数据流主动追**出来的：

```
看到：.exceptionally(ex -> { log.error(...); return null; })
脑子里冒出：这个 null 最后去哪了？
    ↓ 往上追父任务
找到：.filter(Objects::nonNull)   ← null 在这被过滤掉了
    ↓ 再看汇总
找到：.mapToDouble(Result::getSpend).sum()
    ↓ 结论
失败子任务 → null → 被过滤 → sum 少算 → 父任务不知道 → 返回脏数据
```

关键动作：**不只是看一行代码，要顺着数据流从头追到尾**，null 从哪来、流到哪去、最终产生什么影响。

#### 开发过程中踩了哪些坑？

```
**坑一：`allOf().join()` 只暴露第一个失败**
写测试验证多个子任务同时失败时，试了一下不用 ERROR 结果、直接让异常传播会怎样：
```java

CompletableFuture.allOf(futures.toArray(...)).join();

// 结果：只抛出第一个失败子任务的异常

// SKU-002、SKU-003 的失败信息完全丢失

```
亲眼看到这个现象，更加确认 ERROR 结果对象方案的必要性——这不只是设计选择，是实际验证过的。
#### 怎么验证改动是成功的？
**第一层：单元测试**——覆盖三个核心场景：
| 场景 | 预期行为 |
|------|----------|
| 全部成功 | 正确返回 totalSpend |
| 部分失败 | 抛 CalculationException，异常信息含失败 SKU |
| 全部失败 | 抛 CalculationException |
**第二层：行为对比**——同样输入跑改造前后两个版本：
```

改造前：部分子任务失败 → 返回残缺 totalSpend，status=SUCCESS（脏数据）

改造后：部分子任务失败 → 抛 CalculationException，携带失败 SKU 列表

```
两个版本行为明确不同，说明改造生效。
**第三层：日志验证**——故意让某个子任务失败，检查：
- ERROR 日志里有没有 `skuId` 和 `uomType`（可定位）
- 异常信息里有没有失败原因（可排查）
三层验证都通过，说明"失败可统计、可定位、不产生脏数据"这三个目标都达到了。

### Q4：单元测试怎么覆盖这个场景？
**面试官意图**：考察你有没有真的写过测试。
**回答：**
```java

// 场景一：所有子任务成功，结果正确汇总

@Test

void testAllSuccess() {

    List\<CompletableFuture\<Result>> futures = List.of(

        CompletableFuture.completedFuture(Result.success("SKU-001", "CASE", 1000.0)),

        CompletableFuture.completedFuture(Result.success("SKU-002", "CASE", 2000.0))

    );

    double total = aggregate(futures);

    assertThat(total).isEqualTo(3000.0);

}

// 场景二：部分子任务失败，整体必须抛异常，不能返回脏数据

@Test

void testPartialFailureShouldThrow() {

    List\<CompletableFuture\<Result>> futures = List.of(

        CompletableFuture.completedFuture(Result.success("SKU-001", "CASE", 1000.0)),

        CompletableFuture.completedFuture(Result.error("SKU-002", "CASE", "DB timeout"))

    );

    // 有 ERROR，不能返回 1000.0 这个脏数据，必须抛异常

    assertThatThrownBy(() -> aggregate(futures))

        .isInstanceOf(CalculationException.class)

        .hasMessageContaining("SKU-002");  // 异常信息要能定位是哪个 SKU

}

// 场景三：子任务本身抛异常（模拟 DB 超时）

@Test

void testSubTaskThrowsException() {

    CompletableFuture\<Result> failedFuture = CompletableFuture

        .supplyAsync(() -> { throw new RuntimeException("DB timeout"); })

        .exceptionally(ex -> Result.error("SKU-001", "CASE", ex.getMessage()));

    Result result = failedFuture.join();

    assertThat(result.isError()).isTrue();

    assertThat(result.getErrorMsg()).contains("DB timeout");

}

// 场景四：全部失败

@Test

void testAllFailure() {

    List\<CompletableFuture\<Result>> futures = List.of(

        CompletableFuture.completedFuture(Result.error("SKU-001", "CASE", "timeout")),

        CompletableFuture.completedFuture(Result.error("SKU-002", "CASE", "timeout"))

    );

    assertThatThrownBy(() -> aggregate(futures))

        .isInstanceOf(CalculationException.class);

}

```
> "重点是场景二：验证有部分失败时，系统**不能**把剩余成功结果当正确答案返回，必须整体失败。这是防止脏数据的核心保证。"

### Q5：如果大多数成功、极少数失败，可不可以降级——忽略失败的，用成功的继续？
**面试官意图**：考察你对业务容忍度的判断，没有标准答案。
**回答：**
> "这取决于业务对数据准确性的要求。在我们的场景里，KAM 用 Spend 模拟做促销预算决策，数字不准直接影响资金分配，所以选择了严格策略：有任何失败就整体失败，不返回残缺数据。
>
> 但如果是数据看板这类场景，允许少量数据缺失，可以做降级：用默认值填充失败的 SKU，并在结果里打上'部分数据缺失，共 X 个 SKU 未计算'的标记告知用户。关键原则是不能'静默'——用户必须知道数据是不完整的，由用户决定是否采用这个结果。"

### Q6：子任务之间有没有依赖？如果有依赖怎么处理？
**面试官意图**：考察你对并行任务设计的理解。
**回答：**
> "在我们的场景里，子任务之间没有依赖——SKU-001 CASE 第1周的计算和 SKU-002 UNIT 第2周的计算完全独立，所以可以完全并行，用 `allOf` 等所有完成再汇总。
>
> 如果子任务之间有依赖，比如 B 需要 A 的结果，CompletableFuture 可以用 `thenCompose` 做链式依赖：A 完成后自动触发 B 的计算，不需要手动等待。多个前置依赖可以用 `thenCombine` 等 A 和 B 都完成后再触发 C。"
