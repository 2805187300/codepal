# 亮点③：线程池背压——有界队列 + 阻塞式拒绝策略

---

## 1. 业务背景

### 1.1 整体链路回顾

先把前两条亮点串起来，理解本节在哪个位置：

```
KAM 在页面上调整大促参数，点"模拟"
    ↓
系统收到请求（通过 Kafka 消息触发）
    ↓
亮点①：查 KPI 明细数据（批量 IN 查询 + HashMap 索引）
    ↓
亮点②：把计算任务拆成子任务，用 CompletableFuture 并行跑
    CompletableFuture.supplyAsync(task, executor)
                                        ↑
                              提交到这个线程池
    ↓
亮点③：线程池怎么设计，才能稳定处理突发提交 ← 本节
    ↓
汇总所有子任务结果，返回总 Spend 给 KAM
```

**本节的 `executor`**，就是 `supplyAsync` 第二个参数传入的线程池，所有子任务都提交到这里排队、等待被 worker 线程取走执行。

### 1.2 任务从哪里触发的？——Kafka 详解

#### Kafka 是什么？

KAM 点"模拟"之后，**不是直接调后端接口**，而是通过 Kafka 消息触发的。

**为什么不直接调接口？**

```
直接调接口（同步）：
  KAM 点模拟 → 后端算完 → 返回结果
  问题：Spend 模拟要几秒，KAM 页面会卡住等待
通过 Kafka（异步）：
  KAM 点模拟 → 消息扔进 Kafka → 立刻返回"已提交"
  后端慢慢算，算完推送结果给前端
  KAM 不用盯着等，可以继续操作
```

**Kafka 的三个核心角色：**

```
Producer（生产者）= 往 Kafka 里写消息
    → 你们的 API 层，KAM 点模拟时把"启动模拟"写成消息发出去
Kafka Broker（消息中间件）= 暂存消息的地方
    → 消息存在这，等消费者来取
Consumer（消费者）= 从 Kafka 里读消息
    → 后端的 Kafka Listener 线程，读到消息就触发 Spend 计算
```

现实类比：Kafka 就像**快递中转站**——Producer 是寄件人，Broker 是中转站，Consumer 是收件人。

**Topic 和 Partition：**

```
Topic（主题）= 消息的分类，类似快递按目的地分区
  你们有个 topic：spend-simulation-requests
  所有"启动模拟"的消息都放在这个 topic 里
Partition（分区）= topic 的细分，支持多个消费者并行消费
  Topic: spend-simulation-requests
    ├── Partition 0: [消息1, 消息4, ...]
    ├── Partition 1: [消息2, 消息5, ...]
    └── Partition 2: [消息3, 消息6, ...]
```

#### Kafka Listener 线程是什么？

后端用 Spring Kafka，`@KafkaListener` 注解的方法就是消费者入口：

```java
@KafkaListener(topics = "spend-simulation-requests")
public void onMessage(SimulationRequest request) {
    // 收到消息，把子任务提交到线程池
    submitSubTasks(request);  // 这一步很快，只是提交，不等待执行完
}
// 提交完立刻返回，继续消费下一条消息
```

**Kafka Listener 线程的两个职责：**

```
职责①：持续 poll 消息（从 Broker 拉取消息）
职责②：每隔一段时间向 Broker 发 heartbeat（心跳）
        告诉 Broker："我还活着，继续给我发消息"
```

#### 为什么 Listener 线程不能被占用？——Heartbeat 机制

```
正常情况：
  Listener：poll消息 → 提交子任务（很快）→ poll消息 → 发heartbeat → poll消息...
  Broker：  收到heartbeat → 知道消费者活着 ✓
如果 Listener 线程被占用（CallerRunsPolicy 让它自己跑计算任务）：
  Listener：poll消息 → 自己跑计算任务（5秒）→ ...
            这5秒内没有 poll，没有 heartbeat
  Broker：  超过 max.poll.interval.ms 没收到 heartbeat
            → 认为这个消费者挂了
            → 触发 Rebalance（分区重新分配）
            → 消费组短暂中断，消息积压
            → 其他 KAM 的请求也受影响
```

**这就是为什么不能用 CallerRunsPolicy 的根本原因：它让 Listener 线程自己去跑任务，破坏了 heartbeat 机制，导致 Kafka 误判消费者挂掉。**

#### 正确做法：Listener 只负责派活，不自己干活

```
Kafka Listener 线程的定位：接单派活，不亲自执行
  收到消息 → 解析参数 → 把子任务提交给线程池 → 立刻返回
  线程池的 5 个 worker 去真正执行计算
这样 Listener 线程始终轻量、活跃，heartbeat 正常发送
```

### 1.3 什么是线程池和 worker？

```
线程池 = 工厂
核心线程（worker） = 固定 5 个工人，永远在岗
任务队列           = 传送带，排队等待的任务放这里
任务               = 每个子任务的计算逻辑（查 HANA + 算 Spend）
工人不断循环：
  从传送带取一个任务 → 执行 → 执行完 → 再取下一个
5 个 worker = 同一时刻最多 5 个子任务在并行执行
其余任务    = 在队列里排队等空闲 worker
```

代码层面，每个 worker 就是一条一直活着的线程，不断取任务执行：

```java
// 线程池内部每个 worker 在做的事（伪代码）
while (true) {
    Runnable task = queue.take(); // 没任务就阻塞等，有了就取出来
    task.run();                   // 执行计算
}
// 5 条线程同时这样跑 → 同一时刻最多 5 个任务并行
```

### 1.4 问题的来源：突发提交

KAM 不止一个人，实际上同时有几十个 KAM 在使用系统，各自反复调整参数、反复点"模拟"。

```
t=0s  KAM-1 点模拟 → Kafka Listener 收到 → 提交 300 个子任务进线程池
t=1s  KAM-2 点模拟 → Kafka Listener 收到 → 提交 300 个子任务进线程池
t=2s  KAM-3 点模拟 → Kafka Listener 收到 → 提交 300 个子任务进线程池
...
线程池只有 5 个 worker，每秒能处理的任务数有限
提交速度 >> 消费速度 → 队列越堆越长
```

### 1.5 任务积压在哪里？——JVM 堆内存

队列是一个 Java 对象，存在 **JVM 堆内存**里。每个排队的任务（Runnable）也是对象，包含了计算所需的上下文数据（skuId、uomType、日期、KPI 明细引用等）。

```
1 个子任务对象：假设占 2KB（闭包 + 上下文）
1 次模拟：300 个子任务 = 600KB
10 个 KAM 同时模拟：3000 个子任务 = 6MB
持续提交不消化：越积越多 → 几百 MB → OOM
```

OOM（OutOfMemoryError）= JVM 堆内存耗尽，服务直接崩溃，所有 KAM 的请求全部失败。

## 2. 问题：无界队列无限积压

### 2.1 原始代码

```java
// 问题：使用无界队列的线程池
ExecutorService executor = Executors.newFixedThreadPool(5);
// 等价于底层：
new ThreadPoolExecutor(
    5, 5,
    0L, TimeUnit.MILLISECONDS,
    new LinkedBlockingQueue<>()   // ← 无界！不设容量上限
);
```

`LinkedBlockingQueue` 不传容量参数时，默认容量是 `Integer.MAX_VALUE`（约 21 亿），相当于无界。

### 2.2 问题场景

```
队列容量：无限
worker：5 个
提交速度：300 任务/次，多个 KAM 并发提交
结果：
  队列长度：0 → 300 → 600 → 900 → 1200 → ...
  内存占用：持续增长
  到某个点：JVM 堆撑满 → OOM → 服务崩溃
```

### 2.3 为什么说这是"积压在 JVM 内"？

线程池的队列是一个 Java 对象，存在 JVM 堆里。每个排队的任务（Runnable）也是对象，包含了计算所需的上下文数据。任务越堆越多，占的内存越来越多。

---

## 3. 解决方案：有界队列 + 阻塞式拒绝策略

### 3.1 换成有界队列

```java
BlockingQueue\<Runnable> queue = new ArrayBlockingQueue<>(100);  // 最多装 100 个任务
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    5,                        // corePoolSize：5 个核心线程，永远活着
    5,                        // maximumPoolSize：也是 5，不允许扩张
    0L, TimeUnit.MILLISECONDS,
    queue                     // 有界队列，装满就需要处理
);
```

**corePoolSize vs maximumPoolSize 的区别：**

```
corePoolSize（核心线程）：线程池一直保持的线程数，即使空闲也不销毁
maximumPoolSize（最大线程）：队列满了之后，可以临时扩张到的上限
正常流程：
  任务来了 → 先用核心线程跑
  核心线程都忙 → 任务进队列排队
  队列也满了 → 创建临时线程（最多扩到 maxPoolSize）
  还是满 → 触发拒绝策略
我们的配置 core=max=5：
  不允许扩张，线程数始终是 5
  队列满了直接触发拒绝策略（不创建额外线程）
```

**为什么不设计非核心线程（不让 max > core）？**

非核心线程方案长这样：

```
core=5, max=20, queue=100
5个核心线程都忙 → 任务进队列
队列满（100个） → 临时扩张到最多20个线程
20个线程都忙、队列还满 → 触发拒绝策略
高峰过去，临时线程空闲60s → 自动销毁
```

听起来合理，但有一个根本问题：**队列满、20个线程也都忙了，还是得触发拒绝策略**。

一旦要处理拒绝，丢任务不行，CallerRunsPolicy 不行，还是得自定义阻塞式拒绝策略。

所以两个方案的本质对比：

```
方案A（我们用的）：core=max=5，队列满 → 立刻背压
方案B（非核心线程）：core=5, max=20，队列满 → 先扩线程，线程也满 → 再背压
方案B 只是把背压触发时机推后了，并没有消除背压
反而多了线程扩张/销毁的开销
```

**方案B 什么时候更合适？**

任务是纯 IO 密集型时（大量时间等网络、等数据库，CPU 空闲），多开线程能让 CPU 多干活，扩张有收益。

**我们为什么选方案A？**

子任务是 IO + 计算混合型——既要查 HANA（IO），也要做 Spend 计算（CPU）。

计算部分真正占 CPU，线程太多反而互相抢 CPU、上下文切换增加。

5 个线程在我们的机器配置下已经能充分利用 CPU，再多线程带来的收益 < 切换开销。

**一句话：背压和扩张都能应对突发，但扩张有收益的前提是任务 IO 密集、CPU 空闲。我们是计算混合型，扩张没收益还有开销，所以直接背压更干净。**

### 3.2 四种内置拒绝策略都不合适

| 策略 | 行为 | 为什么不行 |
|------|------|------------|
| `AbortPolicy`（默认） | 抛 `RejectedExecutionException` | 任务直接丢失，Spend 计算残缺 |
| `DiscardPolicy` | 静默丢弃新任务 | 任务丢失，且不报错，脏数据 |
| `DiscardOldestPolicy` | 丢掉最旧的任务 | 任务丢失 |
| `CallerRunsPolicy` | 让提交任务的线程自己跑 | 会占用 Kafka Listener 线程（见下） |

**为什么 CallerRunsPolicy 特别危险？**

子任务是由 Kafka Listener 线程提交的（Kafka 消费到消息 → 触发 Spend 模拟 → 提交子任务）。如果让 Kafka Listener 线程自己跑任务：

```
Kafka Listener 线程：
  正常职责：持续消费 Kafka 消息，每 heartbeat 间隔向 broker 汇报
      ↓ 队列满，CallerRunsPolicy 触发
  被迫去跑计算任务（可能需要几秒）
      ↓ 这段时间它没有发 heartbeat
  Kafka broker 认为这个消费者失联
      ↓ 触发 rebalance（分区重新分配）
  整个消费组短暂中断消费，影响其他消息的处理
```

### 3.3 自定义阻塞式拒绝策略——背压

队列满了不丢任务，而是让**提交者阻塞等待**，直到队列有空位：

```java
executor.setRejectedExecutionHandler((task, pool) -> {
    try {
        // put() 的语义：如果队列满了，就阻塞当前线程，直到队列有空位
        // 和 offer() 的区别：offer() 满了直接返回 false，put() 满了阻塞等待
        pool.getQueue().put(task);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new RejectedExecutionException("任务提交被中断", e);
    }
});
```

### 3.4 什么是背压？

背压（Backpressure）= 下游处理能力满了，压力向上游传递，上游自动放慢速度。

```
没有背压（无界队列）：
  上游：拼命往里塞 → 队列无限增长 → OOM
有背压（阻塞式拒绝）：
  上游提交速度过快 → 队列满 → put() 阻塞上游 → 上游被迫等待
  下游处理完一个腾出空位 → put() 返回 → 上游继续提交
整体效果：上游速度自动匹配下游处理能力，队列长度稳定在上限附近
```

现实类比：地铁进站闸机，站台满了就关闸，乘客在外面等，不会让整个站台都被挤爆。

### 3.5 put vs offer 区别

面试常问：

```java
// offer()：尝试放入，满了立刻返回 false，不阻塞
boolean success = queue.offer(task);  // 满了就丢弃或抛异常
// put()：放入，满了就阻塞等待，直到有空位
queue.put(task);  // 满了就等，不返回，不丢任务
```

我们用 `put()` 是因为：不能丢任务，必须等到能放进去为止。

## 4. 完整线程池配置

```java
// 最终实现
BlockingQueue\<Runnable> queue = new ArrayBlockingQueue<>(100);
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    5,                          // 5 个 worker 线程
    5,                          // 不扩张（core == max）
    0L, TimeUnit.MILLISECONDS,
    queue
);
// 阻塞式拒绝策略：队列满了就阻塞提交者，形成背压
executor.setRejectedExecutionHandler((task, pool) -> {
    try {
        pool.getQueue().put(task);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new RejectedExecutionException("任务提交被中断", e);
    }
});
```

**参数选择的理由：**

- `corePoolSize = maxPoolSize = 5`：不允许扩张，线程数固定，避免线程数膨胀

- `queue capacity = 100`：给一定的缓冲空间，不让背压太激进；同时限制上限，防止 OOM

- 阻塞策略而非丢弃：Spend 计算结果要求完整，不能丢任务

## 8. 面试官拷打：高难度追问 & 标准回答

### Q1：背压会不会导致上游线程一直卡住？

**面试官意图**：考察你对阻塞策略副作用的理解。

**回答：**

> "理论上会，如果下游一直处理不完、队列一直满，上游的 `put()` 会一直阻塞。这是一个需要用监控来兜底的地方——如果队列长期处于满载状态，说明 worker 数量或队列容量需要调整，或者上游提交速度需要限制。

>

> 在我们的场景里，worker 处理速度是可以预估的，队列容量 100 给了足够缓冲，正常情况下阻塞是短暂的。如果阻塞时间过长，需要靠超时机制（如整体 Spend 模拟有 timeout）来兜底。"

---

### Q2：这个问题是怎么发现的？怎么定位的？

**面试官意图**：验证真实参与度。

**回答：**

> "是在 code review 时发现的。看到线程池用的是 `Executors.newFixedThreadPool`，知道它底层用的是无界 `LinkedBlockingQueue`，在高并发提交场景下有内存积压风险。结合业务场景——多个 KAM 并发提交、每次几百个子任务——估算了一下积压规模，认为这是一个需要解决的潜在问题。"

### Q3：单元测试怎么测饱和、中断、关停这三个场景？

**面试官意图**：考察测试覆盖的思维。

**回答：**

```java
// 场景一：队列饱和时，提交者应该被阻塞（而不是抛异常或丢任务）
@Test
void testQueueSaturationBlocks() throws InterruptedException {
    // 填满线程池：5 个 worker 跑长任务 + 100 个在队列
    for (int i = 0; i < 105; i++) {
        executor.submit(() -> {
            LockSupport.parkNanos(TimeUnit.SECONDS.toNanos(10)); // 模拟长任务
        });
    }
    // 第 106 个任务提交，应该阻塞而不是立刻完成
    AtomicBoolean submitted = new AtomicBoolean(false);
    Thread submitter = new Thread(() -> {
        executor.submit(() -> {});
        submitted.set(true);
    });
    submitter.start();
    Thread.sleep(500);
    // 500ms 后 submitted 还是 false，说明提交者确实被阻塞了
    assertThat(submitted.get()).isFalse();
    submitter.interrupt();
}
// 场景二：提交线程被中断时，不能静默吞掉，要正确传播中断
@Test
void testInterruptDuringPut() {
    // 填满队列，然后中断提交线程
    // 验证抛出 RejectedExecutionException 且线程中断状态被保留
    Thread.currentThread().interrupt();
    assertThatThrownBy(() -> executor.submit(() -> {}))
        .isInstanceOf(RejectedExecutionException.class);
    assertThat(Thread.currentThread().isInterrupted()).isTrue();
    Thread.interrupted(); // 清除中断状态
}
// 场景三：线程池 shutdown 后，队列里剩余任务要能正常跑完
@Test
void testGracefulShutdown() throws InterruptedException {
    CountDownLatch latch = new CountDownLatch(10);
    for (int i = 0; i < 10; i++) {
        executor.submit(() -> {
            latch.countDown();
        });
    }
    executor.shutdown();
    boolean allDone = executor.awaitTermination(5, TimeUnit.SECONDS);
    assertThat(allDone).isTrue();
    assertThat(latch.getCount()).isEqualTo(0);  // 所有任务都跑完了
}
```

**补充一：单元测试框架原理——JUnit 5 + Mockito**

项目用的是 **JUnit 5**（测试运行框架）+ **Mockito**（Mock 框架），这也是 Java 业界最主流的组合。

**单元测试的核心问题：依赖怎么处理？**

你要测的类（比如 `PlanningService`）依赖了 `KpiRepository`、`RedisHandler` 等，这些依赖在单元测试里不能用真实的（因为没有数据库连接）。解决方案是 **Mock**——用一个"假对象"替代真实依赖，这个假对象你可以控制它的行为。

```
真实调用链：
  PlanningService → KpiRepository → HANA 数据库
单元测试调用链：
  PlanningService → MockKpiRepository（假的，你控制返回什么）
                        ↑
              不需要数据库，想让它返回什么就返回什么
```

**JUnit 5 核心注解：**

```java
@Test              // 标记这是一个测试方法
@BeforeEach        // 每个测试方法执行前跑（初始化数据）
@BeforeAll         // 所有测试方法执行前跑一次（静态方法）
@AfterEach         // 每个测试方法执行后跑（清理）
@DisplayName("...")// 给测试起个可读的名字
@ParameterizedTest // 参数化测试，同一逻辑跑多组数据
```

**Mockito 三步走：**

```java
@ExtendWith(MockitoExtension.class)  // 让 Mockito 接管 JUnit
class PlanningServiceTest {
    @Mock
    KpiRepository kpiRepository;     // ① 声明 Mock 对象
    @InjectMocks
    PlanningService planningService; // ② 自动把 Mock 注入被测类
    @Test
    void testGetKpiDetails() {
        // ③ 定义 Mock 行为（when...thenReturn）
        when(kpiRepository.findBySkuIdIn(List.of("SKU-001")))
            .thenReturn(List.of(new KpiData("SKU-001", "CASE", 1200)));
        // 执行
        var result = planningService.getKpiDetails(List.of("SKU-001"));
        // 断言结果
        assertThat(result).hasSize(1);
        assertThat(result.get(0).getBaseVol()).isEqualTo(1200);
        // 验证 Mock 被调用了（且只调用了一次）
        verify(kpiRepository, times(1)).findBySkuIdIn(any());
    }
}
```

**项目里实际用到的 Mockito 技巧（从真实测试文件看到的）：**

```java
// 1. mockStatic：Mock 静态方法（项目里有用到）
try (var sc = mockStatic(SpendCalculator.class)) {
    sc.when(() -> SpendCalculator.calculateDailyPerProduct(any(), anyString()))
      .thenReturn(mockResult);
    // 测试逻辑...
}  // 出了 try 块，静态 Mock 自动还原
// 2. @Mock vs @Spy
@Mock   // 完全假的，所有方法默认返回 null/0/false
@Spy    // 真实对象，只 Mock 你指定的方法，其他走真实逻辑
// 3. ArgumentMatchers
when(repo.findBySkuIdIn(anyList()))     // 任意 List
when(repo.findById(eq("SKU-001")))      // 精确匹配
when(repo.find(any(String.class)))      // 任意 String 类型
// 4. verify 验证调用行为
verify(repo, times(1)).findBySkuIdIn(any());   // 调用了 1 次
verify(repo, never()).save(any());             // 从未调用
verify(repo, atLeast(1)).findBySkuIdIn(any()); // 至少 1 次
```

**什么用 Mock，什么不用 Mock：**

```
用 Mock（替换掉）：
  ✓ 数据库访问（Repository）
  ✓ Redis 操作
  ✓ 外部 HTTP 调用（OData 服务）
  ✓ Kafka Producer/Consumer
  原则：凡是需要外部系统的，全 Mock
不用 Mock（测真实逻辑）：
  ✗ 被测类本身的业务计算逻辑
  ✗ 纯工具类（SpendCalculator、数学计算等）
  原则：你要验证的那段代码，必须是真实执行的
```

**补充二：第三层监控——Spring Actuator + Prometheus（项目实际方案）**

项目不用 JVisualVM（那是本地调试工具），生产/测试环境用的是：

```
你的 Java 应用（JVM）
      ↓ Spring Actuator 把 JVM 内部状态暴露成 HTTP 接口
http\://app/actuator/prometheus
      ↓ Prometheus 每 15 秒来抓一次，打时间戳存下来
Prometheus 时序数据库
      ↓ Grafana 连接 Prometheus，把数字画成曲线
Grafana 看板（人眼看的）
```

**先搞清楚四个概念：**

**JVM 指标**：JVM 运行你的 Java 程序，内部有很多状态——heap 用了多少内存、有多少线程在跑、GC 发生了几次。这些状态默认藏在 JVM 内部，外面看不到。

**Heap（堆内存）**：JVM 管理的最大内存区域，专门存放所有 `new` 出来的对象：

```
JVM 内存结构：
  ┌─────────────────────────────────┐
  │  Heap（堆）← 最大，存所有对象    │
  │    Young Generation（新生代）    │  new 出来的对象先在这里
  │    Old Generation（老年代）      │  活得久的对象晋升到这里
  ├─────────────────────────────────┤
  │  Metaspace（元空间）             │  存类的结构信息
  ├─────────────────────────────────┤
  │  Stack（栈）每个线程一个         │  存局部变量、方法调用帧
  └─────────────────────────────────┘
```

结合背压理解：每提交一个任务，JVM 在 heap 里 new 一个对象。无界队列堆了 10000 个任务 = heap 里有 10000 个对象在等，内存持续上涨。

**GC（Garbage Collection，垃圾回收）**：JVM 自动回收没人引用的对象来释放 heap 空间。正常情况下 heap 是锯齿状（涨一涨，GC 一下回落）；无界队列堆积时，锯齿底线一直上移，最终 OOM（OutOfMemoryError，内存溢出崩溃）。

```
正常（有背压）：         异常（无界队列堆积）：
  ▲                       ▲
  │  ╭╮  ╭╮  ╭╮           │              ╭──── OOM
  │ ╭╯╰─╯╰─╯╰─╯           │        ╭─────╯
  │╭╯                      │   ╭────╯
  └──────────▶ 时间         └──────────────▶ 时间
  锯齿=GC后回落             底线持续上移=堆积
```

**Spring Actuator**：Spring Boot 自带的"体检接口"，把 JVM 内部状态暴露成 HTTP 端点，可以直接 curl 查询：

```bash
curl http\://localhost:8080/actuator/metrics/jvm.memory.used
# 返回：当前 heap 用了多少字节
curl http\://localhost:8080/actuator/metrics/executor.queue.size
# 返回：线程池队列当前有多少任务在等
```

**Prometheus**：时序数据库，每隔 15 秒自动来抓一次 Actuator 接口，打上时间戳存下来：

```
10:00:00  heap=512MB  queue=3
10:00:15  heap=518MB  queue=7
10:00:30  heap=489MB  queue=2  ← GC 了，回落
```

这样有了历史数据，可以回溯"昨天下午三点内存为什么飙高"。

**Grafana**：把 Prometheus 里的数字画成图表，设置报警（比如 heap 超过 80% 就发通知）。

**类比：**

```
JVM      = 发动机
Actuator = 仪表盘（把转速、油温暴露出来）
Prometheus = 行车记录仪（每15秒记一帧）
Grafana  = 回放软件（画成曲线，看趋势）
```

从 `application.yaml` 可以看到项目已配置：

```yaml
management:
  endpoints:
    include: info, health, metrics, prometheus, loggers, shutdown
```

**Actuator 暴露的 JVM 指标（访问 `/actuator/metrics` 可以看全部）：**

```
jvm.memory.used          → 当前 heap 使用量
jvm.memory.max           → heap 最大值
jvm.gc.pause             → GC 停顿时间
jvm.threads.live         → 存活线程数
executor.queue.size      → 线程池队列长度  ← 背压验证关键指标
executor.active          → 活跃线程数
```

**验证背压是否生效的方法：**

```
压测时在 Grafana 上观察两条曲线：
改造前（无界队列）：
  executor.queue.size 曲线：持续上涨，没有上限
  jvm.memory.used 曲线：跟着上涨，触发频繁 GC
改造后（有界队列 + 阻塞）：
  executor.queue.size 曲线：稳定在 100 以内，不超界
  jvm.memory.used 曲线：在固定区间波动（正常 GC 锯齿），不无限上涨
  → 说明生产者被阻塞了，任务没有无限堆积
  → 背压机制生效
```

**本地也能快速看（不需要 Grafana）：**

```bash
# 应用启动后直接 curl 看指标
curl http\://localhost:8080/actuator/metrics/executor.queue.size
curl http\://localhost:8080/actuator/metrics/jvm.memory.used
# 返回示例：
{
  "name": "executor.queue.size",
  "measurements": [{"statistic": "VALUE", "value": 42.0}]
}
```

## 9. Kafka 深入：背压、分区、消费顺序

### 9.1 队列满了，Kafka 里的消息会怎样？

背压链路完整理解：

```
Kafka Broker（消息持久化存储）
      ↓ Listener 线程 poll 消息
Consumer 应用内存
      ↓ put() 提交到线程池队列
ArrayBlockingQueue（容量100）
      ↓ worker 线程取出处理
业务逻辑执行
```

队列满时：

```
队列满（100条在等）
    ↓
put() 阻塞，Listener 线程停止 poll Kafka
    ↓
消息留在 Kafka Broker，offset 不推进
    ↓
等 worker 消费掉几条，队列有空位
    ↓
put() 返回，Listener 继续 poll，恢复消费
```

**消息留在 Broker 里不是问题，这正是设计目标。** Kafka 本来就是持久化存储消息的，消息在 Broker 里等待完全正常，不是丢失。没有背压时 Consumer 拼命拉消息 → 线程池 OOM 崩溃 → 什么都处理不了；有了背压 Consumer 慢下来 → Kafka 里消息多等一会 → 系统稳定运行。这是主动用"慢"换"稳"的工程取舍。

---

### 9.2 Kafka Broker 满了怎么办？

Kafka 用两个配置控制消息保留：

```
retention.ms    = 消息保留时间（默认 7 天）
retention.bytes = 每个 partition 最大存储量
超过限制：最老的消息被自动删除（不管有没有被消费）
```

所以"Kafka 满了"的真正风险是：**消息过期被删，Consumer 还没消费到就永久丢失**：

```
处理速度 << 生产速度（长期积压）
    ↓
消息在 Broker 堆积超过 retention.ms（比如 7 天）
    ↓
Kafka 自动删除老消息
    ↓
Consumer 的 offset 指向一个已不存在的位置
    ↓
消息永久丢失，业务数据缺失
```

**应对方案：**

```
① 监控 Consumer Lag（消费滞后量）
   Lag = Broker 最新 offset - Consumer 当前 offset
   Lag 持续增大 → 消费跟不上生产 → 立刻报警
② 扩容 Consumer
   增加 Consumer 实例数（不能超过 partition 数）
   或增加 worker 线程数提升单机消费速度
③ 增大 retention 时间，给更多缓冲时间处理积压
④ 业务降级：临时只处理高优先级消息
```

### 9.3 为什么既有 Topic 又有 Partition？

两个概念解决的问题完全不同：

**Topic = 消息的业务分类**

```
不同业务消息必须分开，否则无法区分：
  disaggregation-request  ← 拆分计算请求
  kpi-value-change        ← KPI 数据变更
  funds-change            ← 资金变更
  workflow-completion     ← 工作流完成
如果只有一个 Topic，所有消息混在一起：
  Consumer 无法区分这条消息该由哪段代码处理
  处理拆分的代码和处理资金的代码互相干扰
```

**Partition = 同一 Topic 内的并行通道**

```
disaggregation-request（1个 Topic）
  ├── Partition 0  ← Consumer A 消费
  ├── Partition 1  ← Consumer B 消费
  └── Partition 2  ← Consumer C 消费
作用：提高吞吐量，同一类消息被多个 Consumer 并行处理
```

**类比：**

```
Topic     = 快递公司的不同业务线（顺丰/京东/邮政）
            不同业务线的包裹不能混
Partition = 同一业务线内的多条传送带
            多条并行跑，提高速度
```

**一句话：Topic 解决"消息给谁用"（业务隔离），Partition 解决"怎么更快处理"（水平扩展）。两个问题完全不同，不能互相替代。**

### 9.4 这个项目为什么要保证消费顺序？

**消息是什么：** Disaggregation 拆分计算的触发请求——KAM 在界面上操作账户计划，每次改动都发一条消息：

```
t=1  KAM 把 SKU-001 折扣从 8折 改成 7折  → 消息A
t=2  KAM 又把 SKU-001 折扣从 7折 改成 9折  → 消息B
t=3  KAM 删除了 SKU-001                   → 消息C
```

**乱序消费的后果：**

```
正确顺序 A → B → C：
  最终结果：SKU-001 被删除 ✓
乱序消费 C → A → B：
  先处理"删除"，再处理"改折扣"
  最终结果：SKU-001 还在，折扣 9折 ✗  数据完全错了
```

**账户计划状态机场景更典型：**

```
账户计划状态流转：草稿 → 规划中 → 审批中 → 已批准
消息A：把账户计划从"草稿"推进到"规划中"
消息B：在"规划中"状态下触发拆分计算
乱序，B 先到：
  账户计划还是"草稿"，前置状态不对
  拆分计算触发失败，或用错误状态下的数据计算
```

**本质：这些消息不是独立事件，而是同一业务对象的连续变更，后一条依赖前一条的结果。**

**Kafka 怎么保证顺序：**

```
同一个 partition 内的消息严格有序
同一个 key 的消息路由到同一个 partition
发消息时用账户计划 UUID 作为 key：
  accountPlanUuid → hash → 固定路由到某个 partition
  同一账户计划的所有消息都在同一个 partition 里
  → 消费时天然有序
```

**所以这个项目宁可少用 partition 也要保顺序——业务正确性比吞吐量更重要。**

这个项目用的是 SAP CAP 框架封装的消息层，代码里不直接写 `@KafkaListener`，partition 配置由运维在 Kafka 集群侧管理，应用代码对 partition 数量透明。
