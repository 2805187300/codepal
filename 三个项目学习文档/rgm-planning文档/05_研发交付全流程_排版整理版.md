# 实际开发全流程——结合 rgm-planning 项目

> 这份文档结合 rgm-planning 的真实配置，梳理从需求到上线的完整开发流程。

> 涵盖：Git 操作、本地开发、UT/IT、CI/CD Pipeline、Bug 定位、数据库/Redis/Kafka 查看方式。

## 0. 一次完整开发任务的全流程（总览）

从拿到需求到代码上线，完整走一遍是这样的：

```
① 拿到需求（Jira ticket / 与 PM、senior 对齐）
         ↓
② 拉分支
   git checkout develop && git pull origin develop
   git checkout -b feature/my-task
         ↓
③ 搭本地环境（第一次做的话）
   装好 JDK 17 / Maven / Node.js / Docker Desktop
   配好 hana.properties（连云上 HANA，从团队文档获取）
   需要测 Kafka/Redis 时：cd srv/mock/local && docker-compose up -d
         ↓
④ 本地开发
   写代码（Handler → Service → Repository）
   export GITHUB_SHA=local_build && mvn spring-boot\:run
   用 Postman / curl 手动调 API 验证功能
   看 Terminal 控制台日志排查问题
         ↓
⑤ 写单元测试（UT）并在本地跑
   不需要任何中间件，H2 内存数据库自动替代 HANA
   cd srv && mvn test
   确保通过率 ≥ 92%（质量门禁，低于这个不能提 PR）
         ↓
⑥ 跑集成测试（IT）——只跑和自己改动相关的
   需要连云上 HANA（配好 hana.properties 即可，不需要启动其他中间件）
   export LOCAL_TEST=true && export GITHUB_SHA=local_build
   cd integration-tests && mvn test \\
     -Dcucumber.features=src/test/resources/customer/planning/xxx.feature
         ↓
⑦ 提 PR
   git add <具体文件> && git commit -m "feat: xxx"
   git push origin feature/my-task
   在 GitHub 上开 PR：feature/my-task → develop
         ↓
⑧ CI/CD 自动跑（GitHub Actions）
   编译 → UT → 集成测试 → Sonar → BlackDuck → CodeQL
   在 GitHub Actions 页面看每个 stage 的日志
   有失败 → 看日志 → 本地修 → 重新 push → CI 重跑
         ↓
⑨ Code Review
   团队 senior 审代码，提意见 → 修改 → 再 push
   CI 全绿 + Review 通过 → Merge 到 develop
         ↓
⑩ 自动部署到 INT 环境
   Merge 后 CI 再次触发：构建镜像 → 推制品库
   ArgoCD 检测到新镜像 → 自动部署到 INT（US21 + EU12 两个区域）
         ↓
⑪ 测试环境验证
   在 INT 环境手工冒烟测试
   有问题 → kubectl logs 看 Pod 日志 → 回到④修
         ↓
⑫ 上 Stage / 生产（由 senior/release manager 操作）
   打 Release Tag → Stage 验收（UAT）→ 生产部署
   （实习生一般参与到 ⑪ 为止）
```

**几个关键节点：**

| 节点 | 卡点 | 怎么处理 |
|------|------|----------|
| UT（本地） | 通过率 < 92% | 修失败的测试，不能跳过 |
| IT（本地） | 需要 HANA 连接 | 配好 hana.properties，不需要其他中间件 |
| CI 红了 | 某个 stage 失败 | 看 GitHub Actions 日志，本地复现修完重推 |
| Code Review 有意见 | 按意见改，再 push | 正常流程，不要 force push |
| 测试环境有 Bug | 冒烟发现问题 | kubectl logs 看日志，本地复现，重走 ④-⑨ |

**UT 和 IT 需要哪些中间件：**

```
单元测试（UT）：
  ✓ 什么都不需要启动
  ✓ H2 内存数据库自动替代 HANA
  ✓ Kafka/Redis 全部 Mock
  一行命令：cd srv && mvn test
集成测试（IT）：
  ✓ 需要连云上 HANA（配好 hana.properties）
  ✗ 不需要启动 Kafka（文件模拟）
  ✗ 不需要启动 Redis（IT 不测缓存层）
  一行命令：export LOCAL_TEST=true && export GITHUB_SHA=local_build
            cd integration-tests && mvn test -Dcucumber.features=...
什么时候才需要 docker-compose 起 Kafka/Redis：
  → 测试真实 Kafka 消息时序（Consumer 逻辑）
  → 测试分布式锁、缓存相关功能
  → 大多数日常开发用不到
```

## 2. Git 工作流

### 2.1 分支策略

```
main/master
    └── develop（productive branch，主干）
            └── feature/fix-xxx（开发者的工作分支）
```

从 `.pipeline/config.yml` 可以看到：

```yaml
general:
  productiveBranch: 'develop'   # develop 是主干分支
```

CI/CD 只在 `develop` 分支的 push/PR 触发（见 `build.yml`）：

```yaml
on:
  push:
    branches: [develop]
  pull_request:
    branches: [develop]
```

### 2.2 日常 Git 操作流程

**1. 开始新任务：从 develop 拉分支**

```bash
git checkout develop
git pull origin develop            # 确保本地是最新的
git checkout -b feature/my-task    # 新建功能分支
```

**2. 开发过程中：频繁提交**

```bash
git add src/main/java/...          # 精确 add，不用 git add .
git commit -m "feat: add KPI batch query optimization"
git push origin feature/my-task
```

**3. 合并回 develop：提 PR**

```bash
# 在 GitHub 上创建 PR：feature/my-task → develop
# PR 触发 CI/CD Pipeline 自动跑
# CI 全绿 + code review 通过 → merge
```

**4. 发现 develop 有新提交，需要同步**

```bash
git fetch origin
git rebase origin/develop    # 推荐 rebase，保持线性历史
# 或者
git merge origin/develop
```

### 2.3 Commit 信息规范

项目使用 Conventional Commits 格式：

```
feat: 新功能
fix:  Bug 修复
test: 测试相关
refactor: 重构
chore: 构建/工具配置
示例：
feat: add distributed lock watchdog for tenant sync job
fix: resolve N+1 query in KPI detail batch loading
test: add unit tests for CompletableFuture exception handling
```

### 2.4 `GITHUB_SHA` 是什么？

这个项目里有个特殊约定——构建时必须传入 `GITHUB_SHA`：

```bash
export GITHUB_SHA=local_build   # 本地开发时用这个占位值
```

原因：代码里用 `GITHUB_SHA` 作为数据版本标识（就是第四条亮点里的智能跳过机制）：

```java
// PlanningService.java
apUuids.removeIf(apUuid ->
    currentCommit.equals(planningRedisHandler.getValue(apUuid, tenantId)));
// currentCommit 就来自 GITHUB_SHA 环境变量
```

本地跑 `local_build`，CI 跑时自动注入真实的 Git commit hash。

## 3. 本地开发环境搭建

### 3.1 本地开发需要安装什么？

```
你电脑上只需要装：
  ✓ JDK 17
  ✓ Maven 3.5+
  ✓ Node.js 20+（CDS 编译依赖）
  ✓ Docker Desktop
不需要手动安装：
  ✗ Kafka      → docker-compose 自动拉镜像
  ✗ Redis      → docker-compose 自动拉镜像
  ✗ Zookeeper  → docker-compose 自动拉镜像
  ✗ HANA       → 没有本地版，连云上的实例
```

**Docker 在这里的作用是"本地模拟中间件"，不是"部署用的"。** 两者要区分清楚：

```
用途一：本地开发时模拟中间件（docker-compose）
  docker-compose up -d
  → 在你自己电脑上跑一个本地的 Kafka / Redis
  → 你的 Java 代码连这个本地的中间件
  → 纯粹为了本地调试，不上线
用途二：生产部署（CI/CD 做的事）
  kaniko 构建 Docker 镜像（把 Java 应用打包）
  helm 部署到 Kubernetes
  → 把应用本身容器化，部署到云上
  → 云上的 Kafka/Redis 是独立的云服务，和 docker-compose 无关
```

**实际连接关系：**

```
本地开发时：
  你的 Java 代码（直接跑，不是容器）
       ↓ 连接
  docker-compose 起的 Kafka + Redis（本地模拟）
  云上的 HANA（必须连真实的，无法本地模拟）
生产环境：
  Kubernetes Pod（Java 应用容器）
       ↓ 连接
  云上托管的 Kafka / Redis / HANA（全是真实的）
```

**还有个更简单的情况**：本地默认 Spring Profile 是 `default`，Kafka 消息用**文件模拟**，不需要真实 Kafka。所以大多数开发场景连 docker-compose 都不需要启动，只有测试真实消息时序或 Consumer 逻辑时才需要。

### 3.2 启动本地依赖（Docker Compose）

需要测试 Kafka/Redis 相关功能时，项目自带 `srv/mock/local/docker-compose.yml`：

```yaml
services:
  kafka-service:   # Kafka 消息队列，端口 9092
  zookeeper:       # Kafka 依赖的 ZooKeeper，端口 2181
  console:         # Kafka Web UI（Redpanda Console），端口 18080
  redis:           # Redis 缓存，端口 6379，密码 default
```

启动：

```bash
cd srv/mock/local
docker-compose up -d    # 后台启动，第一次会自动下载镜像
docker-compose ps       # 查看状态
docker-compose down     # 用完关掉，不污染系统
```

访问 Kafka Web UI：http\://localhost:18080（可以在这里看 topic、消息）

### 3.2 HANA 连接配置

本地连接真实 HANA 需要在 `srv/mock/local/hana.properties` 里配置凭据（该文件不提交 git）：

```properties
# hana.properties（gitignore 的，需要手动从团队文档获取）
db.url=jdbc\:sap\://your-hana-host:443?encrypt=true
db.user=YOUR_USER
db.password=YOUR_PASSWORD
```

### 3.3 启动应用

```bash
# 必须先设环境变量，再启动
export GITHUB_SHA=local_build
export LOCAL_INIT_TENANT=t88    # 本地初始化的租户 ID
mvn spring-boot\:run
```

应用启动后监听 `http\://localhost:8080`，可以用 Postman 或 curl 调用 OData API。

### 3.4 Mock 用户

本地开发用 mock 安全，不需要真实 IAS 登录。Mock 用户在 `application.yaml` 里定义：

```yaml
cds:
  security:
    mock:
      users:
        - name: "test-user"
          roles: ["Admin"]
```

HTTP 请求头加 `Authorization: Basic ...` 或直接不加（Spring Profile = default 时通常允许）。

## 5. 单元测试（UT）

### 5.1 项目 UT 现状

```
srv/src/test/java/  ← 543 个测试文件
测试框架：JUnit 5 + Mockito
数据库：H2（内存数据库，测试时替代 HANA）
Spring Profile：test（H2 + mock security + 文件模拟消息）
```

**质量门禁（quality-gates.md）：**

```
单元测试通过率必须 ≥ 92%，否则 CI 不通过，不允许合并
```

### 5.2 典型单元测试结构

```java
// 文件位置示例：
// srv/src/test/java/.../service/PromotionProductPriceServiceTest.java
@ExtendWith(MockitoExtension.class)
class PromotionServiceTest {
    @Mock
    private KpiRepository kpiRepository;      // Mock 依赖
    @Mock
    private PlanningRedisHandler redisHandler;
    @InjectMocks
    private PlanningService planningService;  // 被测类
    @Test
    void testBatchQueryKpiDetails() {
        // Arrange（准备数据）
        List\<String> skuIds = List.of("SKU-001", "SKU-002");
        when(kpiRepository.findBySkuIdIn(skuIds))
            .thenReturn(mockKpiDetails());
        // Act（执行）
        Map\<String, KpiDetail> result = planningService.getKpiDetailMap(skuIds);
        // Assert（验证）
        assertThat(result).hasSize(2);
        assertThat(result.get("SKU-001").getBaseVol()).isEqualTo(100.0);
        verify(kpiRepository, times(1)).findBySkuIdIn(skuIds); // 验证只查了一次
    }
}
```

**什么 Mock，什么不 Mock：**

```
Mock：外部依赖（Repository、Redis、外部 OData 服务）
不 Mock：内部业务逻辑（测真实计算逻辑）
原则：单元测试只验证这一个类的逻辑，不验证依赖
```

### 5.3 H2 vs HANA 的差异

```
H2（测试用）          HANA（生产用）
─────────────────────────────────────
内存数据库            列式存储，支持 Predicate Pushdown
不支持 HANA 特有语法  支持 HANA SQL 扩展
启动快，无状态        需要连接外部服务
适合单元测试          适合集成测试 / 生产
```

写 SQL 时要注意：如果用了 HANA 特有语法，单元测试会在 H2 上失败。

项目里复杂 SQL 放在 `srv/src/main/resources/sql/` 下，方便分别维护。

## 6. 集成测试（IT）

### 6.1 什么是集成测试？

单元测试 Mock 了所有外部依赖，集成测试则是**端到端真实跑**：

- 真实 Spring 容器启动

- 真实 H2 数据库（集成测试环境）

- 真实 HTTP 请求打到 API

- 真实 Kafka 消息发送/消费

```
单元测试：只测一个类，依赖全 Mock
集成测试：测完整业务流程，从 HTTP 请求进来，到数据库写入，到 API 响应
```

### 6.2 BDD Feature 文件

项目用 **Cucumber**（BDD 框架），测试用自然语言描述业务场景：

```gherkin
# integration-tests/src/test/resources/customer/planning/planning.feature
Feature: Planning
  Scenario: manual distribution
    # 准备数据
    When ensure DB cleaned
    Then prepare common dataset
    Then prepare kpi data
    # 业务操作
    When create manual distribution account plan as below
      | AccountPlanID | FiscalYear | CustomerID |
      | AP_MD         | 2026       | 1003070    |
    # 验证结果
    Then check account plan 'AP_MD' ready
    Then the distribution result is returned with cells per period and product
```

**文件组织：**

```
integration-tests/src/test/resources/customer/planning/
  planning.feature              ← 主要规划流程
  disaggregation.feature        ← 拆分计算
  guideline.feature             ← 指导方针
  guardrail-changelog.feature   ← 护栏变更日志
  rsp.feature                   ← 零售价格
  ... 共 30+ 个 feature 文件
```

### 6.3 跑集成测试

```bash
# 跑全部集成测试
cd integration-tests
export LOCAL_TEST=true && export GITHUB_SHA=local_build
mvn test
# 只跑一个 feature（开发时常用）
export GITHUB_SHA=local_build && export LOCAL_TEST=true
cd integration-tests && mvn test \\
  -Dtest=customer.planning.TaskCucumberIntegrationTest \\
  -Dcucumber.features=src/test/resources/customer/planning/planning.feature
```

**质量门禁：**

```
集成测试代码覆盖率 ≥ 81%
跑集成测试前先 comment 掉不相关的 scenario
全部跑完后恢复，不能带着 comment 提交
```

### 6.4 集成测试数据怎么准备？

测试数据优先级（来自 integration-test.md）：

```
1. CSV 文件 → 最推荐，可维护性强
2. SQL INSERT 语句
3. jdbcTemplate.update(INSERT...)  → 动态数据用这个
4. SQL UPDATE 修改已有数据
5. SQL SELECT 做断言
```

**永远不用字符串拼接 SQL，必须用参数化查询。**

## 7. CI/CD Pipeline

### 7.1 Pipeline 架构

项目用 **GitHub Actions** + **SAP Piper**（SAP 内部的 CI/CD 框架）：

```yaml
# .github/workflows/build.yml
触发条件：
  - push to develop 分支
  - PR 向 develop 分支
Pipeline 阶段（并行/串行）：
  init-stage
      ↓
  build-application-stage ─────────────────────────────┐
      ↓                                                 ↓
  post-build-stage      integration-test-stage    security-stage
      ↓
  promote-stage
      ↓
  eureka-deploy-stage（部署到 dev/sit 环境）
      ↓
  report-to-cumulus（上报发布状态）
```

### 7.2 每个阶段做什么？

```
init-stage
  → 初始化 pipeline 环境，判断是否在 productive branch（develop）
build-application-stage
  → mvn clean install（编译 + UT）
  → kaniko 构建 Docker 镜像
  → helm 打包 Helm Chart
  → sonar 代码质量扫描
integration-test-stage
  → 启动临时环境，跑 Cucumber 集成测试
security-stage
  → BlackDuck（OSS 开源合规扫描）
  → CodeQL（静态代码安全分析）
promote-stage
  → 把构建产物（Docker 镜像、Helm Chart）推到制品库
eureka-deploy-stage-dev（PR 时）
  → 部署到 dev 环境（rgm-dev）
eureka-deploy-stage-sit（merge 到 develop 时）
  → 部署到 SIT/INT 环境：
    rgm-int (us21) 和 int (eu12) 两个区域
```

### 7.3 Pipeline 配置关键文件

```
.pipeline/config.yml        ← Piper 步骤配置（构建工具、镜像、Helm 参数）
.github/workflows/build.yml ← GitHub Actions 编排（阶段顺序、依赖关系）
azure-pipelines.yml         ← Azure DevOps Pipeline（备用，PoC 阶段）
```

### 7.4 版本管理

```yaml
# .pipeline/config.yml
steps:
  artifactPrepareVersion:
    versioningType: cloud_noTag
    # cloud_noTag：每次构建自动生成版本号，不打 git tag
    # 格式：原版本号 + commit hash 后缀
    # 例如：1.0.0-abc1234
```

### 7.5 PR 被 CI 拦截怎么办？

**质量门禁（quality-gates.md Rule 3）：**

> 任何 PR 必须所有 CI/CD checks 全绿才能 merge，不能 bypass。

```
常见 CI 失败原因：
  ① UT 通过率 < 92%      → 修失败的测试
  ② 集成测试失败          → 看 Cucumber 报告，找失败的 step
  ③ Sonar 代码质量问题    → 看 SonarQube 报告，修 code smell/bug
  ④ BlackDuck 发现高危依赖 → 升级依赖版本
  ⑤ CodeQL 安全漏洞       → 修代码，消除 SQL 注入/XSS 等风险
  ⑥ 编译失败              → 本地先 mvn clean compile 确认能过
```

## 8. 发现 Bug 后的流程

### 8.1 Bug 来源

```
来源一：本地开发时自己发现
来源二：CI/CD 测试报错
来源三：测试环境（INT/SIT）上报
来源四：生产告警（Grafana/监控）
```

### 8.2 日志在哪看

日志分四个场景，位置完全不同：

**场景一：本地开发时——应用日志**

直接看启动 `mvn spring-boot\:run` 的那个终端，日志打在控制台：

```
2026-08-17 10:23:45 INFO  PlanningService - Processing tenant: t88
2026-08-17 10:23:45 ERROR JobHandler - Failed to sync tenant: t88
java.lang.NullPointerException: ...
    at com.sap.s4hana...PlanningService.java:142
```

想看 SQL 日志，在 `application.yaml` 里加：

```yaml
logging:
  level:
    org.hibernate.SQL: DEBUG    # 打印所有 SQL 语句
```

### 8.3 Bug 定位流程

**Step 1：复现**

```bash
# 先在本地复现
export GITHUB_SHA=local_build && export LOCAL_INIT_TENANT=t88
mvn spring-boot\:run
# 用 Postman / curl 发送触发 Bug 的请求
curl -X GET "http\://localhost:8080/odata/v4/PlanningService/AccountPlans" \\
  -H "Accept: application/json"
```

**Step 2：看日志定位**

按照上面"日志在哪看"的方法，找到对应的错误日志，重点看：

- 异常类型和 message

- stack trace 第一行（最直接指向出问题的代码行）

- 出问题前后的 INFO 日志（还原执行路径）

**Step 3：定位到代码**

常用定位路径：

```
① HTTP 请求 → 找对应的 CAP Handler
   路径：srv/src/main/java/.../handlers/
② Handler 调 Service
   路径：srv/src/main/java/.../service/
③ Service 调 Repository（SQL 查询）
   路径：srv/src/main/java/.../repository/
   SQL 文件：srv/src/main/resources/sql/
④ Kafka 消息 → 找 Consumer
   路径：srv/src/main/java/.../consumer/
```

**Step 4：加临时 debug 日志**

```java
// 临时加日志定位问题（提交前删掉）
log.debug("KPI batch query params: skuIds={}, tenantId={}", skuIds, tenantId);
log.debug("Query result count: {}", results.size());
```

**Step 5：写失败的测试，再修代码**

TDD 式修 Bug：先写一个能复现 Bug 的 UT，让它失败，再修代码让测试通过：

```java
@Test
void testBatchQueryShouldNotTriggerNPlusOne() {
    // 这个测试在修复前会失败
    List\<String> skuIds = List.of("SKU-001", "SKU-002", "SKU-003");
    planningService.getKpiDetails(skuIds);
    // 验证只调用了一次 DB 查询
    verify(kpiRepository, times(1)).findBySkuIdIn(any());
}
```

### 8.3 典型 Bug 类型和定位技巧

| Bug 类型 | 现象 | 定位方法 |
|---------|------|----------|
| N+1 查询 | 慢请求，DB 查询量异常多 | 加 `show_sql=true` 看 SQL 日志 |
| NPE | NullPointerException | 看 stack trace 的第一行 |
| 数据不一致 | Redis 和 DB 数据不同 | 分别查 Redis key 和 DB 记录 |
| Kafka 消息丢失 | 业务流程中断 | 查 Kafka Console 的 topic offset |
| 并发问题 | 偶发错误，难以复现 | 加锁 or 看线程 dump |

### 12.2 谁来触发部署？

```
自动部署（不需要手动操作）：
  PR 阶段  → CI 自动部署到 dev 环境（让你在真实环境验证）
  merge 后 → CI 自动部署到 int / rgm-int（两个区域）
手动部署（需要操作）：
  stage 和 production 通常走发布流程，
  由 Tech Lead 或 Release Manager 在 ArgoCD 里手动触发
  或者通过 GitHub 手动触发 workflow_dispatch
```

### 12.3 部署工具：ArgoCD GitOps

项目用 **ArgoCD** 管理 Kubernetes 部署，是 GitOps 模式：

```
GitOps 模式的核心思路：
  代码仓库（Git）= 唯一真相来源
  ArgoCD 持续监听 Git 仓库里的 Helm Chart
  一旦 Chart 有变化（新镜像、新配置）→ ArgoCD 自动同步到 K8s
  不需要手动 kubectl apply
部署流程：
  CI 构建新镜像 → 推到镜像仓库（Artifactory）
        ↓
  CI 更新 Helm Chart 里的镜像版本号 → 推到 GitOps 仓库
        ↓
  ArgoCD 检测到 GitOps 仓库变化
        ↓
  ArgoCD 自动 helm upgrade → K8s 滚动更新 Pod
```

从 `build.yml` 可以看到部署目标配置：

```yaml
# merge 到 develop 后，自动部署到这两个环境
deployment-target:
  rgm/argocd-gitops-rgm-testing/rgm-k-rgm-int-us21-non-kyma/rgm-int
  rgm/argocd-gitops-rgm-testing/k-rgmsh-int-eu12-co/int
```

### 12.4 Helm Chart 是什么？

Helm 是 Kubernetes 的"包管理器"，Helm Chart 是一套 K8s 配置模板：

```
.ci/charts/rgm-planning/
  Chart.yaml          ← Chart 元信息（名称、版本）
  values.yaml         ← 默认配置
  values.production.yaml ← 生产环境覆盖配置（Pod 数量、资源限制等）
  templates/
    app.yaml          ← Deployment（Pod 定义）
    service.yaml      ← Service（网络暴露）
    hpa.yaml          ← HPA（自动扩缩容）
    ...
```

部署时，Helm 把 `values.yaml` + 对应环境的 `values.xxx.yaml` 合并，渲染成最终的 K8s yaml，然后 apply 到集群。

**你作为开发不需要手动操作 Helm**，CI/CD 自动处理。但要知道：

```
想改某个环境的配置（比如增加 Pod 数量）
  → 修改对应的 values.xxx.yaml
  → 提 PR
  → merge 后 CI 自动部署生效
```

### 12.5 生产部署的完整流程

```
① 代码 merge 到 develop
         ↓
② CI 自动部署到 INT 环境（两个区域）
         ↓
③ 回归测试 + 冒烟测试通过
         ↓
④ 打 Release Tag（触发 pushTag.yml workflow）
   git tag v1.2.3
   git push origin v1.2.3
         ↓
⑤ CI 把 Helm Chart 推到 release 制品库
   （与 develop 时推到 testing 制品库不同）
         ↓
⑥ 在 ArgoCD 里把 stage 环境指向新版本
         ↓
⑦ Stage 验收（UAT）通过
         ↓
⑧ 在 ArgoCD 里把 production 指向新版本
   → K8s 滚动更新（先起新 Pod，再停旧 Pod，零停机）
         ↓
⑨ 上报 Cumulus（SAP 内部发布记录系统）
```

**作为实习生，你一般只参与 ①②③，④⑤⑥⑦⑧⑨ 由 senior/release manager 操作。**

## 13. 面试常见问题

**Q: 你们的 CI/CD 是怎么做的？**

> "用 GitHub Actions + SAP Piper 框架。PR 提交后自动触发 Pipeline，包括编译、单元测试（通过率必须 ≥ 92%）、集成测试、Sonar 代码质量扫描、BlackDuck 依赖安全扫描、CodeQL 静态分析。全部绿了才能 merge。merge 后自动构建 Docker 镜像，通过 Helm Chart 部署到 Kubernetes（SAP BTP），用 ArgoCD GitOps 管理部署状态。"

**Q: 怎么做集成测试的？**

> "用 Cucumber BDD 框架，测试用 Gherkin 语法写 feature 文件，描述完整业务流程。测试覆盖从 HTTP 请求进来、经过 Spring 容器、写数据库、到 API 响应的全链路。本地跑时用 H2 内存数据库，CI 上跑真实环境。我们有 30+ 个 feature 文件，覆盖促销管理、账户计划、拆分计算等核心业务。"

**Q: 发现 Bug 后你们怎么处理？**

> "先本地复现，加日志定位到具体方法。然后先写一个能复现 Bug 的单元测试（TDD 风格），让它失败；再修代码让测试通过。这样既修了 Bug 又保证了以后不会回归。修完跑全量 UT 确认通过率在 92% 以上，再提 PR 走 CI。"

**Q: 数据库和 Redis 你们怎么查看线上数据？**

> "本地用 DBeaver 连 HANA，或者在 BTP 的 HANA Database Explorer 里直接跑 SQL。Redis 本地用 redis-cli 或 Redis Insight GUI，线上通过日志观察。Kafka 本地有 Redpanda Console 这个 Web UI，可以实时看 topic 消息和 Consumer 消费进度。"
